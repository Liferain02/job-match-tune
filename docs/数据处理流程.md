# 数据处理流程

> 状态说明（2026-08-09）：本文保留数据链路的设计与演进细节；后文部分样本数量和外部源可用性是 2026-05/06 的实验快照。当前推荐入口是 `scripts/data/build_current_data_pools.sh`，最新审查结论见 `后训练与数据流程优化_2026-08-09.md`。

## 1. 目标

这份文档只讲数据，不讲模型训练细节。

项目里的数据链路目标一直是两件事：

1. 把公开招聘 JD 持续沉淀成一个可复用的原始职位库。
2. 把原始职位库持续加工成适合当前任务口径的 SFT 数据。

这里的“当前任务口径”指的是固定的结构化抽取字段：

- `岗位方向`
- `核心职责`
- `必备技能`
- `加分项`
- `经验要求`
- `学历要求`

因此，原始 JD 多并不等于可训练样本多。中间还要经过抓取、统一 schema、清洗、去重、规则标注、样本筛选和分层。

---

## 2. 数据链路总览

当前推荐链路是：

1. 抓取或导入公开职位数据
2. 写入 `raw JSONL + SQLite`
3. 统一映射到 `jd_raw` 原始表
4. 清洗、去重并构造 JD、简历、匹配候选池
5. 按原始来源分组切分，构造三项任务的 SFT 数据
6. 按配置抽取多任务集；同一来源的模板变体不会优先挤占样本额度
7. 从 SFT 正例构造结构化 hard negative preference 数据
8. 生成质量、隐私、泄漏、来源多样性和 preference readiness 报告

一键执行：

```bash
bash scripts/data/build_current_data_pools.sh
```

`data/sft/`、`data/sft_expanded/` 和 `data/sft_multilingual_weak/` 属于历史或专项实验路径，不再是当前 14B 多任务训练的推荐入口。

对应代码和脚本：

- 抓取器：`src/jobmatch_tune/crawler/`
- 清洗与规则：`src/jobmatch_tune/preprocess/`
- 数据构造：`src/jobmatch_tune/dataset/`
- 数据脚本：`scripts/data/`

## 3. 第一阶段：从单一官网源起步

项目最开始不是大规模抓站，而是先验证一条最小可行链路。

### 3.1 腾讯公开招聘

第一条稳定源是腾讯公开招聘。

原因：

- 公开接口相对稳定
- 技术岗占比高
- JD 结构完整
- 职责、要求、学历、经验等字段比较容易从正文抽出来

抓取器：

- [`tencent_careers.py`](../src/jobmatch_tune/crawler/tencent_careers.py)

关键词配置：

- [`tencent_keywords.txt`](../configs/tencent_keywords.txt)

抓取方式：

- 按关键词分页请求腾讯公开职位接口
- 详情页再抓完整 JD
- 结果同时写：
  - `data/raw/tencent_jd_raw.jsonl`
  - SQLite `jd_raw`

这个阶段的目标不是追求大，而是先把 `raw -> clean -> sft` 跑通。

---

## 4. 第二阶段：扩公开官网中文源

只靠腾讯不够，后面按“稳定、匿名、结构完整”的优先级，逐步接了更多中文官网源。

### 4.1 百度招聘

百度招聘不是直接调一个公开 JSON 列表，而是利用 SSR 页面里埋的 `window.__INITIAL_DATA__`。

抓取器：

- [`baidu_talent.py`](../src/jobmatch_tune/crawler/baidu_talent.py)

关键词配置：

- [`baidu_keywords.txt`](../configs/baidu_keywords.txt)

做法：

1. 搜索页按关键词拿职位列表
2. 详情页解析 SSR 数据
3. 提取岗位标题、正文、地点、公司等字段
4. 写入：
   - `data/raw/baidu_jd_raw.jsonl`
   - SQLite `jd_raw`

### 4.2 京东招聘

京东这条线价值很高，因为匿名列表接口比较稳定。

抓取器：

- [`jd_careers.py`](../src/jobmatch_tune/crawler/jd_careers.py)

做法：

1. 调京东公开招聘匿名 API 拉职位列表
2. 分页遍历职位
3. 再抓详情并映射到统一 raw schema
4. 写入：
   - `data/raw/jd_careers_raw.jsonl`
   - SQLite `jd_raw`

### 4.3 Moka 托管招聘官网

Moka 是后面最有效的中文官网扩量来源之一。

原因：

- 很多公司官网都基于同一套 Moka 招聘 API
- 接口一致性好
- JD 通常比较完整
- 技术公司占比高

抓取器：

- [`moka_careers.py`](../src/jobmatch_tune/crawler/moka_careers.py)

源配置：

- [`moka_sources.yaml`](../configs/moka_sources.yaml)

做法：

1. 在 `moka_sources.yaml` 里维护可用公司源
2. 每个源通过 `org_id` 或站点配置调用同一套职位接口
3. 统一拉列表和详情
4. 写入：
   - `data/raw/moka_jd_raw.jsonl`
   - SQLite `jd_raw`

这条线后面陆续接入了：

- 岚图
- 申万宏源
- 东方财富
- 中控
- 智源
- 华勤
- 微步
- 华虹
- 阶跃星辰
- 若干游戏、云、基础设施公司

### 4.4 为什么没有把字节、阿里、华为接进主链路

不是没研究，而是性价比不够高。

结论是：

- 字节：接口、签名都定位到了，但网关态校验更重，匿名直调不稳定
- 华为：前端线索明确，但匿名 API 没真正打通
- 阿里：更像 SPA 壳，列表接口没有确认到稳定公开 JSON

所以主链路优先接的是：

- 腾讯
- 百度
- 京东
- Moka

这几条匿名稳定的中文官网源。

## 6. 原始数据怎么落盘

每条职位最终会进入两个地方：

1. `data/raw/*.jsonl`
2. `data/jobmatch_tune.sqlite3` 的 `jd_raw`

这样做有两个目的：

- JSONL 适合审查和离线重放
- SQLite 适合统一重建下游、做统计和增量写入

raw 层的原则是：

- 尽量保留来源原貌
- 不在 raw 层做过多“聪明处理”
- 只做最基本的字段映射和去空值

---

## 7. 第四阶段：把原始职位统一成 clean schema

raw 数据来自不同站点，不统一就没法训练。

统一清洗入口：

- [`normalize_jd.py`](../src/jobmatch_tune/preprocess/normalize_jd.py)

对应脚本：

- [`rebuild_data_pipeline.sh`](../scripts/data/rebuild_data_pipeline.sh)

### 7.1 `normalize_jd` 做了什么

它做的事情包括：

1. 统一字段名
2. 规范正文文本
3. 提取结构段落
4. 抽语言
5. 做规则标注
6. 标记 `sft_ready`

输出文件：

- `data/interim/jd_clean.jsonl`

### 7.2 段落拆分

在 clean 层会尝试把正文拆成：

- `responsibilities`
- `requirements`
- `bonus`

这一步是后面构造训练 labels 的基础。

### 7.3 基础规则抽取

规则都放在：

- [`jd_field_rules.py`](../src/jobmatch_tune/preprocess/jd_field_rules.py)

主要负责：

- `岗位方向` 推断
- `学历要求` 抽取
- `经验要求` 抽取
- `技能` 抽取

这一步很关键，因为很多数据源本身并没有结构化标签，只能靠规则和正文信号做弱监督。

### 7.4 原子产出与新鲜度

规范化不会直接覆盖正式 JSONL，而是先写同目录临时文件，全部成功后再原子替换。进程中断时，上一份完整产物仍可继续审查，不会留下看似存在但实际截断的文件。

`data/interim/jd_clean.manifest.json` 记录原始数据库状态、产物行数和 SHA-256，以及真正影响标签语义的规则文件哈希。训练 readiness 同时检查该清单与十个下游产物的依赖时间；原始数据或语义规则变化但派生数据没有重建时，`pipeline_fresh=false`，不会进入训练。这里没有引入额外的数据平台，仍使用文件、哈希和已有统一脚本。

## 8. 第五阶段：去重

清洗后的职位很多会重复。

去重入口：

- [`deduplicate.py`](../src/jobmatch_tune/preprocess/deduplicate.py)

输出：

- `data/interim/jd_clean_dedup.jsonl`

去重目的：

- 避免同一个职位被多个渠道重复写入
- 避免训练时重复样本放大偏差
- 保持评估集和训练集的分布更干净

## 9. 第六阶段：为什么“原始数据多”不等于“高质量 SFT 多”

这是这个项目里最重要的一个经验。

项目过程中，原始职位库已经做到二十多万中文、总量接近三十万。但默认高质量 SFT 集并没有同步到万级。

原因不是抓不到数据，而是下面这几个问题：

1. 很多职位不是当前任务范围内的软件/AI 技术岗
2. 很多职位是业务、运营、销售、供应链、制造、交付岗
3. 很多职位正文不完整
4. 很多职位方向在当前 schema 下不应该硬标

所以后面明确把数据分成了多层，而不是只保留一个 `data/sft/`。

---

## 10. 数据分层是怎么做的

核心逻辑在：

- [`build_sft_dataset.py`](../src/jobmatch_tune/dataset/build_sft_dataset.py)

### 10.1 默认高质量集 `data/sft/`

这是默认主训练集，只保留高信任样本。

当前准入条件大致是：

1. 中文
2. `sft_ready=true`
3. 来源属于高信任官网源
4. 职位标题有明确技术信号
5. 标题没有明显业务/销售/运营信号
6. 必须能识别出 `岗位方向`
7. 职责/要求结构要基本完整
8. 至少有学历、经验、技能中的一个

这里故意收得严，因为这套数据要直接拿去做默认 SFT。

### 10.2 扩展实验集 `data/sft_expanded/`

这是第二层数据。

特点：

- 允许更多 `sft_ready` 样本进入
- 可以混入少量高置信弱标注技术岗
- 适合做扩量实验、第二阶段 SFT、对照实验

它不是默认 demo 版本的数据来源。

### 10.3 中英混合弱标注集 `data/sft_multilingual_weak/`

这是规模优先的实验集。

用途：

- 做扩量实验
- 做第二阶段增量训练
- 做多语言或弱监督对照

不适合直接替代默认高质量集。

---

## 11. 为什么后来把“2 万高质量集”撤回了

这个问题必须说明白。

中间有一段时间，我确实把默认集拉到过 `2 万`。但后面在你明确强调“数据质量是核心中的核心”之后，我重新审了准入逻辑和样本来源，结论是：

- 那版 `2 万` 里混了过多弱标注样本
- 还混了不少其实不属于当前 schema 的职位
- 如果直接拿去训默认模型，会把错误方向和错误边界学进去

因此后面做了两件事：

1. 把默认 `data/sft/` 收回到严格高质量口径
2. 把大样本量方案拆到 `data/sft_expanded/` 和其他实验链路

这不是推翻数据工作，而是把“数量”和“默认训练质量”分开。

---

## 12. 第七阶段：修复最严重的数据质量问题

### 12.1 问题一：标题规则过窄，误杀真实技术岗

后面我们发现默认高质量集掉得太快，不是因为数据不够，而是因为标题准入规则太窄。

当时统计过的主要失败原因里，`title_not_included` 是最大头。

后来做的修复包括：

- 扩充技术标题信号
- 加入方向相关的标题补充规则
- 把 `产品经理 / 客户端 / 嵌入式 / 运维 / 安全` 等真实技术类纳入 schema

### 12.2 问题二：上游方向推断会把未知职位默认映射到第一个类

这是后面发现的更严重问题。

之前 `infer_job_direction()` 在完全匹配不到时，会回落到 schema 的第一个类。这个行为会把很多非技术岗硬标成 `AI应用开发`。

后面已经修掉：

- 匹配不到就返回空，不再伪造方向
- 只对明确技术模式做方向归类

这一步虽然会让默认高质量集数量下降，但质量会明显更可信。

### 12.3 问题三：高信任官网里仍然有大量“方向为空”的样本

修掉错误回退后，出现了一个更真实的结果：

- 大量高信任官网样本现在 `岗位方向=""`

这不是坏事，而是说明：

- 之前有一部分样本其实被错误标了方向
- 现在需要从这些空方向样本里“回收真正的技术岗”

后续优化重点就是这一步。

## 13. 当前数据脚本怎么用

### 13.1 抓官网数据

```

单独刷新某个源：

bash scripts/data/refresh_baidu_data.sh

```

```bash
bash scripts/data/import_public_job_exports.sh
bash scripts/data/import_chinese_job_exports.sh
```

### 13.3 重建 clean 和训练集

```bash
bash scripts/data/rebuild_data_pipeline.sh
```

使用 SQLite 重建时，规范化过程默认按 1000 条流式读取和写回，可通过 `--batch-size` 调整。2026-08-09 在 293582 条数据上验证：输出与旧实现 SHA-256 完全一致，峰值内存从约 6.3GB 降到约 102MB。

它会依次产出：

1. `data/interim/jd_clean.jsonl`
2. `data/interim/jd_clean_dedup.jsonl`
3. `data/sft/`
4. `data/sft_expanded/`

截至当前这版仓库，数据层大致是：

- `jd_clean.jsonl`: `293582`
- `jd_clean_dedup.jsonl`: `269351`
- `jd_train_pool_combined.jsonl`: `38720`

当前默认高质量集：

- `data/sft/train.jsonl`: `2707`
- `data/sft/valid.jsonl`: `338`
- `data/sft/test.jsonl`: `339`

当前 5300 条 JD 质量集：

- `data/sft_jd_quality/train.jsonl`: `4240`
- `data/sft_jd_quality/valid.jsonl`: `530`
- `data/sft_jd_quality/test.jsonl`: `530`
- 分层来源：`strict=3217, strict_plus=270, quality_weak=1813`
- 弱外部来源：`2083 / 5300 = 39.30%`，低于 40% 上限
- 核心职责空值：`10 / 5300 = 0.19%`，分段修复前为 75 条；剩余样本没有足够原文依据自动补写
- 经验要求空值：`2692 / 5300 = 50.79%`；正文仍可由当前规则确认恢复的空标签为 0
- 必备技能空值：`946 / 5300 = 17.85%`
- 学历要求空值：`1404 / 5300 = 26.49%`；此前确认的 11 条研究生/学士/专科漏标仍由规则覆盖，当前比例变化来自质量配额重排

扩容探测结论：

- 权利不明的两个 GitHub 爬虫源退出训练后，5500 条版本的弱外部来源达到 41.98%，且 `经验要求` 空值率为 56.35%，超过 56% 门禁。
- 40% 弱来源上限下，5500 条只能生成 5391 条，说明没有足够合格官网样本补位。
- 因此默认值调整为 `5300`。最新方向清洗并重建后，保留 3217 条 strict 官网样本，弱外部来源为 39.30%，`经验要求` 空值率为 50.79%，JD 解析训练门禁通过。这里选择质量优先，不为凑行数放回权利不明或更弱的样本。

当前扩展实验集：

- `data/sft_expanded/train.jsonl`: `16000`
- `data/sft_expanded/valid.jsonl`: `2000`
- `data/sft_expanded/test.jsonl`: `2000`

这里最重要的不是数字本身，而是口径：

- `data/sft/` 是默认主训练集
- `data/sft_jd_quality/` 是当前 JD 解析任务的 5300 条候选训练主线
- `data/sft_expanded/` 是扩量实验集
- 不能再把这些层混为一谈

`data/sft_jd_quality/` 的构建方式不是简单把弱标注样本混进去，而是分层追加：

1. `strict`：高信任中文官网源，经过技术岗标题、方向、结构化职责/要求等过滤。
2. `strict_plus`：从 combined pool 里回收结构完整、方向和学历较明确的样本。
3. `quality_weak`：对弱源和公开数据做保守回收，要求具备岗位方向、学历或经验、至少两个技能、足够长的职责/要求文本，并清理“本科/硕士误入经验字段”等噪声。
4. `bootstrap`：兜底层。当前 5300 条构建未使用该层；保留分层定义只是为了让未来真实缺口可见，不用兜底数据冒充高质量样本。

## 15. 这条数据链路目前最清楚的结论

### 15.1 做对了的事

1. 没有只靠一个站点
2. 原始职位库已经做大
3. 官网源和公开导出源已经统一到一套 clean schema
4. 数据已经分层，不再把弱标注直接混进默认集
5. 已经把一个严重的方向误标 bug 修掉
6. 岗位方向强信号审计已纳入 readiness 报告：最新重建的 2467 条单一强标题信号样本中有 33 条冲突候选（1.34%）。复合岗位和最终抽样变化会使该数值小幅波动，因此它用于人工复核，不直接作为自动改标门禁。
7. 经验要求明确年限漏标审计已纳入 readiness。修复空格、中文数字、范围写法和毕业日期误抽后，当前质量集的经验空值为 2692 / 5300（50.79%），其中可由当前规则确认恢复的数量为 0。

## 16. Match 配对的最小清洗与来源约束

Match 训练池使用 JD 组合池和简历组合池做规则配对。配对前只执行三项可客观验证的处理：

1. 删除 JD 中上游教育抽取任务的包装行，不删正文学历要求。
2. 删除简历联系方式和年龄、性别、婚育、户籍等敏感个人资料，再计算标签和去重。
3. `hf_job_educational_` 弱来源在配对所用 JD 中最多占 40%；其他来源不足时宁可少生成，不突破上限凑数。

2026-08-13 按当前规范化代码最终重建：合成池 4,800 条，组合池为 4,798 条（train 3,840 / valid 479 / test 479）；教育弱来源 1,919 条（40.00%），包装行、隐私命中和实体跨 split 均为 0。与私有 Match Gold V1 的完整配对、JD、简历及两个单任务池重合均为 0。

旧 Match SFT 只按完整配对 ID 切分，虽然配对本身不重复，但 1,200 个独立 JD 中有 700 个（58.33%）跨 train/valid/test，2,418 份简历中有 611 份（25.27%）跨 split。现在配对前先分别按脱敏后的 JD 和简历内容切分实体，只允许同一 split 内配对。重建后 Match SFT 为 train 3,838 / valid 480 / test 480，1,200 个 JD 实体和 2,409 个简历实体的跨 split 数均为 0。readiness 直接审计两类匿名实体键，不再只查完整 prompt 哈希。Match Gold 审计也同时检查完整配对、Match 池中的单独 JD/简历、JD 单任务池和 Resume 单任务池，当前五种重合均为 0。

Match SFT 中的“推荐投递岗位方向”原本全部是五种泛化占位语。这些值现在由已有的规范 JD/简历方向生成，共覆盖 16 个实际方向。所有 prompt 都保留 `命中项目` 字段；后续证据审查又删除了只因“算法工程方向”等宽泛文字而命中的 2,337 条伪项目证据。当前 1,587 条配对保留 1,734 条包含明确 JD 技能的项目证据。readiness 对单任务 Match 和多任务中的占位推荐、项目字段丢失均设置 0 容忍门禁。

学历硬约束审查发现旧 Match 池有 214 条标签与输入语义不一致：54 条误放行、160 条误拒绝，并影响 76 条匹配等级。修复并完整重建后，4,798 个配对 ID 与 split 均保持不变，学历标签矛盾数降为 0。readiness 现在会重放每条配对的学历要求与简历学历，任一矛盾都会阻断 Match SFT。

经验硬约束审查发现“25年校招”曾被误当成 25 年经验，造成 3 条错误的经验满足标签；2026-08-13 最终池中 1,944 条明确年限要求样本全部为不满足（train 1,540 / valid 208 / test 196）。readiness 要求每个含明确年限要求的 split 同时覆盖满足和不满足两类；并显式要求真实/人工 Pair 质量证据，当前 `match.ready_for_sft=false`。这里不通过给合成简历编造年限来平衡标签。

这些数据仍然 100% 是合成配对，所以只能说格式和数据门禁通过，不能说真实人岗匹配质量已验证。
