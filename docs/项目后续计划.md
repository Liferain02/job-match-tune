# 项目后续计划

更新时间：2026-08-09

后续只围绕三项核心功能推进：JD 解析、简历解析、人岗匹配。每项改动都必须能改善准确率、解释性、速度或基本可用性，不为了“架构完整”增加新模块。

产品交互的已落地方案、开源项目取舍和分阶段验收见 [产品交互与优化目标](产品交互与优化目标.md)。当前最优先的是让用户更快拿到可核验的匹配依据，而不是扩展新的招聘管理功能。

## 持续审查目标

本项目采用持续目标，不把“列出下一步”当成完成：循环核验数据获取与许可、版本和哈希、清洗去重、敏感信息、实体级切分、标签质量、训练准入、评测泄漏和产物新鲜度。每轮只选择一个影响最大的实际缺口，完成代码或数据修复、测试、真实重建和中文文档后立即进入下一轮；不引入数据平台、任务队列或其他非必要架构。

当前已完成的循环：

1. 公开 JD 来源版本、哈希、正文权利与训练用途门禁。
2. 无许可证来源旁路清理、弱外部来源 40% 上限和 5300 条质量集重建。
3. OCR/格式变体的跨切分泄漏检测与连通分组切分。
4. 293582 条 JD 规范化流式化，输出哈希不变，峰值内存由约 6.3GB 降到约 102MB。
5. 规范化原子写入、原始库/语义规则哈希清单和下游产物新鲜度门禁。
6. 岗位方向强标题信号审计；修复算法、安全方向优先级和弱来源二次覆盖。最新重建后有 34 条冲突复核候选（占 2479 条单一强信号样本的 1.37%）。
7. 经验要求漏标与日期误抽修复：支持“3 年以上”“至少两年”“工作年限3～5年”等常见写法，拦截毕业日期 `1-2024年`；质量集经验空值从 2899 降至 2727（54.70% → 51.45%），剩余可确认规则漏标为 0。
8. JD 质量集构建改为单遍筛选 269351 条 strict 输入；真实基准输出哈希完全一致，峰值 RSS 从约 3329024KB 降至 347136KB（约 -89.6%）。
9. JD 去重改为边判重边写盘，并只缓存幂等规范化后的相似度文本；269351 行输出哈希不变，峰值 RSS 从约 1246356KB 降至 714916KB（约 -42.6%）。
10. 技能 schema 纳入新鲜度哈希，并补 23 个经空标签审计确认的客户端、前端、游戏、算法和硬件技能；技能空值从 1106 降至 943（20.87% → 17.79%），弱来源降至 39.43%。
11. 学历抽取补齐研究生、学士和专科表述，并完整保留“优先”语义；11 条明确漏标全部进入最终集，学历空值从 1403 降至 1392（26.47% → 26.26%），弱来源降至 39.42%。
12. JD 职责分段支持同一行多个标题、HTML/方括号标题和“岗位描述/核心职责”等常见别名，移除会误切普通句子的泛化“优先”标题；同时仅对高置信小米历史倒置数据交换职责与要求。全量重建后核心职责空值从 75 降至 10（1.42% → 0.19%），其余缺口没有足够原文依据，不自动补写。
13. 基础 JD SFT 构建改为单遍收集强样本和弱候选，不再加载 269351 个完整对象。真实 strict/expanded 六个输出 SHA 不变；expanded 峰值 RSS 从约 3341824KB 降至 297472KB（约 -91.1%），strict 仅 67072KB。
14. 弱结构 JD 池把筛选、转换和去重合并到单遍读取。真实 36090 行输出 SHA 不变，峰值 RSS 从约 1461760KB 降至 260096KB（约 -82.2%）。
15. JD 组合池按 manual、supplemental、weak、public 的既有优先级边读边转换和去重，不再加载 269351 条 manual 全集。真实 39765 行输出 SHA 不变，峰值 RSS 为 301568KB。

当前继续审查下游产物新鲜度：规范化已哈希语义规则，但其他 builder 目前主要依赖输入/输出时间，需确认代码语义变化是否可能让旧产物仍显示 fresh。只为核心构建器补直接依赖，不建立通用编排平台。

## 1. 提高 JD 和简历解析质量

- 扩充人工留出评测集，优先补当前容易出错的岗位方向、技能别名、中文经验年限、复杂 PDF 和中英混排样本。
- 对模型输出执行统一 schema 校验，明确区分 JSON 解析失败、字段缺失和业务值错误。
- 评测报告分别展示原始模型输出和规则修正后的结果，确认提升到底来自模型还是后处理。
- 只保留一条推荐的数据构建主线；旧实验分支不再继续扩展。

完成标准：三项任务都能在未参与训练的人工样本上稳定复测，新增规则不会让已有正确样本回退。

## 2. 改善人岗匹配

- 继续保留当前可解释的方向、技能、学历、经验和项目命中结果。
- 先完善技能别名和评分边界，再判断是否真的需要语义模型；没有人工对照数据前不引入 embedding、reranker 或新的大模型。
- 让“匹配分数”和“模型解释”解耦：基础分数可直接返回，用户需要详细建议时再调用模型生成解释。
- 为评分规则增加版本号，避免规则变化后旧报告无法比较。

完成标准：人工对比中，分数高低与真实匹配顺序基本一致；解释内容可以追溯到 JD 或简历原文，不编造经历。

## 3. 保证核心流程可用

- 补文件类型检查、清晰的上传错误和超大文件测试。
- 优先优化一次匹配的三次顺序生成；确认瓶颈后再做并行或后端批处理。
- 保持 API、前端和训练脚本的基本回归测试，修复影响主流程的问题。
- 提供一个小型、脱敏、可公开的端到端示例，验证安装、解析和匹配流程。

完成标准：新环境可以按 README 跑通示例；文本、PDF、OCR sidecar 和匹配流程都有明确成功/失败结果。

## 暂不做

- 不扩成完整 ATS，不做职位发布、候选人管道、多租户和组织权限。
- 不做简历模板编辑器、求职信、面试题等外围功能。
- 不继续增加一次性招聘网站 probe，除非核心训练数据确实不足。
- 不为现有规模提前引入微服务、插件系统、任务队列或复杂前端构建体系。
- 不为了减少文件数量大规模重构稳定代码；只在核心流程确实难以维护时拆分。
