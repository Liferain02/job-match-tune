# JD 解析实现逐层拆解

## 目标与入口

JD 解析要把标题、职责、要求、加分项转换为稳定 JSON，同时守住“职责中出现过”不等于“必备技能”的语义边界。调用入口是 `ModelService.parse(ParseRequest(task="jd_parse"))`；Prompt 来自 `dataset/templates.py::jd_parse_prompt`，Schema 来自 `schemas.py::JDParseOutput` 和 `inference/structured_output.py`。

## 实现步骤

1. `build_prompt` 拼入系统约束“严格基于输入，不编造”。Transformers 使用 chat template；vLLM 使用兼容消息请求及 JSON schema response format。
2. 原始生成交给 `postprocess_json.py::parse_json_output`：`remove_thinking` → `extract_json_text` → `repair_json_text` → JSON decode。
3. `normalize_parsed_data` 调用 `_split_misplaced_fields` 修复字段串位，补回可从原文确定的职责行，再规范方向、学历、经验和列表。
4. `jd_skill_evidence.py::collect_skill_evidence` 按 section 保存 requirement、responsibility、bonus、other 证据。只有 requirement evidence 能进入公开 `必备技能`；模型字段只是候选集合，不是证明。
5. `skill_canonicalization.py` 只在已知词表内处理别名、OCR 空格和连字符，输出规范技能名及内部 `技能证据`。

输入 `岗位职责：用 Kafka 处理日志；任职要求：熟悉 Java` 时，输出必备技能只能有 Java；Kafka 可留在职责证据中，不能影响缺失技能扣分。

## 调用关系和数据去向

`/api/parse` 直接把规范结果返回前端；`/api/match` 则把结果传给 `compute_match_rule_result`。离线数据侧，`preprocess/normalize_jd.py::normalize_jd_row` 使用 `jd_field_rules.py` 生成训练池结构字段；这条弱监督链与在线模型后处理职责不同，但共享 `configs/label_schema.yaml`。

## 错误、测试与限制

- 严格生成不可用时，Transformers 路径仍会走容错 JSON 后处理；无法组成对象则明确失败。
- 原文没有 section 标记时证据只能归入 other，系统宁愿少报必备技能，也不把上下文出现冒充硬要求。
- 测试集中在 `tests/test_postprocess_json.py`、`tests/test_jd_skill_evidence.py`、`tests/test_jd_field_rules.py`、`tests/test_structured_output.py`。
- 局限：中文/英文混排和非标准栏目仍可能降低 section 识别；有限方向 taxonomy 不能覆盖全部行业职位；证据策略提高精度但可能损失召回。
