# 请求生命周期与完整调用链

## 为什么这样分层

产品的核心不是一次 LLM 调用，而是把不可控生成限制在结构化抽取和解释，把硬条件交给可复查规则。调用链是：输入校验 → 文本提取 → JD/Resume 并行解析 → 规范化 → 确定性匹配 → 解释生成 → 前端展示。这样能把“抽错字段”“规则错”“解释矛盾”分别定位。

## 调用者、入口与参数

- 前端 `frontend/src/App.js` 调用 `/api/parse`、`/api/match`、批量及文件接口。
- FastAPI 入口在 `src/jobmatch_tune/api/server.py`：`parse`、`match`、`batch_parse`、`batch_match`、`resume_file_parse`、`jd_file_parse`、`match_files`。
- 文本匹配入口参数为 `MatchRequest(jd_text, resume_text, max_new_tokens)`；文件入口接收两个 `UploadFile`。
- `ModelService` 根据 `INFERENCE_BACKEND` 选择 Transformers 或 vLLM-compatible server，并记录 backend、model、adapter 和 parse mode。

## 逐步变化与返回

1. Pydantic 先验证任务名、文本非空及 token 上限。
2. 文件路径通过 `validate_upload_content` 做大小、扩展名、魔数与可解析性校验，再进入 PDF/DOCX/图片/文本提取。
3. `ModelService.match` 同时提交 JD 和 Resume 解析；两者无数据依赖，完成后才调用 `compute_match_rule_result`。
4. `parse_json_output` 清除思维文本、抽取/修复 JSON、规范字段。JD 技能必须带“任职要求”证据。
5. 规则结果包含方向关系、学历/经验、命中/缺失技能、分项与启发式策略。它被序列化进 `match_prompt`，约束解释模型。
6. API 返回 `jd_parse`、`resume_parse`、`rule_result`、`analysis`、`execution` 和延迟；前端只展示，不在浏览器重算业务规则。

示例：JD 要求 Java/Kafka，简历只有 Java。规范化后 `命中技能=[Java]`、`缺失技能=[Kafka]`，解释可以建议补 Kafka，但不能把 Kafka 写成候选人优势。

## 失败、降级、测试与边界

- JSON 解析失败返回 `ok=false` 和错误，不拿半截输出继续评分。
- 文件错误使用 `too_large`、`unsupported_type`、`extension_content_mismatch`、`corrupt_file` 等结构化错误；昂贵 OCR/模型调用不会发生。
- 批量接口逐项保留失败，避免一个坏样本让整批无结果。
- 对应测试：`tests/test_server.py`、`tests/test_upload_validation.py`、`tests/test_rule_engine.py`、`tests/test_postprocess_json.py`、`tests/frontend_report_smoke.mjs`。
- 当前 `server.py` 较集中，但规模尚小；没有账号、队列、异步任务状态和多租户隔离，不能直接公网部署。
