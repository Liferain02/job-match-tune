# 项目定位、讲述主线与岗位匹配

## 一、先给出准确定位

JobMatchTune 不是一个“输入简历，Qwen 直接输出匹配分”的聊天 Demo，也不是一个可以直接部署给企业使用的 ATS。更准确的定义是：

> 面向中文招聘场景的 LLM 后训练、结构化抽取、确定性匹配和可信评测工作台。

这个定位包含四层能力：

1. 数据层：公开 JD、合法简历候选、来源许可、隐私、清洗、去重和实体级切分。
2. 模型层：Qwen3-14B、QLoRA SFT、历史 DPO、结构化生成和双推理后端。
3. 产品层：JD 解析、Resume 解析、规则匹配、解释生成、文件上传、批量接口和 Web UI。
4. 治理层：Gold、三层评测、泄漏审计、Readiness、训练暂停门禁和运行 manifest。

面试最应该强调的不是“我用了14B模型”，而是：系统如何把不稳定的模型能力约束成可审计产品结果，以及项目如何在发现数据证据不足后主动停止训练。

## 二、项目解决什么问题

中文 JD 和简历存在三个根本困难。

第一，输入是非结构化文本。岗位要求可能散落在标题、职责、任职要求和加分项，简历技能可能藏在项目或实习描述里。单纯关键词匹配漏召回，单纯 LLM 又可能编造。

第二，匹配不是纯语义相似。一个候选人写了很多与岗位相近的技术，不代表学历、年限或岗位方向满足；JD 职责里提到 Kafka，也不一定意味着 Kafka 是硬性门槛。

第三，评测很容易自欺。模板变体可能被当成独立样本，同一 JD/Resume 可能跨 train/test，规则合成 Pair 可能被误称为真实行为数据，已检查 Gold 上的修复可能被误称为新泛化能力。

因此系统没有采用“让 LLM 一步完成全部判断”，而是拆为：

```text
LLM 负责理解与抽取
        +
Normalization 负责格式和证据边界
        +
Deterministic Policy 负责硬条件和评分
        +
LLM 负责基于事实生成解释
        +
Evaluator 分层验证每一层
```

## 三、30秒版本

> 我做了一个中文 JD 与简历匹配系统。它不是让大模型直接输出一个不可解释的分数，而是先用 Qwen3-14B 分别解析 JD 和简历，再通过有证据约束的技能归一化、岗位方向兼容和确定性规则计算匹配结果，最后让模型只负责解释。项目后期我重点重构了数据和评测体系，发现模板膨胀、实体级泄漏以及4,798个 Match Pair 全部为合成数据，因此增加 SourceGroup、Entity Split、Gold 隔离和训练 Readiness 门禁。最终历史25条项目内人工复核 Gold 的匹配等级和方向准确率是0.96，但因为真实 Pair 仍不足，门禁主动阻止了继续 SFT/DPO。

## 四、3分钟版本

可以按“问题—方案—困难—结果—边界”讲。

### 1. 问题

招聘文本不是结构化数据库，JD 中职责、硬要求和加分项容易混淆；简历还有 PDF、DOCX、扫描件和 OCR 噪声。直接用关键词会丢失上下文，直接让 LLM 打分则很难审计。

### 2. 方案

我把在线匹配拆成三个模型调用。第一次解析 JD，第二次解析 Resume，两者没有语义依赖；得到结构字段后，规则引擎计算方向、技能、学历、经验和项目五个分项；第三次模型调用只根据原文和规则 JSON 生成解释。

在模型输出与规则之间还有一个关键的 semantic normalization 层。比如技能 OCR 只在已知词表内恢复，`Py test` 可以归一成 `Pytest`，但不会对全文做无界 fuzzy match。JD 技能则保存 requirement、responsibility、bonus、other 四类 evidence，只有任职要求证据可以成为必备技能。

### 3. 困难

最大的困难不是模型加载，而是数据可信度。我最初也会关注样本行数和最终指标，后来发现一个简历可以扩成多个模板，15,470条 Resume SFT 实际只有2,557个 source group，而且98.75%的来源组是从 JD bootstrap 出来的；匹配池4,798对全部是规则合成，显式年限样本1,944条全是不满足。于是我把随机 Pair split 改成先按 JD/Resume entity 切分再配对，并把这些事实写进 Readiness gate。

### 4. 结果

项目内冻结的25条人工复核 Gold 上，历史 Product Final 的技能命中/缺失 F1 是0.990649/0.986667，匹配等级和方向 exact match 都是0.96。语义边界修复后的保存预测回归六项结构指标达到1.0，但因为错误样本已经看过，我明确把它标成 `REGRESSION AFTER INSPECTION`，不称为新盲测结果。解释结构一致率是1.0，证据 grounding 是0.92，建议是否提高求职成功率没有数据支持。

### 5. 边界

系统是可审计原型，不是招聘决策产品。启发式分数不是录用概率；当前 Resume、Match、Multitask readiness 都是 false，因此没有继续训练。重新启动项目必须等待合法独立 Resume、人工/真实 Match Pair、新 Blind Gold 或真实用户反馈。

## 五、10分钟讲述结构

第一分钟讲问题和定位；第二到四分钟讲在线三阶段架构；第五到七分钟讲数据污染与 Entity Split；第八分钟讲三层评测；第九分钟讲最重要的失败；第十分钟讲工程边界和停止条件。

建议现场画两条线：上方是离线数据/训练/评测，下方是在线解析/规则/解释。不要画成每次用户请求都经过 SFT。

## 六、项目真正的亮点排序

### 第一亮点：知道什么不该交给 LLM

结构化语义抽取允许模型参与；硬条件判断和最终等级要求稳定，因此交给规则。解释允许生成，但必须读取规则事实。这个边界比“调用了一个大模型”更能体现 AI 工程判断。

### 第二亮点：从结果导向转向证据导向

项目没有把高指标当作终点，而是追问：Gold 是否独立、来源是否多样、Pair 是否真实、建议是否可验证。最终训练被 readiness 阻断，是可信工程闭环的一部分。

### 第三亮点：错误能映射回具体层

Raw 错可能是模型抽取；Normalized 改善可能来自 canonicalization；Product Final 错可能是规则策略；解释错可以再拆为结构矛盾和无证据陈述。这样才能决定该改 Prompt、数据、规则还是评测。

### 第四亮点：不过度设计

项目补了上传校验、批量 API、启动脚本、依赖复现和 benchmark harness，但没有为了简历堆微服务、Redis、Kafka、Celery、账号和多租户。

## 七、适合投递的岗位

### 高匹配

- AI 应用工程 / LLM 应用工程：重点讲混合系统、结构化输出、证据约束和服务化。
- 后训练 / 模型评测工程：重点讲 QLoRA、DPO、Gold、三层评测和训练门禁。
- AI 数据工程：重点讲 source admission、source group、entity split、隐私和数据 profile。

### 较高匹配

- AI 后端 / 推理工程：讲 FastAPI、模型生命周期、并发锁、vLLM 受控并发、文件安全和 benchmark。必须承认当前没有真实 vLLM A/B 数字。

### 中等匹配

- NLP 算法工程：可以讲任务建模和评测，但不要声称提出了新的模型结构或算法论文贡献。

### 不应包装

- 纯研究型模型岗位：项目没有预训练或原创模型方法。
- 成熟 ATS 产品：没有真实企业用户、录用 outcome、鉴权、多租户或合规生产部署。

## 八、最容易说错的三句话

错误：“模型准确率达到96%。”  
正确：“项目内25条冻结 Gold 上，模型解析、确定性 normalization 和规则组合后的 Product Final 匹配等级 exact match 为0.96。”

错误：“我的简历数据有15,470条。”  
正确：“SFT 有15,470个格式样本，但只有2,557个 source group，且98.75%的来源组来自 bootstrap。”

错误：“DPO 把产品效果进一步提升了。”  
正确：“历史上实现并执行过 DPO 流程，但当前 preference 证据和新数据 readiness 不足，新增 DPO 已暂停；不能用训练 loss 代替独立产品收益。”

## 九、工程冻结意味着什么

Engineering Freeze 只表示：在当前证据条件下，继续加规则、合成数据或训练轮次的边际价值很低。它不表示产品已完成外部验证。面试时可以把“知道何时停止”作为项目判断力，而不是把停止描述为无事可做。
