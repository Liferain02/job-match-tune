# 样本血缘、六倍扩增与实体级防泄漏推导

数据条数不是独立信息量。当前简历 SFT 有 15,470 条样本，却只有 2,557 个 `source_group`，扩增比约 6.05；其中 2,525 个组来自 bootstrap。面试时必须能解释这些数字为什么同时“有价值”和“不能过度解读”。

## 1. 三个容易混淆的对象

```text
实体 entity       一份真实或基础简历、一条 JD、一个 JD—简历对
样本 sample       实体渲染成的一条训练对话
变体 variant      同一实体的不同表达或噪声版本
```

例如一份基础简历被渲染为 original、profile_card、bullets、compact、ocr_like、mixed_cn_en 六种形式：数据库里是六条训练样本，统计独立候选人时仍只能算一个实体。

## 2. 六种简历变体实际改变了什么

### original

保留源文本，最接近自然输入。

### profile_card

按目标岗位、教育、技能、实习、项目和优势重排为卡片式文本。

### bullets

把主要字段改写成项目符号，学习列表布局。

### compact

压缩字段和分隔符，学习密集输入。

### ocr_like

替换中英文标点、去句末标点，并注入 `My SOL`、`Py test`、`Kubernet es` 等已知 OCR 噪声。

### mixed_cn_en

使用 Target Role、Education、Skills、Projects 等英文标题，正文仍混合中文。

六种变体共享完全相同的 assistant label。因此扩增训练的是输入格式鲁棒性，不是增加六倍标签知识。

## 3. 一条训练样本的完整形态

```json
{
  "id": "resume_001_ocr_like",
  "task_type": "resume_parse",
  "source_group": "resume_001",
  "messages": [
    {"role": "system", "content": "统一系统提示"},
    {"role": "user", "content": "请解析以下简历……"},
    {"role": "assistant", "content": "{...标准 JSON...}"}
  ]
}
```

`source_group` 会移除 `_ocr` 后缀，确保 OCR 原件和清洁版本仍属于同一实体。

## 4. 为什么随机按行切分会制造虚高

假设同一简历有六个变体，按 80/10/10 独立随机切分。它至少有一个变体进训练集，同时又有变体进测试集的概率很高。模型在测试时可能只需识别相同事实的改写，而非泛化到新简历。

这类泄漏不会被“文本完全去重”发现，因为六个 user 文本不同；标签却完全相同，语义和实体高度相关。

正确约束是：

```text
∀ source_group g, split(g) 只能取 train/valid/test 中一个值
```

## 5. `normalized_input_hash` 做了什么

规范化步骤：

1. Unicode NFKC；
2. 转小写；
3. 只保留 Unicode 类别首字母为 L 或 N 的字符，即字母和数字；
4. SHA-1 哈希。

所以：

```text
“Python / FastAPI”
“python，fastapi”
```

会产生相同或非常接近的规范化内容键。它能抓住标点、空白、大小写不同的重复输入。

它不能证明语义不同：同义改写仍可能产生不同哈希；因此“跨集合 hash overlap=0”只说明没有这种归一化精确重叠，不等于数据完全独立。

## 6. 为什么匹配样本需要 `linked_source_groups`

一个 pair 样本包含两个实体：JD 和简历。仅按 pair id 分组不够。

```json
{
  "source_group": "pair_001",
  "linked_source_groups": [
    "match_jd:<jd_hash>",
    "match_resume:<resume_hash>"
  ]
}
```

考虑：

```text
Pair A = JD-1 + Resume-1
Pair B = JD-1 + Resume-2
```

即使 A、B 的 pair id 不同，它们共享 JD-1。如果 A 在训练、B 在测试，测试仍见过同一 JD。`linked_source_groups` 用来把这种间接相连样本绑定到同一集合。

## 7. 并查集如何完成传递闭包

`split_linked_samples` 使用 union-find：

1. 每个 sample 建一个 `group:<source_group>` 节点；
2. 每个 linked entity 建一个 `linked:<entity>` 节点；
3. user 输入 hash 建一个 `input:<hash>` 节点；
4. 把一个样本涉及的节点 union；
5. 找出所有连通分量；
6. 以连通分量为最小单位打乱并切分。

传递关系示例：

```text
A 共享 JD-1 与 B
B 共享 Resume-2 与 C

A ─ JD-1 ─ B ─ Resume-2 ─ C
```

即使 A 与 C 没有直接共同实体，并查集仍会让三者处于同一分量，从而不会跨集合。

## 8. 并查集复杂度

带路径压缩的 `find` 和 union 操作摊还接近常数，严格说是反 Ackermann 复杂度：

```text
O((V + E) α(V))
```

之后按分量展开样本是线性。因此对当前万级数据足够，无需图数据库。

## 9. 切分比例为何可能不是精确 80/10/10

算法按“连通分量个数”算 train/valid/test 数，再把分量内所有样本整体展开。不同分量大小不一致，所以最终样本条数比例只能近似目标比例。

这是正确性与比例精确度之间的取舍：宁愿验证集多一点或少一点，也不能拆开同一实体。

当分量少于 3 时，代码把全部样本放入 train，并用首条同时作为 valid/test。这只是让极小 smoke 数据不崩溃，不能作为正式独立评测。

## 10. 内容去重和实体去重的区别

简历 SFT 还对 `user_text + assistant_text` 做 SHA-1 内容去重：

```text
内容去重：完全相同训练对只保留一次
实体分组：不同变体仍被绑定到同一 split
```

两者缺一不可。内容去重控制重复梯度；实体分组控制评测泄漏。

## 11. 15,470 条数据该如何准确表达

错误说法：

> 我有一万五千份简历训练数据。

准确说法：

> 简历 SFT 有 15,470 条格式变体样本，对应 2,557 个 source group，平均约 6.05 个样本/实体；其中 2,525 个组来自 bootstrap，所以主要价值是格式鲁棒性与流程验证，不代表拥有一万五千名真实候选人的独立分布。

进一步的问题是 bootstrap group rate 约 98.75%，高于 readiness 目标。即使没有跨 split 泄漏，源多样性仍然不足。

## 12. 为什么“无泄漏”和“数据够好”是两回事

一个数据集可以同时满足：

- train/valid/test 没有 source group 重叠；
- 没有规范化输入 hash 重叠；
- 没有 linked entity 重叠；

但仍然主要由模板合成、单一来源和相似标签构成。因此防泄漏审计回答“评测有没有明显作弊”，不回答“训练分布是否真实丰富”。

## 13. 当前真实审计门槛

Readiness 会检查：

- exact duplicate；
- cross-split normalized input hash；
- cross-split linked source group；
- cross-split source group；
- 每任务 source group ratio；
- 任务数据量和标签质量；
- 管线 freshness。

当前 SFT 管线 fresh，但 resume、match、multitask 仍 not ready。最关键原因不是脚本不能跑，而是真实独立实体和真实 pair 证据不足。

## 14. Preference 数据的一个额外风险

`build_preference_dataset.py` 对从 prediction mismatch 得到的 preference rows 使用普通随机行切分，而不是 `split_linked_samples`。如果多条 preference 来自同一实体或同一原始输入，可能跨 train/valid。

bootstrap preference 则分别从已经切好的 SFT train 和 valid 构造，继承上游集合边界，相对安全。

因此后续若真的启用 prediction-derived DPO 数据，应先补 `source_group`/linked entity 并改为实体级切分。这是明确、有限、值得做的优化，不需要重建整套数据平台。

## 15. 面试追问：为什么 SHA-1，不用更安全的 SHA-256

这里的 hash 用于重复内容标识，不用于密码、签名或对抗碰撞。SHA-1 速度和长度足够；理论碰撞风险对当前数据规模可忽略。若用于审计产物完整性，项目的 freshness manifest 使用 SHA-256，语义不同。

## 16. 面试口述模板

> 我把样本数和独立实体数分开统计。一份简历会生成六种格式变体，所以 15,470 条简历样本只对应 2,557 个 source group。切分不能按行随机，我用 source group、规范化输入 hash 和匹配对两侧的 linked entity 建图，再用并查集按连通分量切分，保证同一简历、同一 JD 以及传递相连的 pair 不跨集合。这个机制解决评测泄漏，但不解决真实来源不足，所以 readiness 仍然是 false。
