# 在线核心流程函数级实现详解

## 一、请求入口和数据模型

在线服务入口是 `src/jobmatch_tune/api/server.py`。FastAPI 层首先通过 Pydantic 限制请求，而不是把任意大文本直接交给模型。

### 文本接口模型

- `ParseRequest`：任务只能是 `jd_parse` 或 `resume_parse`；文本1～20,000字符；`max_new_tokens` 64～4096。
- `MatchRequest`：JD 和 Resume 都必须非空且不超过20,000字符。
- `BatchParseRequest`：最多64条文本。
- `BatchMatchRequest`：最多32组 JD/Resume。

这些限制的作用是尽早拒绝无效请求，并给推理成本设置可解释上界。它不是完整的配额系统，因为没有用户身份和全局限流。

### 路由

| 路径 | 核心调用 | 作用 |
|---|---|---|
| `GET /health` | `health()` | 后端、模型、adapter、CUDA、并发模式 |
| `POST /api/warmup` | `ModelService.load()` | 显式加载模型 |
| `POST /api/parse` | `ModelService.parse()` | 单条 JD/Resume 解析 |
| `POST /api/match` | `ModelService.match()` | 完整匹配 |
| `POST /api/batch_parse` | `batch_parse()` | 最多64条解析 |
| `POST /api/batch_match` | `batch_match()` | 最多32组匹配 |
| `POST /api/resume_file_parse` | 文件校验与解析 | 简历文件 |
| `POST /api/jd_file_parse` | 文件校验与解析 | JD 文件 |
| `POST /api/match_files` | 文本/文件组合 | 两侧混合输入 |

路由函数本身主要做 HTTP 异常映射，核心编排集中在 `ModelService` 和文件 helper。

## 二、模型生命周期

`ModelService.__init__` 从环境变量读取：

- `JOBMATCH_INFERENCE_BACKEND`：默认 `transformers`。
- `JOBMATCH_MODEL_PATH`：默认 `models/Qwen3-14B`。
- `JOBMATCH_ADAPTER_PATH`：默认历史 DFT adapter。
- `JOBMATCH_LOAD_4BIT`：默认启用。
- `JOBMATCH_VLLM_BASE_URL`、`JOBMATCH_VLLM_MODEL`。
- `JOBMATCH_VLLM_MAX_CONCURRENCY`：默认4。
- `JOBMATCH_PARALLEL_MATCH_PARSE`：默认允许，但只有 vLLM 满足并发条件时真正并行。

`load()` 使用同一把 Lock 保护初始化，避免并发 warmup 重复加载两份14B模型。`loaded` 对 Transformers 检查 tokenizer/model，对 vLLM 检查 client。

### Transformers 加载

`src/jobmatch_tune/inference/predict.py::load_model` 的步骤：

1. `AutoTokenizer.from_pretrained(..., trust_remote_code=True)`。
2. 若4-bit，构造 `BitsAndBytesConfig`：NF4、BF16 compute、double quant。
3. `AutoModelForCausalLM.from_pretrained` 使用 `device_map="auto"`。
4. GPU 上 dtype 为 BF16，CPU 为 FP32。
5. 若存在 adapter，`PeftModel.from_pretrained` 注入 LoRA。

这是单机低资源路径，不等于最优服务部署方案。

### vLLM 加载

`_load_vllm` 创建 OpenAI client，并通过 `models.list()` 检查服务连通。真正的 vLLM server 由 `scripts/serve/start_vllm_server.sh` 管理，API 不在同一进程加载 vLLM engine。

## 三、Prompt 构造

`src/jobmatch_tune/inference/predict.py::build_prompt` 是统一入口：

- `jd_parse` 调 `jd_parse_prompt`。
- `resume_parse` 调 `resume_parse_prompt`。
- `match` 要求同时提供 Resume 和序列化后的 Rule Result。

系统 Prompt 只有一个核心约束：“严格基于输入内容输出 JSON，不要编造”。任务 Prompt 再限定字段。

为什么 Prompt 看起来不复杂？因为系统没有把所有业务边界都寄托在 Prompt 上。字段合法性、技能证据和匹配结论还会经过确定性处理。更长 Prompt 不自动等于更可靠，反而可能增加训练/推理漂移。

## 四、JD 与 Resume 解析

### Transformers 路径

`_parse_with_transformers`：

1. 构造 messages。
2. `_complete_with_transformers` 应用 Qwen chat template，关闭 thinking。
3. tokenize 后移到模型设备。
4. 在 `self._lock` 和 `torch.no_grad()` 下调用 `generate`。
5. 只截取输入 token 之后的新 token。
6. decode 后交给 `parse_json_output(raw, context_text=原文)`。

生成配置是 deterministic：`do_sample=False`，temperature/top_p 为 None。这样方便回归，但不能消除模型输出结构错误。

### vLLM 路径

`_complete_with_vllm` 在 `BoundedSemaphore` 内提交 chat completion：temperature=0、max_tokens 受请求控制，并传入任务 JSON Schema response format。即使服务端支持 structured output，返回内容仍会进入同一 `parse_json_output`，避免后端间产品行为分叉。

## 五、为什么 JD/Resume 有时并行、有时不并行

两侧解析在业务上互不依赖，因此 `_parse_match_inputs` 可以创建两个 future。但 Transformers 后端最终都会进入同一个模型 Lock；线程并行只会排队，还增加上下文和显存风险，所以 `match_parse_mode` 返回 sequential。

vLLM 自身有连续批处理与调度，且 API 通过并发槽限制请求数。当 backend=vLLM、parallel=true、max concurrency≥2 时，两侧才真正并行。

面试中的准确回答是：

> 任务 DAG 允许并行，但执行后端决定是否并行。默认 Transformers 为共享模型串行安全，vLLM 才受控并发。

## 六、JSON 后处理

入口为 `src/jobmatch_tune/inference/postprocess_json.py::parse_json_output`。主要阶段：

1. `remove_thinking`：去除思维或特殊标记。
2. `extract_json_text`：从围栏或前后说明中定位 JSON 对象。
3. `repair_json_text`：处理有限的常见格式损坏。
4. JSON decode。
5. 保存 `raw_data` 与 `raw_json_ok`，供三层评测使用。
6. `normalize_parsed_data` 做字段级规范。
7. 返回 `{ok, data, error, raw_*}`。

后处理只修格式和可从原文证明的字段，不应该补出输入中没有的经历。

### JD 字段规范

`_split_misplaced_fields` 处理职责、要求、加分项串位；`_merge_missing_responsibilities` 可补回原文中确定存在但模型漏入的职责行。方向通过 `canonicalize_job_direction` 收敛。

最关键的是 `src/jobmatch_tune/preprocess/jd_skill_evidence.py::collect_jd_skill_evidence`。它按 section 查找技能，并为每个 canonical skill 保存：

- requirement evidence；
- responsibility evidence；
- bonus evidence；
- other/context evidence；
- model candidate 状态。

`required_skills_from_evidence` 只选择 requirement evidence 非空的技能。模型说“必备”只是候选，原文要求段才是证据。

### Resume 字段规范

`_normalize_resume_fields` 统一目标岗位、教育列表、核心技能、实习、项目和优势标签；方向通过 Resume context canonicalize，优势标签再用 `configs/resume_strength_alias.yaml` 收敛。

Resume 技能可以从核心技能、项目、实习和原文中提取，因为这些位置都能证明候选人至少陈述过该技能；这与 JD “出现不等于要求”的边界不同。

## 七、技能 Canonicalization

入口在 `preprocess/skill_canonicalization.py`。

### 词表构造

`_vocabulary` 把 canonical 与 aliases 合并；`_lookup_maps` 同时建立精确 key 和去 OCR 分隔符的 compact key。compact key 只有唯一 canonical 时才能启用，避免两个技能压缩后冲突。

### 匹配策略

1. 先 NFKC 和空白规范化。
2. 优先 exact casefold lookup。
3. 再尝试唯一 OCR compact lookup。
4. 在原文查找时使用带 ASCII 边界的正则。
5. 只有足够长或含 `+/#/.` 的技能允许字符间 OCR separator。

因此 `Py test`、`C + +` 能恢复，但短技能 `Go` 不允许匹配 `g o`；`C` 也不会从 `C++`、`C#` 或 `C 语言` 中重复抽取。

这个实现不是传统编辑距离 fuzzy match。它牺牲任意错拼召回，换取业务硬条件所需的精度和可解释性。

## 八、确定性匹配规则

核心函数是 `src/jobmatch_tune/match/rule_engine.py::compute_match_rule_result`。

### 技能

`_skill_lists` 对 JD 重新收集 requirement evidence；Resume 则合并核心技能、项目、实习和原文中的已知技能。两边转换为 normalized key 求交集和差集。

### 方向

`evaluate_direction_compatibility` 先把方向映射到最小 leaf，再返回：

- `exact`：同一 leaf；
- `compatible`：有限跨方向组合且职责、上下文、共享技能都满足；
- `mismatch`：缺方向或证据不足。

AI 平台兼容要求至少两个共享技能，同时共享技能集合中既有 AI 技能又有工程技能，并且两侧都有模型服务/平台信号。算法和普通后端不会默认兼容。

### 学历

学历映射为等级：中专、大专、本科、硕士、博士。JD 中“优先”不视为硬门槛；无明确要求也视为不阻塞。

### 经验

`_extract_required_years` 支持数字、中文数字和范围，并过滤毕业年份、入学年份和“25年校招”等日期语义。Resume 没有明确年限时，即使项目很多，也不会凭空判定满足三年经验。

### 项目

`_match_projects` 检查项目/实习行是否出现 JD required skill。每条命中项目贡献5分，最多10分。它是简单、可解释的证据，不是项目质量模型。

### 分数

`MatchScoringPolicy` 冻结权重：方向20、技能45、学历10、经验15、项目10；等级阈值85/65/45。策略初始化校验权重总和、阈值顺序和无技能默认分。

结果显式包含：分数、等级、方向关系/证据、学历/经验、命中/缺失技能、命中项目、技能 evidence、分项和策略。分数标记为 `heuristic_compatibility_score`，不是概率。

## 九、解释生成

规则完成后，`match_prompt` 同时传入 JD、Resume 和序列化规则 JSON。解释模型输出五个字段：结论、优势、短板、建议、推荐方向。

这个设计有两个重要效果：

1. LLM 不再决定硬条件，只把已确定事实转换为用户语言。
2. 解释仍可能错误，因此必须做 structural contradiction 和 evidence grounding 检查。

如果模型把缺失 Kafka 写成优势，结构一致检查会发现；如果提到规则和解析都没有的 Agent，grounding 会发现。但“建议学习 Kafka 是否真的增加录用机会”当前无法验证。

## 十、文件上传链路

`src/jobmatch_tune/api/upload_validation.py::validate_upload_content` 在高成本提取前执行。

- PDF：扩展名、`%PDF` signature、pypdf 可解析性。
- DOCX：ZIP signature、`[Content_Types].xml` 和 `word/document.xml`。
- 图片：Pillow verify/load，检测实际格式并与扩展名匹配。
- TXT：严格 UTF-8、拒绝 NUL 和过量控制字符。

错误区分 `too_large`、`unsupported_type`、`extension_content_mismatch` 和 `corrupt_file`。校验通过后才进入 `resume/ingest.py`；扫描 PDF 或图片再由 RapidOCR 路径处理。

这能阻止常见坏输入，但不是恶意文档沙箱，没有杀毒、PDF 脚本隔离或租户级文件存储。

## 十一、响应与前端

匹配响应包含：

- `jd_parse`、`resume_parse`；
- `rule_result`；
- `analysis` 与 raw output；
- `execution.backend/parse_mode`；
- JD、Resume、parse wall、rule、analysis、total timings。

Vue 前端只渲染这些事实，并通过 `utils/text.js` 生成 Markdown。界面使用“启发式匹配分数”，不在浏览器重算等级。依赖由 package-lock 锁定，Vite 本地构建，不依赖 CDN。

## 十二、实现局限

- `server.py` 职责较集中，但当前规模仍可维护。
- Transformers 推理锁限制吞吐。
- vLLM 路径尚无当前硬件真实基准。
- API 没有统一 response Pydantic model。
- OCR 与文件处理没有任务队列，超大批量不适合同步接口。
- 规则 taxonomy 有限，项目命中较粗糙。
- 前端没有真实浏览器 E2E。

这些局限应在面试中主动说明，同时解释为什么当前没有继续平台化。
