# JSON 修复、字段归一化与技能证据逐层精读

模型输出“能被 `json.loads` 读取”并不等于“能被产品正确使用”。这一章拆解 `parse_json_output` 的每一层语义，并解释为什么它是项目里最容易被低估、也最值得面试深讲的部分。

## 1. 四层输出语义

当前解析器同时保留四个概念：

```text
raw_output       模型原始文本
raw_json_ok      原始文本是否就是严格 JSON
raw_data         严格 JSON 成功时的原始对象
data             修复并业务归一化后的产品对象
```

例如模型输出：

````text
<think>先分析字段</think>
```json
{“岗位方向”: “AI开发”, “必备技能”: [“Py thon”, “RAG”,],}
```
````

严格层应判失败，因为有 thinking、代码围栏、中文引号和尾逗号。产品层可能通过修复得到可用结构。把两个结果分开，才能分别回答：模型原生格式遵循率是多少，以及产品最终可用率是多少。

如果只统计修复后的 `ok`，会把后处理功劳算到模型上；如果只统计 strict，又会低估线上系统的实际可用性。

## 2. `remove_thinking` 的边界

实现用跨行正则删除 `<think>...</think>`。这对 Qwen thinking 输出有效，但有三个边界：

- 只处理成对标签；未闭合的 `<think>` 不会被完整删除；
- 若业务正文真的包含该标签，会被一并删除；
- 它不负责去 Markdown 围栏，围栏依赖下一步截取首尾花括号规避。

生产系统更稳妥的办法是依赖受约束输出或解析器状态机；当前做法是对已观察错误的最小修复，不应宣称为通用 JSON repair。

## 3. `extract_json_text` 为什么取第一个 `{` 到最后一个 `}`

这一策略可以处理：

```text
下面是结果：
{"岗位方向": "后端开发"}
希望有帮助。
```

但如果输出含两个 JSON 对象：

```text
示例 {"a": 1}
结果 {"b": 2}
```

首 `{` 到末 `}` 会拼成非法 JSON。这是有意的保守行为：项目期望一个顶层对象，不尝试猜测多个对象里哪一个才是真结果。

## 4. `repair_json_text` 实际修了什么

当前只有四类有界修复：

1. 中文双引号替换为 ASCII 双引号；
2. 中文单引号替换为 ASCII 单引号；
3. 删除对象或数组结束前的尾逗号；
4. 对一个历史观察到的 match 尾部错位模式补上“匹配结论”键。

注意：把中文单引号变成 `'` 并不会让 Python 风格单引号 JSON 自动合法，因为 JSON 字符串仍要求双引号。这说明函数不是“万能修复器”，只处理数据中真实出现过的错误。

不应加入激进修复，例如自动补任意缺失括号、用 `eval` 读取 Python 字面量或猜字段。这些做法可能把错误内容静默改成貌似正确的业务结果。

## 5. `normalize_parsed_data` 如何判断任务类型

它不是靠额外的 task 参数，而是看顶层字段：

```text
有“目标岗位”或“教育背景” → resume
有“匹配结论/匹配优势/主要短板” → match explanation
其他 dict                   → JD
```

优势是调用简单；风险是字段缺失或跨任务字段污染时可能误分类。例如一个损坏的简历输出只含 `核心技能`，会落入 JD 分支。当前依赖结构化输出 schema 和训练格式降低这一概率。

若未来任务增多，应把 task 显式传入归一化器，避免启发式路由继续扩大。但当前三任务规模下，没有必要引入复杂的 parser registry。

## 6. 简历归一化的真实动作

### 6.1 目标岗位

先去空白并与 schema 的标准方向比较；`后端开发工程师` 可映射到 `后端开发`。否则再结合完整简历上下文调用方向规则。

### 6.2 教育、实习和项目

输入可能是字符串、列表或字典：

- 字典值被拼成一条描述；
- 嵌套列表递归展开；
- 普通字符串按换行切分；
- 项目还按中英文分号切分；
- 项目句末没有标点时补 `。`。

这解决模型有时把一段经历输出为字符串、有时输出为列表的问题。

### 6.3 核心技能

技能经过 schema alias canonicalization，同时 `keep_unknown=True`。保留未知技能很重要：简历技能是候选人的开放集合，若只保留白名单，新的框架或业务工具会被误删。

### 6.4 优势标签

处理过程是：

```text
“熟悉工程实践能力强、具备快速学习能力”
  → 按顿号/逗号/和/与切分
  → 去“熟悉/具备/擅长”等前缀
  → 去“能力强/能力/覆盖全面”等后缀
  → alias 映射
  → 去重
```

这是为了让生成风格不同但语义相同的标签落到稳定集合。

## 7. JD 字段错位修复

模型常见错误不是 JSON 语法错误，而是把内容放错字段。`_split_misplaced_fields` 处理以下情况：

- `核心职责` 中以“任职要求”开头的行移到要求；
- 以“加分项/优先”开头的行移到加分项；
- 以“经验要求”开头的行提取到经验字段；
- 以“学历要求”开头的行提取到学历字段；
- 从所有要求行补抽取学历和经验；
- 从原文补回模型截断但有可信前缀的职责行。

最后，系统不会直接使用模型给出的 `必备技能`，而是调用 `collect_jd_skill_evidence` 重建证据。

## 8. 为什么补职责时需要“前缀可信”条件

`_merge_missing_responsibilities` 不是发现原文更多行就全部补回。它要求模型输出与原文章节开头至少匹配一定前缀，然后才把后续缺失行合并。

原因：章节识别可能切错。如果完全不验证就把原文中所有编号行加入职责，会把要求、福利或公司介绍污染进来。前缀匹配是一个低成本置信条件。

## 9. 技能规范化如何避免子串误报

技能识别不是简单的 `if skill.lower() in text.lower()`。典型问题：

- `C` 会命中 `CUDA`、`React` 或普通英文字符；
- `R` 会命中大量单词；
- `Go` 可能命中英文单词的一部分；
- OCR 会把 `Python` 变成 `Py thon`，把 `C++` 变成 `C + +`。

项目的规范化大致分为：

1. Unicode NFKC，统一全角半角；
2. 小写和空白压缩；
3. 建立标准名与 alias 映射；
4. 对足够长或含特殊符号的技能允许 OCR 紧凑匹配；
5. 对单字母/短英文技能使用独立边界，避免嵌在更长 token 中；
6. 输出标准 canonical name。

为什么不是所有词都删除空白后匹配：短词做紧凑匹配会显著增加假阳性。OCR 容错必须根据技能长度和形态设门槛。

## 10. `SkillEvidence` 的数据模型

每项技能保存四类片段：

```text
requirement_evidence       任职要求证据
responsibility_evidence    岗位职责证据
bonus_evidence             加分项证据
other_context_evidence     其他上下文证据
```

`required` 的定义非常严格：只有存在 `requirement_evidence` 才为真。职责中出现某技术不自动等于候选人必须掌握；加分项更不能转成硬门槛。

例如：

```text
岗位职责：使用 Kubernetes 维护平台。
任职要求：熟悉 Python、Docker。
加分项：了解 PyTorch。
```

证据应是：

```json
[
  {"技能": "Kubernetes", "是否必备": false, "证据来源": ["responsibility_evidence"]},
  {"技能": "Python", "是否必备": true, "证据来源": ["requirement_evidence"]},
  {"技能": "Docker", "是否必备": true, "证据来源": ["requirement_evidence"]},
  {"技能": "PyTorch", "是否必备": false, "证据来源": ["bonus_evidence"]}
]
```

最终 `required_skills_from_evidence` 只取 Python 和 Docker。

## 11. 章节标题和句内 cue 的优先级

证据分类先看当前章节；没有明确章节时才看句内 cue：

- 含“优先/加分” → bonus；
- 含“熟悉/掌握/具备/要求/经验/能力”等 → requirement；
- 含“负责/参与/建设/开发/维护”等 → responsibility；
- 都没有 → other。

章节优先是必要的。例如“加分项：具备 Kubernetes 经验”虽然有“具备/经验”要求 cue，但章节明确是加分项，不能被升级为硬要求。

## 12. 一个完整纠错例子

原文：

```text
岗位职责
1. 负责 RAG 服务开发
2. 使用 FastAPI 建设接口
任职要求
1. 熟悉 Python
2. 具备 Docker 使用经验
加分项
1. 熟悉 Kubernetes
```

模型输出：

```json
{
  "核心职责": [
    "1. 负责 RAG 服务开发",
    "任职要求：熟悉 Python",
    "加分项：熟悉 Kubernetes"
  ],
  "必备技能": ["RAG", "FastAPI", "Python", "Docker", "Kubernetes"]
}
```

归一化过程：

1. 把 Python 行从职责移到要求；
2. 把 Kubernetes 行从职责移到加分项；
3. 原文章节识别补回遗漏的 FastAPI 职责和 Docker 要求；
4. 收集五项技能的原文证据；
5. 只有 Python、Docker 有 requirement evidence；
6. 最终必备技能变成 `[Python, Docker]`；
7. RAG/FastAPI 仍保留在技能证据里，但不计硬缺失；
8. Kubernetes 标记 bonus，不计硬缺失。

这类纠错直接影响用户感知：否则候选人会被错误告知缺少三个“必备”技能。

## 13. 为什么规则不能全塞进 prompt

Prompt 可以要求模型区分“职责、要求、加分项”，但不能保证每次严格遵守。代码规则的优势是：

- 同一输入可复现；
- 错误可以写单元测试；
- 证据可以回显；
- 修改不需要重新训练；
- 评测可区分原始模型与产品最终结果。

但规则也不是越多越好。只应固化业务语义清晰、错误代价高、可从原文验证的内容。对开放式优势总结和建议，不适合继续堆正则。

## 14. 当前实现的局限

### 章节识别依赖标题

完全没有换行、标题或标点的超长 JD，证据分段会变弱。可以用版面/OCR 结构或小型分类器增强，但当前数据规模下先收集失败样本更合理。

### required 是二元值

现实中有“至少会一种”“熟悉 A 或 B”“优先但非必需”等逻辑。当前系统没有表达 AND/OR/optional constraint graph，只区分 required 与非 required。

### 未知 JD 技能可能被丢弃

JD 技能规范化更保守，防止把普通职责短语当技能；代价是 schema 外新技术召回不足。长期应维护可审计词表更新，而不是默认保留所有模型字符串。

### 修复成功不代表语义正确

JSON 修复只保证可解析，字段归一化只处理已编码规则。最终仍需 Gold 和人工边界集验证。

## 15. 调试顺序

发现“技能识别错了”时按以下顺序检查：

1. `raw_output` 中模型是否输出该技能；
2. `raw_json_ok` 是否为真；
3. `raw_data` 的技能在哪个字段；
4. `data.技能证据` 把它归到哪个 evidence kind；
5. 原文对应行被识别到哪个章节；
6. canonicalization 是否把 alias 映射正确；
7. `rule_result.命中技能/缺失技能` 是否只使用 required skills；
8. 前端展示的是 parse 技能还是 rule 技能。

不要一看到结果错就先调训练。很多错误属于字段修复、schema 或证据规则。

## 16. 面试口述模板

> 我把模型结构输出分为严格原始层和产品归一化层。严格层只做 `json.loads`，用于衡量模型自身格式遵循；产品层处理 thinking、中文引号和尾逗号，再做字段归一化。JD 的必备技能不会直接相信模型列表，而是回到原文，根据任职要求、职责、加分项四类证据重新判定，只有 requirement evidence 才进入硬匹配。这样既保留生成模型处理非结构文本的能力，又把高风险业务语义固定成可测试规则。
