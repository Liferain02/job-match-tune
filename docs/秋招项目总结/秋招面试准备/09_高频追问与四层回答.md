# 高频追问与四层回答

使用方法：先只读每组 Q1 并口述；面试官继续深挖时再展开 Q2～Q4。答案不需要逐字背，但事实和边界不能改变。

## 主题一：项目到底是什么

**Q1：一句话介绍项目。**  
A：这是一个中文招聘场景的 LLM 后训练与可解释匹配工作台：模型负责 JD/简历结构化抽取和解释，确定性层负责证据约束、硬条件和启发式评分，Gold 与 Readiness 决定模型能否晋级。

**Q2：它和普通简历匹配 Demo 的区别？**  
A：普通 Demo 常让 LLM 直接给一个分数；本项目保留 Raw、Normalized、Product Final 三层结果，能区分模型错误、后处理收益和规则错误，还审计来源、实体泄漏和训练准入。

**Q3：最终用户是谁？**  
A：当前面向个人求职者和研发验证，帮助理解岗位要求与简历差距；不是企业 ATS，也不替代招聘决定。

**Q4：项目最有价值的产出是什么？**  
A：不是某个 adapter，而是一条可审计闭环，以及在真实数据证据不足时主动阻止继续训练的工程判断。

## 主题二：为什么不是一步 LLM Match

**Q1：为什么不让 LLM 直接输出分数和理由？**  
A：方向、学历、年限和技能是需要复查的硬条件；生成式结论可能漂移，也难判断错在抽取还是推理。

**Q2：拆开后具体几步？**  
A：JD Parse、Resume Parse、Normalization、Rule Match、Explanation。一次完整匹配有三次模型生成，两次解析加一次解释。

**Q3：这样不是更慢吗？**  
A：是，当前用延迟换可审计性。未来可以缓存重复 JD/Resume parse；不优先通过合并 Prompt 牺牲中间事实。

**Q4：规则是不是限制了 LLM 能力？**  
A：它限制的是硬条件漂移。LLM 仍负责复杂文本理解和自然语言解释，两者各做擅长的部分。

## 主题三：Normalization 是否作弊

**Q1：Raw 只有0.56，Normalized 到0.96，算不算后处理作弊？**  
A：不算，只要产品定义本来就是完整流水线、规则不读取 Gold 标签、后处理通用冻结，并同时报告 Raw 和 Final。

**Q2：什么情况下算作弊？**  
A：根据测试样本 ID 写特判、看完 Gold 后仍报 blind、不断调规则只报最终分，或隐藏 Raw 退化。

**Q3：为什么一定要报三层？**  
A：否则无法归因。Raw→Normalized 是工程约束收益，Normalized→Final 主要增加解释，模型训练收益不能从 Final 差值直接推断。

**Q4：当前回归为什么写 after inspection？**  
A：规则修复参考过 Gold 错误，所以只能证明已知问题不再复现，不能证明未见样本泛化。

## 主题四：JD requirement evidence

**Q1：JD 提到一个技能为什么不能直接算必备？**  
A：职责、加分项和任职要求语义不同。职责里“负责 Kafka 平台”不一定要求候选人已有 Kafka。

**Q2：代码如何区分？**  
A：`collect_jd_skill_evidence` 为技能保存 requirement、responsibility、bonus、other/context evidence，最终 required 只取 requirement 非空的技能。

**Q3：模型字段还有什么作用？**  
A：它是 candidate，帮助收集可能技能；但不能代替原文 provenance。

**Q4：非标准 JD 没有“任职要求”标题怎么办？**  
A：保守归入 other，可能少召回。硬门槛错误扣分风险更高，因此不无依据升级为 required。

## 主题五：Skill/OCR canonicalization

**Q1：`Py test` 怎么恢复成 `Pytest`？**  
A：在已知技能词表内生成唯一 compact key，并在原文使用有边界 OCR separator pattern，不是全局删除空格。

**Q2：为什么不用 Levenshtein/fuzzy match？**  
A：硬技能短词和符号多，fuzzy 容易误认普通词、C/C++、Java/JavaScript，且难解释。

**Q3：为什么不是加一条 `Py test` alias？**  
A：单条 alias 只修一个样本。通用逻辑同时覆盖 Python、Kubernetes、C++、Node.js 等，并有反例测试。

**Q4：仍处理不了什么？**  
A：未知技能和任意拼写错误不会猜。只有独立新样本反复证明后才扩词表或候选召回。

## 主题六：短技能 C 的 Bug

**Q1：全量测试发现了什么新 Bug？**  
A：canonicalization 会把 `C++/C语言/C#` 里的 C 再抽成独立技能 C。

**Q2：为什么专项测试没提前发现？**  
A：新模块覆盖了 OCR 和常见假阳性，但旧 `jd_field_rules` 已有的 ASCII boundary contract 在迁移时没有完全继承。

**Q3：怎么修？**  
A：给 standalone C 的右边界增加通用负向条件，拒绝紧邻 `+/#/语言`，并补正反例。

**Q4：这个故事说明什么？**  
A：模块重构不能只验证新需求，还要跑全量契约；边界规则尤其容易在迁移中丢失。

## 主题七：Direction Compatibility

**Q1：为什么不直接比较岗位名称？**  
A：AI 后端、模型服务、算法平台等名称不同但职责可能高度交叉；单纯 exact 召回不足。

**Q2：为什么不用 alias 全映射？**  
A：算法和普通后端在很多岗位并不兼容，宽泛 alias 会牺牲精度。

**Q3：compatible 的证据？**  
A：允许的最小 leaf pair、两侧职责/项目 signal、至少两个共享技能；AI 平台还需 AI 和工程技能共同出现。

**Q4：compatible 为什么和 exact 都给方向20分？**  
A：现有 contract 是方向满足布尔值，没有真实 Pair 支撑任意折扣；relation/evidence 已返回，未来有数据再校准。

## 主题八：启发式评分

**Q1：评分如何计算？**  
A：方向20、技能45、学历10、经验15、项目10；85/65/45分成高、较、基本、低匹配。

**Q2：技能分怎么计算？**  
A：按 required skill 中命中比例乘45；JD 无 required skill 时给20而不是满45，避免无要求岗位自动高分。

**Q3：85分是85%录用概率吗？**  
A：不是。策略明确标记 heuristic，没有真实 outcome 校准。

**Q4：为什么不在25条 Gold 上拟合权重？**  
A：样本太小且已参与规则分析；合成 Pair 又由同一规则生成，拟合会形成循环自证。

## 主题九：学历与年限

**Q1：学历如何判断？**  
A：把中专/大专/本科/硕士/博士映射为有序 rank；JD 无要求或只是“优先”不阻塞。

**Q2：年限如何抽取？**  
A：支持阿拉伯/中文数字和范围，过滤毕业、入学、届别、校招年份等日期语义。

**Q3：简历项目多能否推断三年经验？**  
A：不能。没有明确年限证据时判不满足，避免编造。

**Q4：会不会过于保守？**  
A：会，所以产品应表达“未找到满足证据”，而非断言人没有能力；真实标签到来后才能优化。

## 主题十：SourceGroup

**Q1：15,470条 Resume 为什么不够？**  
A：只有2,557个 source group，同一 source 有多个模板；98.75%的 group 来自 bootstrap。

**Q2：SourceGroup 与去重有什么区别？**  
A：内容去重找相同文本；source group 表示即使文本形式不同也来自同一语义实体。

**Q3：采样时怎么用？**  
A：按 group round-robin，先从每个 group 取一个，再取第二个变体，避免模板多的 source 垄断配额。

**Q4：为什么它影响泛化？**  
A：跨 split 的同源变体会让模型记住内容或标签模板，验证结果偏乐观。

## 主题十一：Entity Split

**Q1：Pair random split 为什么泄漏？**  
A：不同 Pair 仍可能共享 JD 或 Resume 节点；模型在 train 已见过测试侧实体。

**Q2：怎么修？**  
A：先按 JD/Resume entity hash 分别切 train/valid/test，再只在 split 内配对。

**Q3：为什么还要按方向/来源家族分层？**  
A：避免小类别或教育来源集中到单一 split，提高基本分布稳定性。

**Q4：hash split 能证明语义完全独立吗？**  
A：不能，改写近重复可能绕过 exact hash；还要近重复审计和人工抽查。

## 主题十二：Synthetic Match Pair

**Q1：4,798 Pair 怎么来的？**  
A：在 split 内选择同方向/不同方向 Resume 配 JD，再用当前规则生成结构标签。

**Q2：它们有什么价值？**  
A：训练格式、覆盖字段和验证端到端管线。

**Q3：为什么不能证明业务效果？**  
A：Pair 不是用户投递或招聘者选择，标签又来自被训练系统使用的规则，缺少外部观测。

**Q4：继续扩大到十万 Pair 呢？**  
A：只会更强地拟合同一规则偏差，不能解除 readiness。

## 主题十三：QLoRA

**Q1：为什么用 QLoRA？**  
A：14B 全参训练成本高，任务主要是格式和领域适配；4-bit基座+LoRA能降低显存并保留足够适配能力。

**Q2：具体参数？**  
A：NF4、BF16 compute、double quant，LoRA r=8、alpha=16、dropout=0.05，覆盖 attention 和 MLP projection。

**Q3：为什么不是更大 rank？**  
A：没有证据表明当前瓶颈是 adapter 容量，真实数据不足时调 rank 边际价值低。

**Q4：QLoRA 的输出是什么？**  
A：adapter，而不是复制完整14B基座；推理时基座和 PEFT adapter 一起加载。

## 主题十四：SFT 训练设置

**Q1：为什么 assistant-only loss？**  
A：只监督结构化 assistant 响应，避免学习复述 Prompt。

**Q2：为什么 packing=false？**  
A：当前 SDPA 组合存在样本串扰警告，正确性优先；验证兼容 FlashAttention 后才能开。

**Q3：为什么只训1 epoch？**  
A：模板重复较多，更多 epoch 可能过拟合；是否增加应由独立评测决定。

**Q4：如何复现？**  
A：YAML+CLI override，run manifest 记录 Git、配置和数据 hash；GPU wheel 仍需匹配宿主机。

## 主题十五：DFT

**Q1：DFT 是你自己实现的吗？**  
A：不是。项目把 TRL `SFTConfig.loss_type="dft"` 作为 loss 对照项接入。

**Q2：怎么比较 DFT 和 NLL？**  
A：相同9,800 train、320 eval、1 epoch、613 steps；不直接比较不同定义的 loss 数值，比较结构输出和业务评测。

**Q3：结果如何？**  
A：历史耗时约8,050和8,029秒，旧 JD 结果接近，没有强证据证明 DFT 显著领先。

**Q4：为什么还保留？**  
A：它展示训练框架能做受控配置对照；但项目不以 DFT 作为主要创新点。

## 主题十六：DPO

**Q1：DPO 是 SFT 后一步吗？**  
A：通常是。SFT 先建立任务能力，DPO 再在同 Prompt 下学习 chosen 优于 rejected。

**Q2：历史 DPO 指标？**  
A：4,400 preference、275 steps，reward accuracy 0.9297、margin 3.3643，但这不是产品收益。

**Q3：为什么暂停？**  
A：偏好主要合成、pipeline stale，上游 Resume/Match readiness=false；脚本有显式 pause gate。

**Q4：如何恢复？**  
A：新增合法 human preference、独立 holdout，重建 freshness 并通过产品回归，不是设置环境变量强行绕过。

## 主题十七：人工 holdout

**Q1：人工 holdout 是什么？**  
A：训练和调参前隔离、由人复核、方案冻结后用于最终验收的一组样本。

**Q2：和 validation 的区别？**  
A：validation 可反复用于调参；holdout 不应参与模型、规则或阈值选择。

**Q3：随机留10%算吗？**  
A：不自动算。还要实体/来源隔离和人工标签。

**Q4：看过错例后怎么办？**  
A：降级为 regression set，不能再称 blind；新泛化需要新 holdout。

## 主题十八：Gold V1

**Q1：Gold 有多少？**  
A：25条项目内人工复核 Match 样本。

**Q2：独立性怎么证明？**  
A：五类 normalized exact hash 与当前训练池重叠为0，ID/group/Pair不重复。

**Q3：局限？**  
A：单人复核、小规模、精确 hash 审计，不是外部多标注者 benchmark。

**Q4：正式结果？**  
A：历史技能命中/缺失 F1 0.990649/0.986667，等级和方向 EM 0.96；不能说成裸模型准确率。

## 主题十九：三层评测

**Q1：三层分别是什么？**  
A：Raw Model Derived、Normalized、Product Final。

**Q2：Raw 为什么重要？**  
A：能看模型自身字段能力，避免 normalization 掩盖解析退化。

**Q3：Product Final 多了什么？**  
A：规则结果和 Explanation JSON；结构结果由规则决定。

**Q4：当前1.0怎么解释？**  
A：已检查 Gold 的保存预测规则回归，只证明已知错误修复，不是新 blind generalization。

## 主题二十：Explanation Evaluation

**Q1：解释一致率1.0是什么意思？**  
A：与规则结构没有检测到矛盾。

**Q2：为什么 grounding 只有0.92？**  
A：两条保存的旧解释仍包含无支持 Agent 和把 Pytest 写为缺失的陈述。

**Q3：建议有效性呢？**  
A：未评估，没有真实用户投递或招聘 outcome。

**Q4：可以用另一个 LLM judge 吗？**  
A：可作辅助语言质量评审，不能替代真实 downstream outcome。

## 主题二十一：Readiness

**Q1：Readiness=false 是失败吗？**  
A：不是，说明门禁正确揭示证据不足并阻止不可信训练。

**Q2：当前哪些 false？**  
A：Resume、Match、Multitask；总 all_ready_for_sft/training=false。

**Q3：为什么 JD 不足以让多任务通过？**  
A：多任务包含不 ready 的 Resume 和 Match，不能用一个强任务掩盖其他数据线。

**Q4：如何解除？**  
A：新增真实独立来源和标签证据、修复分布并重新审计，不是降低阈值。

## 主题二十二：Transformers 与 vLLM

**Q1：默认用哪个？**  
A：Transformers，依赖少、适合低并发调试和演示。

**Q2：vLLM 何时更好？**  
A：多请求并发和批量吞吐场景，依靠连续批处理；但要同模型、输入和硬件实测。

**Q3：为什么 Transformers 加 Lock？**  
A：共享一个模型/显存，保护初始化和 generate，避免并发风险。

**Q4：当前有 vLLM 提升数字吗？**  
A：没有，环境未安装；只完成受控并发路径和统一 benchmark harness。

## 主题二十三：上传安全

**Q1：上传只看后缀吗？**  
A：不是，检查 signature、OOXML结构、图片真实解码、文本编码和控制字符。

**Q2：为什么在 OCR 前？**  
A：尽早拒绝坏文件，避免昂贵资源消耗和解析攻击面。

**Q3：这是完整安全方案吗？**  
A：不是，没有恶意文件沙箱、杀毒、隔离存储和多租户。

**Q4：为何不继续补？**  
A：当前是本地原型，没有公网匿名上传需求；继续安全平台化属于超范围。

## 主题二十四：批量与并发

**Q1：批量上限？**  
A：parse最多64条，match最多32组。

**Q2：批量是模型 batch 吗？**  
A：当前主要是 API 层多请求编排，不应等同底层 tensor batch；vLLM 可利用服务端调度。

**Q3：部分失败怎么办？**  
A：逐项记录状态，尽量保留成功结果。

**Q4：为什么不无限并发？**  
A：显存、模型线程安全和下游容量有限，通过 backend mode 和 semaphore 限制。

## 主题二十五：前端与工程复现

**Q1：前端为什么从 CDN 改为 Vite？**  
A：锁定依赖、支持离线构建和可重复部署，避免浏览器访问 unpkg 成为运行条件。

**Q2：Python 为什么没有全量 lock？**  
A：CUDA/PyTorch/vLLM 与目标硬件强绑定，当前用分环境 constraints 和验证快照。

**Q3：如何统一启停？**  
A：`start_project.sh` 管理 vLLM/API/frontend、端口、PID和日志；`stop_project.sh` 校验进程后停止进程组。

**Q4：当前缺什么？**  
A：浏览器 E2E、CI、容器和生产 Web server，都是明确边界。

## 主题二十六：为什么不拆微服务

**Q1：server.py 很大，为什么不拆？**  
A：当前单用户原型，复杂度主要是语义和模型，不是团队/扩容边界；拆服务会增加部署和版本一致性成本。

**Q2：何时应该拆？**  
A：文件处理需独立异步、模型需独立扩缩容、多团队所有权或多模型路由时。

**Q3：如果产品化先拆什么？**  
A：先把长耗时文件/OCR任务与在线 API 解耦，再独立推理后端；规则服务不急着拆。

**Q4：为何没有 Redis/Kafka/Celery？**  
A：当前没有真实吞吐和可靠投递需求，加入只会制造简历式架构复杂度。

## 主题二十七：项目中最失败的一件事

**Q1：你最大的错误是什么？**  
A：早期把行数和格式变体当成数据规模，并接受了受训练污染的 Match 评测。

**Q2：如何发现？**  
A：审查 source identity、基础样例和训练池 overlap，而不是只看报告名称。

**Q3：如何处理？**  
A：废弃历史结论，重建 Gold 和审计，没有为了保留漂亮数字降低标准。

**Q4：学到什么？**  
A：评测独立性必须在数据模型中显式表达，不能依赖文件名和人的记忆。

## 主题二十八：如果再做一次

**Q1：最先改变什么？**  
A：先定义 entity/source/provenance 和 Gold protocol，再开始抓取与训练。

**Q2：模型会换吗？**  
A：先用更小基座和规则做可验证 baseline，只有数据/指标证明瓶颈在模型容量时才升14B。

**Q3：还会做 synthetic 吗？**  
A：会，但只用于格式和覆盖，元数据明确标注，不作为业务 evidence。

**Q4：最早设置什么 gate？**  
A：跨实体 split、Gold overlap、source diversity、PII 和真实 Pair provenance。

## 主题二十九：当前为什么停止

**Q1：项目还有技术债，为什么停止？**  
A：剩余核心债依赖新真实数据或真实需求；代码无法凭空解决。

**Q2：vLLM benchmark 还 pending 呢？**  
A：如果没有目标并发需求和环境，安装 vLLM只为填表价值低；不影响当前核心结论。

**Q3：停止是不是放弃？**  
A：不是，冻结了可复查状态和重启条件，把时间转到面试掌握或新证据获取。

**Q4：什么会让你重启？**
