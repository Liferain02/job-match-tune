# 困难挑战、错误决策与修复复盘

这篇是面试价值最高的材料。不要只说“遇到显存不足，所以用了 QLoRA”；那是常见工具选择。更有区分度的是：如何发现指标不可信、如何定位到数据图泄漏、如何拒绝为小 Gold 写特判，以及为什么最终主动停止训练。

## 挑战一：历史 Match 评测看起来很好，但其实被污染

### 现象

历史 Match 评测有64条，看上去覆盖多种格式并能形成不错指标。

### 深挖

审查 sample identity 后发现64条主要来自16个基础样例的格式变体，而且基础样例曾进入 Match 训练池。行数64并不意味着64个独立语义 Pair。

### 根因

早期按文件和行数管理数据，没有把“原始实体、格式变体、配对边”建模为不同层级；holdout 名称被误当成独立性证明。

### 修复

- 宣布旧 Match 结果失效，不重命名包装。
- 新建25条候选并逐条人工复核。
- 增加 Pair、JD、Resume、JD-task、Resume-task 五类 exact hash 重叠审计。
- 冻结 Gold、预测、报告和 isolation audit hash。

### 验证

25条均带 annotator/review time/rationale，五类训练重叠为0，difficulty tags 完整。

### 仍有边界

它仍是项目内单人复核、小规模集合，精确 hash 不能证明所有语义近重复消失。

### 面试结论

最重要的决定不是把指标调高，而是主动废弃了一组有利但不可信的历史结果。

## 挑战二：配对后随机切分造成实体级图泄漏

### 现象

Pair 表面不重复，但同一 JD 或同一 Resume 可能出现在不同 split 的其他 Pair 中。

### 为什么普通去重没用

训练 `(JD_A, Resume_X)`、测试 `(JD_A, Resume_Y)` 时，Pair hash 不同，但模型已经见过 JD_A。匹配数据是二部图，边不同不代表节点独立。

### 修复

`partition_match_entities` 先对 JD/Resume 文本各自生成 entity hash，在来源家族和方向内切分节点；之后只在同 split 的节点之间配对。

### 验证

每条 Pair 保存 `entity_split`、`jd_entity_hash`、`resume_entity_hash`；测试覆盖两侧实体不会跨 split。

### 方法论

凡是 Pair/Triplet/对比学习数据，都要按实体图或 source group 切分，不能只按样本行随机切。

## 挑战三：15,470条 Resume 被误解为15,470份简历

### 现象

Resume SFT 行数看起来充足，格式也丰富。

### 根因

同一 source 被渲染为 original、bullets、compact、OCR、mixed language 等多个变体；统计只看 rows，没有看 source group。

### 修复

新增 Resume profile，统计 unique source groups、expansion ratio、variant 分布和 bootstrap 来源比例；多任务采样改为 source group round-robin。

### 结果

15,470行对应2,557个 group，扩展比6.05；2,525个 group 来自 bootstrap，比例98.75%。Resume readiness 因此为 false。

### 面试结论

数据增强提升格式鲁棒性，但不能增加独立语义证据。样本量必须同时报告 row、group 和 provenance。

## 挑战四：职责中提到的技术被当作必备技能

### 现象

JD 写“负责 Agent 应用开发”，模型或全局技能扫描可能把 Agent 放进必备技能，进而对候选人错误扣分。

### 根因

旧实现把“文本中出现技能”与“任职要求证据”混成一个布尔命中；模型输出字段又被直接当事实。

### 修复

实现 `SkillEvidence`，分 requirement、responsibility、bonus、other/context。模型输出只是 candidate，只有 requirement evidence 能进入 required skill。

### 验证

测试覆盖职责出现、要求出现、职责要求重复、加分项和无 section 场景；规则引擎不再从整段 JD 绕过 evidence。

### 取舍

保守策略可能在非标准 JD 上少召回，但错误硬门槛比少显示一个技能风险更高。

## 挑战五：OCR 断词既要召回，又不能无界模糊匹配

### 现象

`Py test`、`Py thon`、`C + +`、`Node . js` 会漏召回。

### 直觉方案为什么危险

删除全文空格或用编辑距离搜索，会把普通短语和技能子串误识别；短技能 Go/C/R 等尤其危险。

### 修复

只在 known vocabulary 内建立 exact/compact map，compact key 必须唯一；原文匹配使用边界正则，短技能不允许字符间隔 fuzzy。

### 二次发现

全量测试发现短技能 `C` 会从 `C++/C语言/C#` 中重复抽取。修复放在通用 standalone C token 边界，而不是针对 Gold ID。

### 验证

正例覆盖 Py test、Kubernet es、My SOL、C + +；反例覆盖 Postman、pytest-like、普通英文和短技能字符间隔。

### 面试结论

这是一个典型 precision/recall 与业务风险权衡：硬条件系统宁可在未知错拼上保守，也不做不可解释 fuzzy match。

## 挑战六：岗位方向不能只有字符串相等，也不能宽泛 alias

### 现象

AI 后端、模型服务、算法平台、AI Infra 有真实交叉；简单 exact 会错判。但把“算法工程”和“后端开发”设成 alias 又会造成大量假匹配。

### 修复

方向结果升级为 exact/compatible/mismatch；构建最小 taxonomy，只覆盖项目已有方向。compatible 需要：允许的 leaf pair、两侧职责 signal、至少两个共享技能；平台类还要求 AI+工程技能组合。

### 验证

测试既覆盖 AI 平台兼容，也覆盖算法/普通后端、单侧 signal、共享技能不足等反例。

### 仍有边界

taxonomy 有限，不能自动覆盖全部行业岗位。新方向必须先建立人工标注口径。

## 挑战七：启发式分数容易被误解为概率

### 现象

100分制和85/65/45阈值很自然地让用户以为“85分代表85%录用概率”。

### 根因

项目没有真实 outcome，却使用了看起来精确的数值；策略语义没有进入 API。

### 修复

用冻结 `MatchScoringPolicy` 显式保存权重、阈值、`calibration_status=heuristic` 和 `score_semantics=heuristic_compatibility_score`；API 返回分项与策略，UI 改称启发式匹配分数。

### 为什么不拟合权重

25条 Gold 太小且已参与错误分析，4,798条 Pair 是规则自己生成，用它们拟合只会让规则拟合自己的标签。

### 面试结论

校准需要真实/人工 Pair 和招聘 outcome，当前最科学的选择是承认未校准。

## 挑战八：Explanation 1.0 被误解为建议有效

### 现象

历史 explanation consistency=1.0 容易被写成“建议准确率100%”。

### 根因

一个指标混合了结构矛盾、证据支持和建议实际效果。

### 修复

拆成 structural consistency、evidence grounding 和 advice validity。当前回归结构一致1.0、grounding 0.92、advice validity 未评估。

### 面试结论

离线文本一致性不能替代 downstream outcome。指标命名本身也是产品安全设计。

## 挑战九：JD 和 Resume 理论可并行，默认却没有提速

### 现象

两侧解析互不依赖，直觉上开两个线程即可；但 Transformers 后端实际仍串行。

### 根因

同一进程共享一个14B模型。并发 `generate` 可能增加显存峰值和线程安全风险，所以生成由 Lock 保护。

### 修复

执行策略按后端区分：Transformers sequential；vLLM 由 server scheduler 连续批处理，并通过 semaphore 受控并发，才并行提交两侧。

### 验证限制

统一 benchmark harness 已覆盖五类 workload，但当前环境没装 vLLM，所以没有伪造真实提升数字。

### 面试结论

任务可并行性不等于执行资源可并行性；要看共享状态、显存和后端调度。

## 挑战十：上传扩展名可信度不足

### 现象

仅按 `.pdf/.docx/.png` 选择解析器，伪装文件和损坏文件会进入昂贵解析/OCR，甚至形成安全风险。

### 修复

增加前置内容校验：PDF signature+pypdf、DOCX ZIP/OOXML、图片 Pillow decode/格式一致、文本 UTF-8/NUL/control；大小在读取边界和高成本步骤前限制。

### 取舍

这是原型级输入安全，不是恶意文件沙箱。没有因此引入杀毒服务、对象存储或异步扫描平台。

## 挑战十一：训练 loss 好看，产品收益无法证明

### 现象

历史 DPO reward accuracy 0.9297、margin 3.3643，看起来很成功。

### 根因

偏好主要来自合成结构 corruption，模型可能只是学会识别人工制造的错误；旧 Match 评测又受污染。

### 修复

把 adapter 晋级拆成绝对产品阈值和相对 baseline 回归；后来进一步通过 pause gate 和 readiness 阻断新 DPO。

### 面试结论

训练目标指标只能证明优化器完成了自己的任务，不能自动证明业务目标改善。

## 挑战十二：持续加功能导致项目边界膨胀

### 现象

招聘系统很容易继续增加账号、职位收藏、投递记录、推荐、企业端、队列和微服务。

### 根因

把“像完整产品”误认为“解决核心问题”。当前真正瓶颈是数据证据，不是缺一个后台。

### 决策

保留单体 FastAPI、静态前端和脚本化离线流水线；删除 legacy 训练路径和重复文档；不增加 CI、账号、多租户、Redis/Kafka/Celery、Embedding Matcher。

### 面试结论

不过度设计不是少做，而是把工程投入放在语义正确性、复现和评测可信度上。

## 挑战十三：什么时候应该停止项目

### 判断

在当前条件下，继续调规则会过拟合已看 Gold，继续合成数据不会产生真实 Pair，继续训练会绕过 readiness，继续平台化不改善核心证据。

### 决策

进入 Engineering Freeze。重新开放需要合法独立 Resume、人工/真实 Match Pair、human preference、Blind Gold V2 或真实用户 outcome。

### 面试价值

这是项目最成熟的判断：工程能力不仅是把系统做复杂，也包括识别边际收益何时低于可信度风险。

## 如何选择三个 STAR 故事

若面试偏算法/评测：讲历史评测污染、OCR evidence、三层评测。  
若偏数据：讲 source group、entity split、readiness。  
若偏后端/AI 工程：讲 Transformers/vLLM 并发、上传校验、混合规则架构。  
若只能讲一个：讲“发现旧 Match holdout 污染并主动废弃指标”，它最能体现完整判断链。
