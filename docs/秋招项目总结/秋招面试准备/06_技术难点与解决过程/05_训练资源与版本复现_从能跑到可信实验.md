# 训练资源与版本复现：从“能跑”到可信实验

## 1. 挑战不是启动 Trainer，而是让实验结论可复现

Qwen3-14B 的全量参数、激活、梯度和优化器状态超过普通单卡承载能力。即使一次训练侥幸跑完，如果数据版本、依赖版本、mask 或 checkpoint 来源不清楚，结果也不能可信比较。

项目面对的是四个同时存在的约束：

```text
显存有限
样本长度不同
训练库接口变化快
数据质量仍不稳定
```

## 2. 最初容易犯的错误

### 错误一：先全量训练再看显存

14B 全参训练不仅保存模型参数，还要保存梯度和优化器状态；即使 bf16 参数勉强放下，训练状态和激活也会迅速超过显存。

### 错误二：同时打开所有性能选项

packing、Liger、FlashAttention、activation offloading 和 gradient checkpointing 同时打开，失败时无法判断是版本兼容、mask、kernel 还是数据问题。

### 错误三：只保存 checkpoint，不保存运行上下文

之后无法回答：它用了哪份 train/valid、哪些 CLI 覆盖、多少 source group、从哪个 adapter 继续训练。

### 错误四：把 loss 下降当产品提升

模板数据上 loss 很容易下降，但可能只是记住 JSON 格式或重复变体。

## 3. 显存方案为何选择 QLoRA

基础权重使用4-bit NF4存储，计算 dtype 为 bf16；冻结基座，只训练低秩 adapter。

对于线性层：

```text
W' = W + (alpha/r) BA
```

项目使用 `r=8, alpha=16`，目标模块覆盖 attention 的 q/k/v/o 和 MLP 的 gate/up/down。

这降低的是基础权重存储、可训练参数和优化器状态。它不消除激活显存，因此仍需要 micro batch 1 和 gradient checkpointing。

## 4. 梯度累积解决什么

单设备情况下：

```text
per_device_train_batch_size = 1
gradient_accumulation_steps = 16
```

每个 micro step 反向但不更新，累计16步后执行一次 optimizer step，有效更新 batch 约16条。

它降低单步峰值显存，但不会减少完成一个 epoch 的总计算量。多进程训练时还要乘数据并行 world size；当前 `device_map=auto` 不能被简单解释成 DDP。

## 5. Gradient checkpointing 的实际取舍

不保存所有中间激活，反向时重算部分前向：

```text
收益：激活显存下降
代价：训练墙钟时间增加
```

它与4-bit权重量化解决不同内存项。面试中不能把所有显存下降都归因于 QLoRA。

## 6. 为什么 packing 默认关闭

当前使用 conversational messages，并设置 `assistant_only_loss=True`。Packing 会把多个短样本拼入一个序列，效率更高，但必须确认：

- chat template 的 generation mask 正确；
- 样本边界不会污染；
- 截断不切断 assistant JSON；
- 当前 TRL 版本行为一致。

在未做这些验证前关闭 packing，是为了先建立正确性基线。

## 7. Assistant-only loss 的隐藏风险

配置写 `assistant_only_loss=True` 不代表一定只训练 assistant。它依赖 chat template 能提供 generation markers 或 assistant mask。

正确的 smoke test 应打印 token、role 区域和 labels：

```text
system/user token → label = -100
assistant JSON token → label = 对应 token id
padding token → label = -100
```

如果模板不支持，训练可能报错，也可能与预期不同。这个检查比盯着第一个 loss 数字更重要。

## 8. DFT 带来的版本挑战

配置中的 `loss_type: dft` 表示 TRL 的 Dynamic Fine-Tuning，不是 DPO。

当前仓库依赖范围是：

```text
trl>=0.10,<2
```

跨度过大，而 DFT 是较新接口。旧 TRL 可能不支持 `loss_type`，新版本又可能修改 SFTConfig 参数名、数据处理或 mask 行为。

因此仅看 YAML 不能证明历史训练一定使用与当前官方实现相同的 DFT。

## 9. 如何把“版本风险”变成可执行检查

正式训练前至少记录：

```text
Python/PyTorch/CUDA/Transformers/TRL/PEFT/bitsandbytes 版本
GPU 型号与数量
git commit
完整 YAML
CLI 覆盖项
base model 与 adapter 路径/hash
train/valid 文件 hash 与行数
source group 数和任务分布
```

然后运行三个 smoke：

1. 构造 SFTConfig，确认所有参数被目标版本接受；
2. 取一条样本检查 assistant mask；
3. 完成一个 optimizer step 并保存/重新加载 adapter。

## 10. `run_manifest` 已经解决了什么

训练入口在重依赖加载前写 manifest，记录阶段、配置、输出目录、数据路径、CLI 参数以及数据摘要。

这让 checkpoint 能追溯到大部分运行输入。仍需补强的是完整依赖快照、git commit、GPU 信息和模型文件 hash。

## 11. 截断问题如何发现

`max_seq_length=768` 对三任务不是同一种风险：

- JD 尾部常有学历、经验、加分项；
- 简历尾部常有项目；
- Match prompt 同时包含 JD、简历和规则结果。

调试不能只看 OOM。应统计各任务 token P50/P90/P95/P99、截断率和截断位置，再比较 768/1024 的质量、显存和速度。

## 12. 为什么只训练1 epoch

当前简历平均约六种格式变体，bootstrap 比例很高。更多 epoch 会重复看到同一实体标签，增加记忆模板风险。

1 epoch 不是理论最优，而是数据独立性不足时的保守选择。是否增加应由新的独立验证集决定。

## 13. 训练完成后的验证闭环

```text
训练 loss / eval loss
  ↓
strict JSON valid
  ↓
字段级 raw 指标
  ↓
normalized 与 product 指标
  ↓
历史冻结回归
  ↓
新 blind holdout
  ↓
三任务回退检查
```

只有 loss 下降而后面没有提升，不能称为训练有效。

## 14. 当前为什么不继续做参数搜索

瓶颈是 Resume 独立来源和真实 Match Pair，不是已证明的 adapter 容量不足。搜索 rank、学习率、epoch 会在同一合成分布上产生更多数字，却不能回答真实泛化。

这也是“不过度设计”的体现：先解决证据瓶颈，再决定是否扩展训练技术。

## 15. 面试回答结构

> 14B 后训练的挑战不仅是显存。我用4-bit NF4加载冻结基座，只训练rank-8 LoRA，micro batch 1、累积16步，并用gradient checkpointing换显存；packing先关闭以保护assistant-only mask。但更重要的是复现：仓库TRL版本范围过宽，DFT又是较新接口，所以正式训练前要冻结依赖、检查mask、做一步保存重载smoke，并把数据hash、source group和CLI写入manifest。当前数据真实性是瓶颈，因此我没有继续做无意义的rank和epoch搜索。
