# 推理并发与显存约束：从错误并行到可观测后端

## 1. 为什么 JD 和简历看起来天然应该并行

一次匹配要先解析 JD 和简历，两者输入独立：

```text
JD parse ─────┐
              ├→ rule → explanation
Resume parse ─┘
```

理论上并行后：

```text
T_parse_wall ≈ max(T_jd, T_resume)
```

顺序则是二者相加。但 GPU 推理不能因为业务依赖独立就直接开两个 Python 线程。

## 2. 最初“加线程池”为什么不等于并行

Transformers 路径共享同一个模型实例和 GPU。两个线程同时调用 `generate` 会带来：

- KV cache 与激活同时增长；
- 峰值显存不可预测；
- 某些模型/设备状态不是按请求隔离；
- Python 线程无法自动形成高效动态 batch。

项目在 `_complete_with_transformers` 外使用 `_lock`。即使上层提交两个 future，进入 generate 的关键区仍串行。

## 3. `run_in_threadpool` 解决的是另一件事

FastAPI 路由是 async，但模型推理和文件处理是同步函数。`run_in_threadpool` 的作用是防止同步工作堵住事件循环，使健康检查和其他请求仍能被调度。

它解决 Web server responsiveness，不代表同一 GPU 同时推理。

这两个“线程池”概念在面试中必须区分。

## 4. 为什么 vLLM 路径可以不同

vLLM 是独立推理服务，通过 OpenAI 兼容客户端发送请求。服务端可以做 continuous batching 和请求调度，因此客户端同时提交 JD/Resume 才可能转化为真实吞吐收益。

项目的并行条件明确写成：

```text
backend == vllm
JOBMATCH_PARALLEL_MATCH_PARSE 开启
JOBMATCH_VLLM_MAX_CONCURRENCY >= 2
```

否则 `match_parse_mode` 返回 sequential。

## 5. 为什么还需要 BoundedSemaphore

即使 vLLM 支持并发，也不能无限提交。`_vllm_slots` 将客户端在途请求限制为配置的最大并发。

它防止：

- 单个批量请求占满服务；
- 队列无限增长；
- 显存因并发序列过长突然升高；
- 外部调用把服务压垮。

真正安全的上限仍需根据输入长度、输出长度、GPU和vLLM配置压测。

## 6. 批量 API 不是模型 tensor batch

`batch_parse` 和 `batch_match` 在 vLLM 模式下用线程池并发提交多个普通请求；Transformers 模式则顺序调用。

它没有把多条输入 pad 成一个 tensor 后调用一次 `generate`。因此“支持批量接口”不等于“实现了原生模型 batch inference”。

## 7. 如何证明并行真实发生

响应保留：

```text
execution.backend
execution.parse_mode
jd_parse_seconds
resume_parse_seconds
parse_wall_seconds
analysis_seconds
total_seconds
```

并行时通常应看到：

```text
parse_wall_seconds < jd_parse_seconds + resume_parse_seconds
```

但单次样本不足以下结论，还要比较并发1/2/4时的：

- p50/p95延迟；
- requests/s；
- tokens/s；
- GPU峰值显存；
- 错误和超时率；
- 长短请求混合时的尾延迟。

## 8. 为什么默认仍是 Transformers

默认路径依赖少、单请求调试直接、adapter加载方式清晰，适合当前单用户演示和问题定位。

vLLM 更适合多请求吞吐，但当前环境没有完成可复现 benchmark，也不能给出可靠提升数字。因此文档只说明能力和测试方法，不编造性能结论。

## 9. 三次生成带来的延迟结构

一次匹配包含：

```text
JD parse generation
Resume parse generation
Match explanation generation
```

规则计算通常远小于生成时间。所以性能优化顺序应是：

1. 并行前两个独立解析；
2. 限制不必要输出 token；
3. 使用结构化约束减少重试；
4. vLLM continuous batching；
5. 有重复输入时再考虑缓存。

微优化评分正则对总延迟帮助有限。

## 10. 失败与降级策略

### vLLM服务不可达

模型加载/健康检查失败，应该明确报503，不静默切换到另一个可能占显存的本地模型。

### 一侧解析失败

不能用空结构继续评分，否则“无技能要求”会产生虚假乐观结果。当前直接停止匹配。

### 解释生成失败

规则结果实际已经产生。产品后续可以降级只展示规则层，但需要明确“解释暂不可用”，不能伪造建议。

### 并发过高

通过 semaphore、请求上限和批量上限控制，而不是让用户无限提交。

## 11. 当前实现仍有什么不足

- 没有请求级超时和取消传播；
- 没有生产级排队长度、GPU指标和 tracing；
- raw output 默认进入响应，正式环境应受 debug 开关控制；
- Transformers 单模型锁牺牲吞吐换稳定；
- vLLM尚缺本机真实基准；
- 批量 match 会在每个 item 内再次发三次生成，请求放大明显。

这些只有在真实多用户需求出现后才值得继续平台化。

## 12. 面试回答结构

> JD和简历业务上独立，但GPU并发不能只靠Python线程。Transformers路径共享一个模型实例，我用锁串行generate，`run_in_threadpool`只负责不阻塞FastAPI事件循环。只有vLLM后端、并行开关开启且并发至少2时才同时提交解析请求，并用BoundedSemaphore限制在途请求。响应返回backend、parse mode和分阶段墙钟，所以能用数据证明是否并行。当前没有vLLM基准，因此我不会宣称具体加速倍数。
