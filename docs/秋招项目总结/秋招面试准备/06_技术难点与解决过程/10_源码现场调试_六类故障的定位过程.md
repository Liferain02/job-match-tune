# 源码现场调试：六类故障的定位过程

面试官问“遇到什么困难”时，不能只回答“数据质量不好、模型会幻觉”。好的回答要包含观察、假设、最小复现、定位层、修复和防回归。本章给出六条能直接照着源码走的调试路径。

## 1. 总调试原则：先确定错误属于哪一层

```text
输入层       上传、编码、长度、隐私
生成层       原始 token 与 JSON
归一化层     字段错位、alias、证据类别
规则层       技能交集、方向、学历、年限、分数
解释层       自相矛盾、无证据陈述
展示层       前端取错字段、状态提示不清
```

同一句“结果不对”，六层的修法完全不同。直接调大模型或调权重通常是最低效的第一反应。

## 2. 案例一：JD 与简历解析为什么没有并行

### 观察

`jd_parse_seconds` 和 `resume_parse_seconds` 都很长，`parse_wall_seconds` 接近二者之和。

### 第一假设

线程池没有生效。

### 源码定位

看 `ModelService.match_parse_mode`：只有三个条件同时成立才返回 parallel：

```text
backend == vllm
parallel_match_parse == true
vllm_max_concurrency >= 2
```

Transformers 路径即使提交两个线程，`model.generate` 也由 `_lock` 保护；同一模型实例的生成关键区仍然串行。

### 验证

检查 `/health` 或响应：

```json
{"execution": {"backend": "transformers", "parse_mode": "sequential"}}
```

再看环境变量：

```bash
JOBMATCH_INFERENCE_BACKEND
JOBMATCH_PARALLEL_MATCH_PARSE
JOBMATCH_VLLM_MAX_CONCURRENCY
```

### 正确结论

问题不是 `future.result()` 导致串行，而是 Transformers 后端设计为单模型锁串行。要真正并行，需要 vLLM 服务接受两个并发请求并做 continuous batching。

### 防回归证据

接口响应显式返回 backend、parse_mode 和墙钟耗时，使行为可观测；不能只看代码里出现了 `ThreadPoolExecutor` 就认为已并行。

## 3. 案例二：加分项 Kubernetes 被判为缺失技能

### 观察

用户简历没有 Kubernetes，页面却把它列为硬短板；原文中它只出现在“加分项”。

### 错误假设

技能权重太高，需要调低 45 分。

### 分层检查

1. `raw_output`：模型是否把 Kubernetes 放进必备技能；
2. `raw_data`：严格 JSON 中字段位置；
3. `data.技能证据`：证据来源是否为 bonus；
4. `data.必备技能`：是否只取 required evidence；
5. `rule_result.缺失技能`：是否仍出现 Kubernetes。

### 根因

这是 required/bonus 语义错误，不是权重问题。正确修复点在 `collect_jd_skill_evidence` 和章节识别。

### 最小测试

构造只含三行的 JD：

```text
岗位职责：使用 Kubernetes 运维平台
任职要求：熟悉 Python
加分项：了解 Docker
```

断言只有 Python 的 `是否必备=true`，Kubernetes 和 Docker 仍有证据但不进入 required skills。

### 为什么保留非必备证据

完全删掉 Kubernetes 会损失解释价值。正确做法是“保留事实、改变约束角色”。产品可以展示它是加分项，但不能扣硬技能分。

## 4. 案例三：`C` 技能误命中 CUDA

### 观察

JD 要 C，简历只有 CUDA，却被认为技能命中。

### 根因

朴素子串匹配：`"c" in "cuda"` 为真。

### 修复思路

短英文技能需要 token 边界，OCR 紧凑匹配不能无条件应用：

```text
C       只在独立 token/明确技能形态命中
C++     允许处理 C + + 等 OCR 间隔
Python  可允许 Py thon
```

### 为什么不能统一用 `\b`

Python 正则的单词边界基于字母数字和下划线，对 C++、.NET、Node.js 等含符号技术词并不总符合业务边界。项目结合 canonical alias、紧凑 key 和技能长度做有限处理。

### 防回归矩阵

```text
正例：C、C语言、熟悉 C 开发
反例：CUDA、React、Ctrip
正例：C++、C + +
```

## 5. 案例四：2025 年毕业被识别为 2025 年经验

### 观察

应届生简历经验条件异常地判为满足。

### 最小复现

```text
2025 年毕业，参与 1 年项目
```

若取所有“数字+年”的最大值，结果会是 2025。

### 当前过滤

- 数字后 12 个字符出现毕业、入学、应届、在校、出生、届时跳过；
- 大于 50 的时长过滤；
- “25 年校招/秋招”等两位届别过滤；
- 区间要求取合理下界。

### 仍有的边界

“2022—2024 负责某项目”没有直接换算为 2 年；多段相邻实习也没有做日期区间合并。当前实现宁愿保守地得到 0/明确年数，也不推断复杂履历时长。

### 面试取舍

若业务非常依赖年限，应单独设计日期 span parser 并处理重叠区间；当前秋招匹配更关注项目能力，继续扩张年历算法可能过度设计。

## 6. 案例五：评测突然变成 1.0

### 观察

历史报告约 0.96～0.99，修复后冻结回归变为结构 1.0。

### 危险结论

> 系统已经达到 100% 准确率。

### 审计步骤

1. 检查数据是否为同一 25 条 Gold；
2. 检查开发者是否看过错例；
3. 检查规则是否根据这些错例修改；
4. 检查 report 的 `evaluation_validity`；
5. 区分 product final 和 raw model；
6. 看 grounding 是否也为 1.0。

### 正确解释

Gold 已被 inspection，当前 1.0 是历史错误全部修复后的回归结果；grounding 仍为 0.92，说明解释证据仍有问题。需要新的人工 blind holdout 才能评估泛化。

### 工程收益

把报告显式标记 `historical_gold_v1_regression`，让未来读者不能无意中把它当正式 blind accuracy。

## 7. 案例六：DPO 脚本能运行，为什么仍不启动

### 观察

配置、Trainer 和启动脚本都存在，旧 readiness 字段甚至显示 `ready_for_dpo=true`。

### 继续检查

同一摘要还有：

```text
dpo_paused_by_quality_goal = true
dpo_execution_ready = false
dpo_pipeline_fresh = false
```

管线报告显示 preference 文件早于上游最新 SFT 数据。数据主要是 synthetic structured hard negative，不是新的人工真实偏好。

### 正确决策

不运行。先解决 freshness、实体切分和 preference 质量，再做小规模 A/B。

### 这个案例展示的能力

成熟工程判断不是“每个技术都跑一遍”，而是设置停止条件，避免把 GPU 时间投入到无法产生可信结论的实验。

## 8. 补充检查：模型说 JSON 成功，产品为什么仍失败

### 情形 A：raw strict 失败，product 成功

中文引号或尾逗号被 repair。说明产品可用，但模型原生格式遵循仍需改进。

### 情形 B：raw strict 成功，product 语义失败

JSON 合法但字段错位或技能证据错。语法指标无法发现。

### 情形 C：parse 成功，analysis 失败

规则层可用，最后解释 JSON 无效。产品可以考虑降级展示规则结果，而当前 match 实现会返回 `ok` 取决于 analysis 结果并保留 rule result。

### 情形 D：所有 JSON 成功，但建议胡编

用 evidence grounding 检查已知技能陈述；更开放的建议有效性仍无法自动证明。

## 9. 现场打开代码的顺序

面试官若让现场导览，不要从仓库树逐文件念：

1. `api/server.py` 的 `match()`：展示总编排；
2. `_parse_match_inputs()`：展示 vLLM 并行条件；
3. `postprocess_json.py` 的 `parse_json_output()`：展示 raw 与 normalized；
4. `jd_skill_evidence.py` 的 `SkillEvidence.required`：展示 required 语义；
5. `rule_engine.py` 的 `compute_match_rule_result()`：展示事实层；
6. `direction_compatibility.py`：展示兼容必须有双方证据；
7. `run_match_eval.py` 的 `layers`：展示三层评测；
8. `report_data_readiness.py`：展示为什么停止训练。

这条路径从请求编排一路到可信度边界，十分钟内能形成完整闭环。

## 10. 日志和响应中最有用的字段

```text
raw_json_ok                 模型是否原生输出严格 JSON
raw_json_error              语法错误位置
raw_output                  原始生成
execution.backend           实际推理后端
execution.parse_mode        并行或顺序
timings.parse_wall_seconds  用户等待的解析墙钟
timings.analysis_seconds    解释生成时间
岗位方向证据                exact/compatible 的理由
技能证据                    required/bonus/职责片段
匹配分项                    每一分从哪来
```

正式生产不一定把 raw output 返回浏览器，但开发和面试环境需要保留可观测性。

## 11. 一套可复用的故障回答框架

```text
现象：用户看到什么错误？
影响：它会造成误扣分、误解释还是仅格式失败？
分层：输入/生成/归一化/规则/解释/展示？
复现：最短输入是什么？
证据：哪个中间字段第一次偏离预期？
修复：在最靠近根因、最可测试的一层处理。
回归：增加哪组正反边界测试？
限制：还有哪些表达没有覆盖？
```

## 12. 面试口述模板

> 我调试时先比较 raw output、strict JSON、normalized data、rule result 和 final analysis，找到第一次偏离预期的层。比如加分项 Kubernetes 被判缺失，不应该调技能权重，而要看 evidence kind；2025 年毕业被算经验，要修年限过滤；解析没并行则要看实际 backend 和锁，而不是看到线程池就下结论。每次修复都用最短正反例固化测试，同时说明规则未覆盖的边界。
