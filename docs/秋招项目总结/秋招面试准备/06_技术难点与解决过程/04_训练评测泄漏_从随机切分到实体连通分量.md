# 训练评测泄漏：从随机切分到实体连通分量

## 1. 最隐蔽的问题：行不同，实体相同

项目会把一份简历扩成 original、bullets、compact、OCR 等多个样本，也会让同一 JD 或同一简历出现在多个 Match Pair 中。

按行随机切分时，即使文本不完全相同，也可能发生：

```text
训练集：Resume-1 的 original
测试集：Resume-1 的 OCR 版本
```

或者：

```text
训练集：JD-1 + Resume-A
测试集：JD-1 + Resume-B
```

模型已经见过同一实体事实，测试指标会虚高。

## 2. 为什么文本去重不够

完全内容 hash 能去掉相同的 user+assistant 对，但不能识别：

- 同一简历的格式改写；
- OCR 噪声版本；
- 同一 JD 配不同简历；
- 同一简历配不同 JD；
- 通过中间 pair 形成的传递关联。

因此需要同时记录样本身份和它依赖的实体身份。

## 3. 从错误切分到正确抽象

最终为每条样本引入三类键：

```text
source_group：样本的基础来源实体
linked_source_groups：匹配样本涉及的 JD 和 Resume 实体
normalized_input_hash：忽略大小写、空白、标点的输入指纹
```

简历的六个变体共享同一 `source_group`。Match Pair 还保存：

```text
match_jd:<hash>
match_resume:<hash>
```

## 4. 为什么普通 group split 仍然不够

假设：

```text
A = JD-1 + Resume-1
B = JD-1 + Resume-2
C = JD-2 + Resume-2
```

A 与 B 共享 JD；B 与 C 共享 Resume。即使 A 与 C 没有直接共同字段，它们通过 B 连通。若只按每行第一个 group 切分，仍可能拆开这个关联链。

问题本质变成：把所有共享实体的样本连成图，按连通分量切分。

## 5. 并查集实现过程

对每条样本：

1. 建立 `group:<source_group>` 节点；
2. 为每个 linked entity 建 `linked:<id>` 节点；
3. 为 user 输入建 `input:<normalized_hash>` 节点；
4. 将这些节点 union；
5. 对所有样本的 group 节点执行 find；
6. 相同根节点的样本组成一个 component；
7. 打乱 component，而不是打乱 sample；
8. 整体分配到 train、valid、test。

路径压缩后，union/find 摊还复杂度接近常数，远小于数据构建和模型训练成本。

## 6. 比例不精确为什么是合理代价

目标可能是80/10/10，但 component 大小不一。按 component 数量切分后，最终样本行数可能偏离目标。

选择是：

```text
比例精确，但拆开实体
比例近似，但保持独立性
```

项目选择后者。评测可信度比漂亮的整数比例重要。

## 7. 如何证明修复有效

单元测试构造：

```text
a 和 b 共享 jd:1
c、d 使用其他实体
```

切分后断言 a 与 b 必须落在同一 split。

Readiness 进一步审计：

- cross-split source groups；
- cross-split normalized input hashes；
- cross-split linked source groups；
- 各 linked entity 类型的重叠计数；
- 每任务 unique source group ratio。

只有重叠为0并且来源多样性满足门槛，才允许进入训练。

## 8. 修复后为什么 readiness 仍是 false

无泄漏不等于数据好。

当前简历 SFT 15,470行对应2,557个 group，平均约6.05条/组；2,525个 group 来自 bootstrap，占98.75%。Match 的4,798个 Pair 全部为规则合成。

实体切分解决了“验证作弊”，但没有创造新的真实候选人和真实匹配关系。因此系统正确地继续阻止 resume、match、multitask 新训练。

## 9. Gold 独立性也要分层审计

Gold 审计同时比较：

- 完整 pair hash；
- JD hash；
- Resume hash；
- JD 单任务训练文本；
- Resume 单任务训练文本；
- source group 和重复 pair。

这样可以发现“完整 pair 没见过，但其中一侧单体见过”的弱泄漏。

但 normalized hash 为0仍不证明语义独立；同义改写可能产生不同 hash。真正的 blind holdout 还要有来源和流程隔离。

## 10. 一个仍存在的风险

从模型 prediction mismatch 构造的 preference 数据目前使用普通随机行切分，而不是 `split_linked_samples`。如果多条 preference 来自同一实体，就可能跨 train/valid。

因此恢复 DPO 前必须：

1. 把 source_group 和 linked groups 带入 preference；
2. 使用实体连通分量切分；
3. 运行同样的跨集合审计；
4. 再讨论 DPO 指标。

这也是为什么当前不应绕过 DPO pause gate。

## 11. 这次挑战真正体现的工程能力

难点不在实现并查集，而在意识到统计单位错了：样本行不是独立实体，pair 也不是独立的两侧数据。

从“训练条数”转向“来源组数、扩增比、实体重叠和来源分布”，项目对数据规模的表达发生了根本变化。

## 12. 面试回答结构

> 我最初按样本行理解数据规模，后来发现一份简历会扩成六种格式，同一 JD 或简历还会进入多个 pair。随机切分即使文本不完全相同，也会让同一实体跨训练和测试。我为样本增加 source group、JD/Resume linked entity 和 normalized input hash，再用并查集求传递连通分量，按分量整体切分。修复后跨集合重叠为0，但 readiness 仍为 false，因为15,470行只有2,557个来源组且98.75%来自 bootstrap。这个结果说明我修掉了泄漏，却没有拿虚高指标掩盖真实数据不足。
