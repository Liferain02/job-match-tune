# 岗位方向边界：从字符串相等到双侧证据兼容

## 1. 为什么这是匹配任务里最难解释的布尔值

岗位名称没有统一标准：

```text
算法工程师
算法平台工程师
推理工程师
模型服务工程师
AI 后端开发
后端开发
AI Infra
```

字符串不同不一定不匹配；字符串相近也不一定匹配。“算法工程”和“后端开发”可能都在做模型服务，也可能分别是 CV 训练和订单 CRUD。

## 2. 两个极端方案为什么都失败

### 只做字符串相等

会把“后端开发工程师”和“后端开发”误判不同，也无法处理模型服务与 AI 后端的真实交叉。

### 建大 alias 表，把相近方向都映成同一个

会把普通后端、算法训练、AI 应用和平台工程压成一个宽类，召回提高但误匹配严重。

方向兼容需要的不只是名称，还要有职责和技能证据。

## 3. 第一步：小而明确的叶子分类

`direction_leaf` 将已出现的方向映射到最小叶子，例如：

```text
algorithm_platform
model_serving
ai_backend
ai_infra
ai_application
algorithm
data_engineering
backend
frontend
security
```

具体标签优先于宽泛标签。只有“算法”“后端”这类宽泛标题，才允许根据职责中的模型服务/平台信号进一步细化。

没有建设通用职业知识图谱，因为当前 Gold 和产品范围不足以支持完整 ontology。

## 4. 第二步：三态关系而不是一个布尔值

内部保留：

```text
exact
compatible
mismatch
```

`matches` 属性把 exact 和 compatible 映射为 true，供现有评分使用；但响应仍保留 relation、双方叶子、共享技能、证据类型和原因。

这样前端和评测可以区分“完全同方向”与“基于职责证据兼容”，避免丢失判断过程。

## 5. 第三步：跨方向兼容必须满足双侧证据

以 AI 平台相关方向为例，需要同时满足：

1. 两个叶子组成的 pair 在显式白名单；
2. 至少两项共享技能；
3. 共享技能中至少有一项 AI 技能；
4. 共享技能中至少有一项工程技能；
5. JD 上下文出现模型服务/平台信号；
6. 简历上下文也出现模型服务/平台信号。

为什么强调双侧：JD 是模型平台，但候选人只有普通后端经历，不应仅凭 Python、Docker 就判兼容；反过来也一样。

## 6. 一个从误判到修复的例子

输入 A：

```text
JD：算法工程，职责是训练 CV 模型
简历：后端开发，项目是 Java 订单服务
共享技能：无
```

结果必须 mismatch。

输入 B：

```text
JD：算法工程，职责是建设 serving 平台 API
简历：AI 后端，项目是在线推理与 Docker 部署
共享技能：PyTorch、FastAPI、Docker
```

结果 compatible。

如果只改 alias，让“算法工程≈AI后端”，A 和 B 会一起变 true。双侧证据方案只允许 B。

## 7. 为什么至少两项共享技能

一项 Python 太通用，不能证明方向一致。至少两项降低偶然交集，同时 AI 平台类还要求 AI 技能和工程技能各至少一项。

这不是统计学习得到的最优阈值，而是当前小样本下保守、可解释的规则。未来有足够 blind Gold 后才适合校准。

## 8. 为什么 compatible 当前也拿满20分

现有评分只消费 `direction_match` 布尔，因此 exact 和 compatible 都获得方向20分。这是为了保留历史评分行为。

但 relation 已保留，未来可以比较三种方案：

```text
exact 20 / compatible 20
exact 20 / compatible 10～15
compatible 不降分，但页面增加不确定性提示
```

在只有25条已查看 Gold 的情况下直接调分会过拟合，因此当前没有为了“看起来精细”增加新权重。

## 9. 测试为什么必须写负例

仅验证六个 compatible 正例很危险。测试同时覆盖：

- 算法训练 vs 普通后端；
- serving JD vs 普通订单服务；
- 测试开发 vs 后端；
- 前端 vs 后端；
- 离线数仓 vs 普通后端；
- CV 算法 vs RAG 应用；
- GPU 集群 vs 普通 CRUD；
- 产品、安全、客户端与后端。

每个负例都故意保留一部分相似信号，验证缺少双侧证据时必须退回 mismatch。

## 10. 调试方法

发现方向判错时依次打印：

```text
原始方向名称
direction_leaf 的结果
JD direction context
Resume direction context
shared_skills
pair 是否在白名单
两侧信号正则是否命中
最终 evidence_type 和 reason
```

不要先看总分，因为方向错误可能被其他分项掩盖。

## 11. 当前未解决的边界

- 方向 taxonomy 只覆盖项目已有标签；
- 新岗位名称可能原样返回，无法形成可靠 leaf；
- 共享技能只看集合，不衡量熟练度；
- 项目描述可能夸大职责，规则无法验证真实性；
- exact/compatible 的分数尚未用真实 outcome 校准；
- 同一候选人的多方向能力没有显式建模。

## 12. 面试回答结构

> 岗位方向既不能只做字符串相等，也不能用一个大 alias 表把相近岗位全合并。我保留 exact、compatible、mismatch 三态，先映射到小范围叶子；跨方向兼容必须是显式白名单 pair，并同时满足至少两项共享技能、AI与工程技能组合以及 JD/简历两侧的职责信号。测试不仅覆盖正例，还覆盖普通 CRUD、CV 训练等相似但不兼容的负例。当前 compatible 仍与 exact 同分，是为了保持历史策略，等新的 blind Gold 再校准。
