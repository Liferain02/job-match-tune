# 一次匹配请求的完整生命周期与数据快照

这一章只做一件事：把用户点击“开始匹配”之后发生的事情，从 HTTP 请求一直跟到页面展示。面试时如果只能选一条代码主线，应当讲这一条。

对应源码：

- `frontend/src/App.js`
- `src/jobmatch_tune/api/server.py`
- `src/jobmatch_tune/inference/predict.py`
- `src/jobmatch_tune/inference/postprocess_json.py`
- `src/jobmatch_tune/match/rule_engine.py`
- `src/jobmatch_tune/eval/explanation_grounding.py`

## 1. 先记住最终调用图

```text
浏览器
  │ POST /match {jd_text, resume_text, max_new_tokens}
  ▼
FastAPI /match
  ▼
run_in_threadpool(service.match)
  ├── JD parse ───────┐
  ├── Resume parse ───┤ transformers 顺序；vLLM 可并行
  │                   ▼
  │          normalize_parsed_data
  │                   ▼
  ├────────── compute_match_rule_result
  │                   ▼
  ├────────── Match explanation generation
  │                   ▼
  └────────── response: parse + rule + analysis + timing
                      ▼
                 Vue 渲染结果
```

这里最重要的不是框架，而是职责边界：模型先做两次信息抽取；规则层依据抽取结果计算硬结论；模型最后只能围绕规则结果写解释。

## 2. HTTP 输入层做了什么

`MatchRequest` 定义三个字段：

```python
class MatchRequest(BaseModel):
    jd_text: str = Field(min_length=1, max_length=20000)
    resume_text: str = Field(min_length=1, max_length=20000)
    max_new_tokens: int = Field(default=1024, ge=64, le=4096)
```

这不是单纯类型声明，它完成了第一层防御：

- 空 JD 和空简历在进入模型前就被拒绝；
- 单段文本最多 20,000 字符，限制异常大请求；
- 生成长度被夹在 64～4,096，避免调用方把显存和响应时间拉爆；
- Pydantic 验证失败由 FastAPI 返回 422，不进入业务函数。

面试追问“为什么不在前端校验就够了”时，答案是：前端校验改善体验，后端校验才是信任边界。调用者可以绕开前端直接请求 API。

## 3. 为什么路由函数本身是 async，模型函数却放在线程池

模型推理、OpenAI 兼容客户端以及文件解析都是同步调用。如果直接在 `async def` 路由中执行，会阻塞事件循环。因此端点通过 `run_in_threadpool` 执行同步业务函数。

这只解决“不要堵死 FastAPI 事件循环”，不等于 GPU 推理自动获得并发。真正的模型并发由后端实现和锁控制：

- Transformers 路径的 `_complete_with_transformers` 使用同一把 `_lock` 包住 `model.generate`，所以同一进程内生成串行；
- vLLM 路径通过 OpenAI 兼容 HTTP 客户端请求独立服务，并由 `_vllm_slots` 限制并发上限；
- 因此 JD 和简历解析只有在 `backend == "vllm"`、并行开关开启且最大并发至少为 2 时才并行。

这解释了一个容易说错的点：使用 `ThreadPoolExecutor` 不会让单卡 Transformers 同时安全执行两次 `generate`，因为锁仍会串行化关键区；它只在远端 vLLM 能批处理并发请求时真正降低墙钟时间。

## 4. 用一组具体输入贯穿链路

假设 JD 是：

```text
岗位方向：AI 后端开发
岗位职责：负责大模型在线推理服务和平台 API，使用 FastAPI 建设服务。
任职要求：熟悉 Python、PyTorch、Docker；本科及以上；2 年相关经验。
加分项：熟悉 Kubernetes。
```

简历是：

```text
目标岗位：算法平台工程师
本科，1 年实习经历。
技能：Python、PyTorch、FastAPI、Docker。
项目：用 FastAPI 和 Docker 部署 PyTorch 模型服务。
```

前端发送的请求只含原始文本和长度参数，不发送前端猜测的结构字段：

```json
{
  "jd_text": "……",
  "resume_text": "……",
  "max_new_tokens": 1024
}
```

这样做避免前端和后端各维护一套解析规则。

## 5. 第一阶段：构造两个 ParseRequest

`_parse_match_inputs` 把一个 `MatchRequest` 拆为：

```text
ParseRequest(task="jd_parse", text=jd_text)
ParseRequest(task="resume_parse", text=resume_text)
```

两次调用复用 `parse()`，因此单独解析端点和匹配端点不会出现两套逻辑。这里的复用价值比“少写几行代码”更重要：JSON 修复、字段归一化、耗时统计和后端选择都保持一致。

如果使用 vLLM，并行分支通过两个 future 同时提交。随后依次调用 `future.result()` 不是重新串行执行，而是等待已同时开始的任务完成。理想情况下：

```text
parse_wall ≈ max(T_jd, T_resume) + 调度开销
```

顺序模式则是：

```text
parse_wall ≈ T_jd + T_resume
```

必须使用 `timings.parse_wall_seconds` 实测，不能只凭线程数声称吞吐提升。

## 6. 第二阶段：模型抽取不是最终业务数据

每次 `parse()` 都经过：

```text
build_prompt
  → chat template
  → deterministic generation
  → parse_json_output
  → normalize_parsed_data
```

Transformers 路径明确设置：

- `enable_thinking=False`；
- `do_sample=False`；
- `temperature=None`；
- `top_p=None`。

vLLM 路径设置 `temperature=0`，并传入任务对应的 `response_format`。两条路径都追求可复现结构输出，但只有 vLLM 路径把 JSON Schema 约束下推给服务端。

假设模型原始 JD 输出为：

```json
{
  "岗位方向": "AI后端",
  "核心职责": ["负责大模型在线推理服务和平台 API"],
  "任职要求": ["熟悉 Python、PyTorch、Docker", "本科及以上", "2 年相关经验"],
  "必备技能": ["Python", "PyTorch", "Docker", "Kubernetes"],
  "加分项": ["熟悉 Kubernetes"]
}
```

后处理不会照单全收 `必备技能`。它会重新从原文的章节证据判断 Kubernetes 只出现在加分项，因此不应进入硬性缺失技能。这是当前系统“生成式抽取 + 确定性证据校正”的核心。

归一化后的关键结果更接近：

```json
{
  "岗位方向": "AI后端开发",
  "必备技能": ["Python", "PyTorch", "Docker"],
  "经验要求": "2年",
  "学历要求": "本科及以上",
  "技能证据": [
    {"技能": "Python", "是否必备": true, "证据来源": ["requirement_evidence"]},
    {"技能": "Kubernetes", "是否必备": false, "证据来源": ["bonus_evidence"]}
  ]
}
```

## 7. 第三阶段：解析失败为什么直接停止匹配

`match()` 检查两个解析结果的 `ok`。任一失败就抛出 `ValueError`，不继续规则评分。

原因是下游规则依赖结构字段。若用空字典兜底，系统很可能得出“没有必备技能”“没有学历要求”，进而给出虚假的乐观分数。显式失败比静默降级更安全。

当前不足也要说明：错误被合并为 `Failed to parse JD or resume before matching`，没有在产品响应里精确告诉用户是哪一侧失败、原始 JSON 错在哪里。这个是合理的后续可用性优化，但不影响核心计算正确性。

## 8. 第四阶段：规则结果是事实层

规则层依次计算：

1. JD 必备技能、简历技能、命中与缺失；
2. 项目文本是否包含 JD 技能；
3. 方向是 exact、compatible 还是 mismatch；
4. 学历等级是否满足；
5. 年限是否满足；
6. 五个分项和总分；
7. 技能证据和评分策略元数据。

对示例输入，结果大致为：

```json
{
  "岗位方向关系": "compatible",
  "岗位方向匹配": true,
  "命中技能": ["Python", "PyTorch", "Docker"],
  "缺失技能": [],
  "学历匹配": true,
  "经验匹配": false,
  "匹配分项": {
    "方向": 20,
    "技能": 45,
    "学历": 10,
    "经验": 0,
    "项目": 5
  },
  "匹配分数": 80,
  "匹配等级": "较匹配"
}
```

为什么方向可以 compatible：AI 后端与算法平台属于显式白名单方向对；双方上下文都有模型服务/平台信号；共享技能不少于两个；共享技能同时包含 AI 技能 PyTorch 和工程技能 Python/FastAPI/Docker。

为什么项目只有 5 分：当前实现按命中的项目/实习文本条数计数，每条 5 分，上限 10；它不是按项目里命中多少项技能计分。

## 9. 第五阶段：模型只生成解释层

系统将原 JD、原简历和完整 `rule_result` 一起放入 match prompt。模型输出字段是：

- 匹配结论；
- 匹配优势；
- 主要短板；
- 简历优化建议；
- 推荐投递岗位方向。

模型不重新决定 80 分、较匹配、经验不满足。这样把“开放语言生成”限制在更适合它的表达任务上。

若模型把“2 年经验不足”写成“经验满足”，离线评测中的 explanation grounding 会发现冲突；但当前在线 API 并没有在返回前强制拦截解释矛盾，这是需要坦诚说明的边界。

## 10. 返回体为什么保留三类结果

响应同时返回：

```text
jd_parse / resume_parse    模型抽取并归一化后的结构
rule_result                确定性业务判断
analysis                   模型自然语言解释
```

另外还有：

- `analysis_raw_output`：调试模型原始输出；
- `execution.backend`：实际是 transformers 还是 vLLM；
- `execution.parse_mode`：解析并行还是顺序；
- `timings`：JD、简历、解析墙钟、规则、解释、总耗时。

这让前端能够解释结果，也让后端能够定位慢在哪一段。缺点是直接把原始模型输出给客户端会增加响应体并可能暴露不必要细节，若进入正式生产应按 debug 开关控制。

## 11. 三种延迟不要混淆

并行解析时，通常：

```text
jd_parse_seconds + resume_parse_seconds > parse_wall_seconds
```

这是正常现象。前两者是每个任务自身耗时，后者是用户实际等待的墙钟时间。总体近似为：

```text
T_total = T_parse_wall + T_rule + T_analysis + 调度/序列化开销
```

规则计算通常是毫秒级，主要延迟来自三次生成：JD 抽取、简历抽取、解释生成。优化优先级因此应是并行前两次、减少输出 token、启用 vLLM continuous batching，而不是微优化正则表达式。

## 12. 失败场景逐层定位

### 场景 A：接口返回 422

先看请求字段和长度。此时模型根本未运行。

### 场景 B：接口返回 503 模型加载失败

检查模型路径、adapter 路径、GPU 显存、vLLM 服务地址。`/health` 中 loaded=false 可以佐证。

### 场景 C：返回 400 且提示解析失败

检查 `raw_output` 是否缺括号、是否被截断、`max_new_tokens` 是否过小、response format 是否生效。

### 场景 D：技能命中错误

依次看：原文 → parse 原始输出 → 归一化必备技能 → 技能证据 → 简历技能集合。不要直接修改分数权重。

### 场景 E：规则正确但解释错误

看 `rule_result` 与 `analysis` 差异，这是生成解释层的问题；可通过 preference 数据或在线 grounding guard 改进，不应改规则事实迎合解释。

## 13. 面试口述模板

> 一次匹配不是把两段文本交给模型让它直接打分。API 先把 JD 和简历分别解析为结构化字段，在 vLLM 下两次解析可以并行；随后规则层用原文证据重新确认必备技能，计算方向、技能、学历、经验和项目分项；最后把规则结果作为事实输入，让模型只负责生成解释与建议。响应保留解析层、规则层、解释层和各阶段耗时，所以错误可以定位到具体层，而不是只看到一个不可解释的总分。

## 14. 连续追问

### 为什么需要三次模型调用，不能一次完成

一次调用成本低，但抽取、判断、解释耦合后，无法确定错误来源，也无法让规则结果稳定复用。当前任务规模下，可诊断性比省一次调用更重要。真正优化延迟时，先并行两次抽取，再考虑小模型抽取或缓存，而不是回退到不可审计的一次性打分。

### 为什么规则层还需要原文，结构化结果不够吗

模型可能把加分项技能错放进必备技能。规则层用原文章节证据重新判定 required 与 bonus；方向兼容也需要双方职责和项目上下文，不能只看两个短标签。

### 这个架构最大的未完成点是什么

真实用户结果闭环尚未建立；分数仍是未校准启发式；在线解释还没有强制 grounding 拦截；vLLM 的吞吐与显存收益尚缺当前环境基准。这些边界比继续添加页面功能更重要。
