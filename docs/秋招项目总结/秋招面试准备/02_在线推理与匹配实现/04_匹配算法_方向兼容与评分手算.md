# 匹配算法、方向兼容与评分手算

本章不把“规则引擎”当黑盒，而是给出输入集合、每个布尔条件、分数公式、边界样本和当前局限。面试时可以直接在白板上推导。

对应源码：

- `src/jobmatch_tune/match/rule_engine.py`
- `src/jobmatch_tune/match/scoring.py`
- `src/jobmatch_tune/match/direction_compatibility.py`

## 1. 规则结果的输入和输出

输入不是只有两个结构化对象，还包括两段原文：

```python
compute_match_rule_result(
    jd_data,
    resume_data,
    jd_text=jd_text,
    resume_text=resume_text,
)
```

原文用于：

- 校验 JD 必备技能证据；
- 从简历中补技能识别；
- 提取简历真实年限；
- 给方向兼容提供职责/项目语境。

输出包括结论、过程证据和策略元数据，而不仅是总分。

## 2. 技能集合如何构造

令：

```text
J = JD 中具有 requirement evidence 的标准技能集合
R = 简历核心技能 + 项目/实习/原文中识别的标准技能集合
M = J ∩ R
D = J - R
```

技能比较使用规范化后的 canonical name，不是模糊语义相似度。例如 `postgres` 可映射到 `PostgreSQL`，OCR 的 `Py thon` 可映射到 `Python`。

当前明确不做的事情：因为候选人会 TensorFlow 就自动认为会 PyTorch；因为会 Docker 就认为会 Kubernetes。这些属于可迁移能力，不是事实上的技能命中。若要展示，可以作为解释层建议，不能混进硬技能交集。

## 3. 技能分公式

权重为 45：

```text
S_skill = round(45 × |M| / |J|),  当 |J| > 0
S_skill = 20,                     当 |J| = 0
```

为什么没有必备技能时给 20 而不是 45：缺少要求不应被解释为全部满足，否则信息不完整的 JD 会获得不合理高分；给中性偏低的 20，表达“无法充分判断”。

手算：

```text
J = {Python, PyTorch, Docker, Kubernetes}
M = {Python, PyTorch, Docker}
|M| / |J| = 3/4
S_skill = round(45 × 0.75) = round(33.75) = 34
```

Python 的 `round` 是银行家舍入，但在该分母组合下可能产生与“传统四舍五入”不同的 `.5` 边界。当前测试以实现为准；若对外宣称精确公式，需要明确舍入语义。

## 4. 方向不是字符串相等

系统先把岗位方向映射为最小叶子类别。例如：

```text
“算法平台工程师” → algorithm_platform
“模型推理服务”   → model_serving
“AI 后端开发”    → ai_backend
“后端开发”       → backend
```

匹配关系有三种：

```text
exact       两侧落在同一叶子
compatible  叶子不同，但满足显式跨方向证据
mismatch    其他情况
```

`exact` 和 `compatible` 当前都令 `direction_match=True`，都获得完整 20 分。系统保留关系字段，前端和评测仍能区分两者。

## 5. 方向叶子如何结合上下文细化

宽泛的“算法”或“后端”可以被职责上下文细化：

- “算法”且出现模型服务、在线推理、平台 API 等信号，可落到 `algorithm_platform`；
- “后端”且上下文出现模型/AI/推理平台信号，可落到 `ai_backend`。

这防止岗位标题写得宽泛而职责实际很具体。但细化只对少数已知方向开放，没有做一个庞大职业本体。

## 6. AI 平台方向兼容的四个同时条件

两个方向被判为平台类 compatible，必须同时满足：

```text
1. 方向叶子对在 PLATFORM_PAIRS 白名单
2. 共享技能数量 >= 2
3. 共享技能里至少有一项 AI 技能
4. 共享技能里至少有一项工程技能
5. JD 与简历上下文两侧都出现平台信号
```

AI 技能集合包括 PyTorch、TensorFlow、CUDA、Transformers、RAG、Agent；工程技能集合包括 Python、FastAPI、Docker、Kubernetes、Linux、Go、Java。

注意实际是五项条件，其中“技能证据”在代码中合并成 AI 交集和工程交集两个布尔判断。

### 正例

```text
JD 方向：模型服务
简历方向：AI 后端
共享：PyTorch, Python, FastAPI
双方上下文：都有在线推理/模型服务
```

结果 compatible。

### 反例一：只有标题相近

```text
JD：算法平台
简历：后端开发
共享：Python
```

共享不足两项，也没有 AI + 工程组合，结果 mismatch。

### 反例二：技能重叠但职责不同

```text
JD：模型服务
简历：普通后端
共享：Python, Docker, Linux
简历项目没有模型服务/平台信号
```

没有两侧平台语境，结果 mismatch。

### 反例三：只有 AI 技能

```text
共享：PyTorch, TensorFlow
```

没有工程技能交集，不能证明候选人具备服务平台能力。

## 7. 另外两类显式兼容

### 算法工程 ↔ AI 应用

要求共享技能至少两项，且双方上下文都有 RAG、Agent、LLM 应用或工作流等应用落地信号。

### 数据工程 ↔ 后端

要求共享技能至少两项，且双方上下文都有数据平台、ETL、Flink、Spark、数仓或数据服务信号。

为什么只实现三类：这些是项目数据中观察到、语义可说明的高频边界。继续扩张成全职业兼容图会过度设计，而且没有足够 Gold 支撑。

## 8. 学历匹配算法

学历映射为有序等级：

```text
中专 1 < 大专 2 < 本科 3 < 研究生/硕士 4 < 博士 5
```

JD 要求中出现“优先”时，required rank 直接按 0 处理，即不作为硬门槛。例如“硕士优先”不是“必须硕士”。

```text
education_match = JD rank == 0 or Resume rank >= JD rank
S_education = 10 if match else 0
```

局限：没有区分“本科及以上”与“全日制本科”，也没有学校层次和专业适配。这是有意避免把争议性条件编码进硬规则。

## 9. 年限提取算法

支持阿拉伯数字和中文数字：

```text
2年、两年、三年、三至五年、3-5年
```

区间要求取下界。例如 3～5 年要求按至少 3 年判断。

过滤规则避免把日期当经验：

- “2023 年毕业”被排除；
- “25 年校招”被识别为届别而非 25 年经验；
- 只保留 1～50 年的合理时长。

匹配公式：

```text
experience_match = JD years == 0
                   or (Resume years > 0 and Resume years >= JD years)
S_experience = 15 if match else 0
```

这里有一个重要保守性：JD 要 2 年，简历没抽到明确年限时，不能因为有多段项目就猜成满足。

## 10. 项目分如何计算

把简历的项目经历和实习经历逐条扫描，只要某条文本包含任一 JD 必备技能，就算命中一条项目证据。

```text
S_project = min(10, 5 × matched_project_count)
```

这只是粗粒度证据，不衡量项目深度、个人贡献、效果指标，也不区分项目与技能的相关强度。它在启发式总分中权重仅 10，避免过度放大。

## 11. 总分与等级

默认权重：

| 分项 | 满分 |
|---|---:|
| 方向 | 20 |
| 技能 | 45 |
| 学历 | 10 |
| 经验 | 15 |
| 项目 | 10 |
| 总计 | 100 |

等级阈值：

```text
score >= 85  → 高匹配
score >= 65  → 较匹配
score >= 45  → 基本匹配
否则         → 低匹配
```

策略类初始化时会检查：权重非负、总和等于 100、阈值严格递减、无技能默认分不越界、校准状态必须是 `heuristic`。这能防止配置被无意改坏。

## 12. 完整手算案例一：较匹配

```text
方向：compatible                         20
JD 必备 4 项，命中 3 项                  34
学历：本科要求，候选人本科                10
经验：要求 2 年，候选人明确 1 年           0
项目：1 条项目命中 JD 技能                 5
总分                                      69
等级                                  较匹配
```

总分 69 不等于录用概率 69%。它只是当前策略下的相对启发式分数。

## 13. 完整手算案例二：无必备技能的 JD

```text
方向 exact                              20
JD 未解析出 required skills             20
学历无硬要求                            10
经验无硬要求                            15
项目因 JD 技能为空                        0
总分                                    65
等级                                  较匹配
```

这个例子揭示一个边界：信息极少的 JD 也可能到 65。原因是学历和经验无要求被视为满足。产品上应同时展示“JD 信息完整度不足”，而不是只看等级。当前规则结果没有专门的信息完整度分，这是合理的下一步而非继续调权重。

## 14. 完整手算案例三：方向错但技能多

```text
方向 mismatch                            0
技能 5/5                                45
学历满足                                10
经验满足                                15
两条项目                                10
总分                                    80
等级                                  较匹配
```

这说明当前是加权求和，不存在“方向错直接封顶”的 hard gate。是否合理取决于产品语义：技能高度可迁移时 80 可能有解释空间；如果产品把方向视为绝对门槛，就需要增加封顶规则。

在没有真实投递 outcome 和足够边界 Gold 前，不应凭直觉增加 hard gate。面试时主动指出这个案例，比把算法说成完美更可信。

## 15. 复杂度分析

设 JD 标准技能数为 `m`，简历技能数为 `n`，项目/实习条数为 `p`。

- 技能命中使用键集合，约 `O(m+n)`；
- 项目匹配逐项目扫描 JD 技能，约 `O(p×m×文本匹配成本)`；
- 方向、学历和年限正则相对输入长度线性；
- 总体远小于模型生成成本。

因此系统性能瓶颈不在评分规则，没必要引入向量数据库或分布式规则服务。

## 16. 为什么分数写着“未校准”

当前权重和阈值来自业务启发式及回归样本，不是用真实录用/面试结果拟合的。要把分数解释为概率，至少需要：

1. 大量真实 JD—简历对；
2. 清晰且相对一致的结果标签；
3. 时间切分或公司/岗位实体切分；
4. calibration curve、Brier score 或 ECE；
5. 监控岗位分布漂移。

在这些条件缺失时，最诚实的产品文案是“匹配参考分”，而不是“成功率”。

## 17. 最值得增加的测试边界

- `round(45*k/n)` 的所有小分母边界；
- 同一技能只出现在加分项；
- `C` 不命中 `CUDA`，`R` 不命中普通单词；
- “25 年校招”不算 25 年经验；
- “硕士优先”不作为硬门槛；
- compatible 缺任一条件都退化为 mismatch；
- 方向 mismatch 但总分仍高的产品解释；
- required skills 为空时的信息完整度提示。

## 18. 面试口述模板

> 规则分由方向 20、技能 45、学历 10、经验 15、项目 10 构成，目前明确标记为未校准启发式。技能只计算 JD 任职要求中有原文证据的项；方向不是字符串相等，而是 exact、compatible、mismatch 三态，跨方向兼容必须同时满足白名单方向对、至少两项共享技能、AI 与工程技能组合以及双方职责信号。规则输出还携带证据和分项，所以我能手算每一分，也能指出方向错但加权总分仍偏高等边界，而不会把它包装成录用概率。
