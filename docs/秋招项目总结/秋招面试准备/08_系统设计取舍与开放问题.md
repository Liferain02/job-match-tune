# 系统设计取舍与开放问题

## 一、为什么是 LLM + Rule，而不是纯 LLM

纯 LLM 的优势是表达灵活、能理解上下文；缺点是同一输入可能漂移、硬条件不透明、错误难定位。纯规则的优势是稳定；缺点是无法从多样文本抽取所有字段。

当前分工是：

- LLM：非结构化文本→结构化候选；规则事实→自然语言解释。
- Deterministic Layer：JSON、canonicalization、evidence boundary、方向兼容、硬条件和等级。

这是一种 semantic compiler 思路：模型负责解析，normalization 负责语义约束，rule engine 负责执行，解释模型负责呈现。

## 二、为什么不是 Embedding 相似度

Embedding 适合语义召回，但一个高相似简历仍可能不满足三年经验或学历要求。它还能把“负责 Kafka 平台”与“必须掌握 Kafka”都映射成相近向量，无法单独承担硬门槛。

如果未来有大量岗位，可在规则前增加 embedding candidate retrieval，缩小候选范围；最终硬条件仍要单独判断。当前单个 JD/Resume 对不需要为召回引入向量库。

## 三、为什么不让 LLM 自己解释并打分

若同一个生成同时给分和解释，解释往往会反向合理化模型自己的结论。把 Rule Result 注入 Prompt 后，模型只能在已知事实边界内组织语言；Evaluator 还能检查是否违背规则。

代价是系统有三次生成调用，延迟增加。当前选择可信度优先于极致延迟。

## 四、为什么一次匹配要三次生成

JD/Resume 解析分别有独立 schema，利于单任务训练、缓存和错误定位；规则必须等两侧完成；解释又依赖规则结果。把三步合并为一次 Prompt 会减少调用，但丢失中间可观测性和确定性决策边界。

若产品规模扩大，可以缓存相同 JD/Resume 的 parse，真正降低重复成本，而不是牺牲架构分层。

## 五、为什么后处理不算“作弊”

产品评测对象本来就是整条流水线，不是裸模型。只要同时报告 Raw 和 Product Final、规则不读取 Gold 标签、后处理是通用且冻结的，normalization 就是正常工程组件。

作弊发生在：根据测试答案写样本 ID 特判、看完 Gold 后仍声称 blind、只报最终层掩盖 raw 退化。项目通过三层评测和 regression-after-inspection 避免这些问题。

## 六、为什么 direction compatible 不直接打折

当前 `DirectionDecision.matches` 对 exact 和 compatible 都返回 true，方向分均为20。原因是现有评分 contract 是布尔方向满足，尚无真实 Pair 支撑给 compatible 设计15分或其他折扣。

系统已经返回 relation 和 evidence，为未来校准保留信息；当前不发明一个看似精确的 discount。这是保守兼容，而不是认为两者完全相同。

## 七、为什么没有技能语义模型

硬技能短词、版本和符号对 precision 很敏感。通用 embedding 可能把 Java/JavaScript、C/C++ 或相邻工具混得过近。当前有界词表更易审计。

未来若真实错例证明 alias 覆盖不足，可以采用两阶段：词表 exact/canonical 优先，embedding 只生成候选，再要求原文证据和阈值，并由人工 Gold 校准。当前没有足够数据支持。

## 八、为什么项目匹配规则较简单

项目命中只是检查项目/实习行是否出现 required skill，每条5分、最多10分。它没有衡量贡献深度、规模和结果。

复杂项目质量模型需要项目级人工标签，否则只会把关键词长度当能力。当前简单规则至少可解释，并且项目分权重较低。

## 九、为什么经验判断很保守

项目数量不等于工作年限，实习描述也不能自动等于三年经验。规则只接受明确年数，并过滤毕业年份、届别等日期。

这可能让真实有经验但简历没写年限的人被判不满足。产品建议应提示“缺少明确年限证据”，而不是断言候选人没有经验。当前布尔字段仍较粗，是未来有真实标签后可改善的点。

## 十、为什么 API 没有异步队列

当前是单用户/低并发演示，单条请求可以同步完成。引入 Celery/Redis 需要任务 ID、状态机、重试、幂等、结果存储和清理，增加大量非核心复杂度。

只有扫描大文件、批量几百条、多人并发或超时成为真实需求时，才应改异步任务。届时优先把文件提取和模型推理解耦，而不是先拆所有服务。

## 十一、为什么没有自动后端降级

vLLM 不可达时自动切 Transformers 看似高可用，但会造成延迟、并发、结构输出能力和模型版本悄悄变化，评测不可追溯。当前失败显式暴露，运维决定是否切换。

生产环境可以做受控 fallback，但必须返回实际 backend、记录请求版本并对两个后端做同质量基线。

## 十二、为什么不用容器锁死全部环境

前端可由 package-lock 精确锁定；Python 上层用 constraints 限定兼容范围。PyTorch、CUDA、bitsandbytes、vLLM 与 GPU driver 强绑定，跨机器复制单一 wheel 组合未必可用。

当前方案记录验证快照并按目标机器选择底层 CUDA wheel。若进入生产部署，再为确定硬件制作镜像和 SBOM；当前不为了形式上的 lock 牺牲可安装性。

## 十三、为什么没有 CI

仓库已有517个本地测试、Ruff、compileall、shell syntax 和前端 build/smoke。没有 CI 是明确技术债，但当前用户要求不扩展 CI，且 GPU/模型资产不在仓库，完整流水线不能在普通 runner 重现。

如果项目进入协作维护，第一步 CI 应只跑 CPU 单测、Ruff、shell 和前端 build；GPU evaluation 作为手工/定时受控任务，而不是把14B模型塞进每个 PR。

## 十四、如果真正产品化，优先级是什么

真正产品化的前提不是先拆服务，而是先有授权用户与 outcome。之后按风险排序：

1. 合规、数据保留和用户删除机制。
2. 账号、鉴权、配额和审计日志。
3. 对象存储、恶意文件隔离和异步 OCR。
4. parse 缓存与任务队列。
5. vLLM 容量规划、超时和 fallback。
6. 可观察性、成本和质量监控。
7. 人工反馈闭环和模型/规则版本实验。

当前没有这些真实需求，因此只作为系统设计回答，不应在仓库里提前实现。

## 十五、如果获得真实 Pair，下一步怎么建模

先不急着训练一个 end-to-end scorer。应先：

1. 定义 Pair 标签：是否匹配、推荐等级、原因、标注者一致性。
2. 按 JD/Resume entity 和时间切分。
3. 分析方向、学历、经验和技能的条件分布。
4. 用现有规则作为 baseline，测 calibration 和错误类型。
5. 再比较 logistic/ranking model、cross encoder 或 LLM judge。
6. 最终输出需要概率时做校准和置信区间。

这样才能判断复杂模型是否真的优于可解释规则。

## 十六、如果获得真实用户反馈，如何评估建议

Advice Validity 不能只让另一个 LLM 打分。可以设计：

- 用户是否采纳建议；
- 简历字段完整度变化；
- 同类岗位投递回应率；
- 随机或准实验对照；
- 按建议类型分层分析；
- 防止岗位和用户选择偏差。

这是产品研究问题，远超当前离线一致性指标。

## 十七、可观测性应该记录什么

若部署，应记录而不泄漏原文：请求 ID、模型/adapter/规则版本、输入类型和长度、backend、parse mode、各阶段延迟、JSON 成功、错误码、token usage、GPU 容量、用户反馈。原始简历默认不进入日志。

当前 API 已返回 backend、parse mode 和 timings，benchmark 记录 GPU 前后快照；持久化审计尚未实现。

## 十八、如何回答 CAP、微服务等泛化追问

不要硬套分布式理论。当前是单进程原型，没有跨节点一致性问题。可以说明若拆为异步服务，将需要考虑任务幂等、至少一次投递、模型版本一致性和结果存储；但这些不是当前已实现能力。

面试中区分“当前实现”“如果规模化的设计”非常重要。

## 十九、开放问题的优先顺序

最高优先级但外部阻塞：真实数据、Blind Gold V2、outcome。  
中优先级且有真实需求再做：vLLM benchmark、浏览器 E2E、缓存、异步文件。  
低优先级：更大 taxonomy、embedding、复杂项目 scorer。  
明确不做：为简历展示而造微服务和继续 synthetic 训练。

## 二十、系统设计总结

JobMatchTune 的架构价值不在组件数量，而在边界：模型和规则边界、离线和在线边界、训练和评测边界、工程能力和外部证据边界。能把这些边界解释清楚，比画一张包含十个中间件的图更有说服力。
