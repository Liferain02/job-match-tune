# 测试策略、验证矩阵与质量门禁

## 一、测试目标

JobMatchTune 的测试不只验证“函数能跑”，还要保护语义边界：什么算必备技能、短技能边界、方向兼容需要哪些证据、训练集是否泄漏、旧 Gold 是否被覆盖。模型权重和大文件不进入常规测试，因此需要把确定性逻辑、模型接口和真实 GPU 评测分层。

当前完整本地结果是517个 Python tests passed，另有 Ruff、compileall、全部 shell syntax、前端 build 和 smoke。

## 二、测试金字塔

### 纯函数单元测试

数量最多、速度最快，包括文本清洗、学历年限、技能 canonicalization、方向策略、评分、指标和 hash。它们应同时写正例与反例。

### Builder/Audit 测试

用小型内存 JSON rows 验证数据选择、source group、entity split、preference、readiness 和 Gold audit。重点是不访问网络、不加载模型。

### Service Helper 测试

测试 FastAPI service 的请求编排、文件提取、上传校验、批量行为和 backend mode；通过 fake sender/model 避免14B加载。

### 静态前端 Smoke

`tests/frontend_report_smoke.mjs` 验证 Vue 从本地包导入、报告关键字段和无 CDN 依赖；Vite production build 验证模块与 CSS 能打包。

### GPU/产品回归

真实14B生成、adapter A/B、vLLM吞吐和浏览器点击不属于日常单测，使用独立脚本和冻结报告。不能因为单测517通过就声称模型质量通过。

## 三、按领域的测试矩阵

| 领域 | 代表测试 | 核心不变量 |
|---|---|---|
| JD 规则 | `test_jd_field_rules.py` | 学历/年限/方向/技能边界正确 |
| JSON 后处理 | `test_postprocess_json.py` | 格式修复不编造，字段稳定 |
| OCR 技能 | `test_skill_canonicalization.py` | 已知断词恢复、假阳性拒绝 |
| JD Evidence | `test_jd_skill_evidence.py` | 只有 requirement 成为 required |
| Match | `test_match_rule_engine.py` | 集合、学历、年限、项目正确 |
| Direction | `test_direction_compatibility.py` | exact/compatible/mismatch 有证据 |
| Score | `test_match_scoring.py` | 权重100、阈值有序、分项有界 |
| Explanation | `test_explanation_grounding.py` | 矛盾和无证据陈述被发现 |
| Upload | `test_upload_validation.py` | 内容与扩展匹配、坏文件前置拒绝 |
| Resume | ingest/OCR/privacy tests | 文件提取、OCR fallback、PII处理 |

## 四、语义测试如何设计

### 正例与反例成对

只测试 `Py test→Pytest` 会鼓励过宽规则；必须同时测试普通 `pytest-like`、Postman、短字符 spaced text 不匹配。

方向 compatible 也要同时测试：双侧平台 signal+技能满足；只有一侧 signal；只有一个共享技能；算法与普通后端。没有反例的 taxonomy 很快退化成 alias 表。

### 测属性而非样本 ID

规则测试构造最小文本，不引用 `match_eval_001` 等 Gold ID。这样证明修复是一般语义，而不是 memorization。

### 保护历史契约

新 canonicalization 模块上线后，全量测试发现旧 ASCII boundary 对 C 的约束丢失。专项测试通过不够，模块迁移必须跑全仓库。

## 五、数据 Builder 测试

Builder 测试要固定 seed 并检查结构性质，而不是把整份输出 snapshot 写死。

例如 Match Entity Split 应断言：

- 每个 JD entity hash 只属于一个 split；
- 每个 Resume entity hash 只属于一个 split；
- Pair 的两侧来自同一 split；
- 正负构造不越过分区；
- educational source cap 生效。

MultiTask 测试检查 source group round-robin、任务计数、content hash 去重和 split metadata。

## 六、Audit 和 Gate 测试

Audit 工具本身也可能出错，因此测试需要构造每种失败：

- missing annotation；
- duplicate ID/group/Pair；
- train Pair overlap；
- 单侧 JD/Resume overlap；
- difficulty tag 缺失；
- PII 命中；
- pipeline stale；
- synthetic provenance 过高；
- 条件分布单侧。

Readiness 测试不只断言 false，还应检查失败原因进入 report，使开发者知道是外部数据阻塞还是代码产物 stale。

## 七、上传测试

上传测试使用最小真实结构：

- PDF 至少有合法 `%PDF` 和可解析页结构；
- DOCX 是 ZIP 且包含必要 OOXML entries；
- 图片由 Pillow 编码；
- 文本测试 UTF-8、NUL 和控制字符。

还要测试扩展名与实际内容交叉，如 `.pdf` 文件装 PNG。Mock 解析器可以验证 validation failure 时昂贵 parser 没被调用。

## 八、模型边界如何测试

常规测试不会下载或加载14B。`build_prompt`、response schema 和 parse 函数可以纯函数测试；ModelService 用 fake completion 返回固定 JSON。

真实模型需要独立运行：

1. 固定 model/adapter/config/hash。
2. 固定 Gold 和 generation 参数。
3. 保存逐样本 raw output。
4. 生成三层报告和错误分析。
5. 对比 baseline，不覆盖历史文件。

这样单测负责代码确定性，Gold 负责模型/产品行为。

## 九、前端验证

当前前端有三层验证：

1. package-lock + `npm ci` 保证依赖树。
2. `npm run build` 保证 Vue/Vite 模块可生产打包。
3. Node smoke 检查报告与依赖关键契约。

缺少真实浏览器 E2E，所以不能证明文件选择、点击、下载和跨浏览器行为。当前通过人工浏览器测试补足演示链；若进入协作开发，优先增加 Playwright 的最小 happy path 和 API error path。

## 十、Shell 和启动脚本验证

对所有 `.sh` 执行 `bash -n`，能发现语法问题但不能证明进程生命周期正确。启动脚本还需要人工/集成验证：端口占用、PID、健康等待、vLLM失败清理、日志和停止安全。

`stop_project.sh` 会比对进程命令和项目路径，避免 PID 文件过期后误杀其他进程；这类破坏性行为必须有额外人工谨慎。

## 十一、代码质量检查

- Ruff：未定义变量、常见 bug、语法与部分风格。
- compileall：全 src 可编译。
- `git diff --check`：尾随空白和冲突标记等 patch 问题。
- Markdown link/path audit：保证文档引用存在。

这些检查不能替代语义测试，但能用低成本拦截基础错误。

## 十二、为什么没有把测试数当覆盖率

517是执行用例数量，不是行覆盖率，也不代表所有分支。Pytest 参数化还会让测试函数数和执行 case 数不同。项目没有冻结 coverage percentage，因此简历只写“517个本地测试通过”，不写“覆盖率100%”。

## 十三、Gold 文件保护

正式回归前后计算 Gold、历史 report、历史 predictions 和 isolation audit SHA256。新回归写日期化新路径；重放器记录 source predictions hash 和 generation reused。

这种保护比“测试通过”更直接证明历史证据没有被覆盖。当前四个冻结 hash 在语义回归前后保持不变。

## 十四、一次完整验证命令

```bash
conda run -n tune-demo ruff check .
conda run -n tune-demo pytest -q
conda run -n tune-demo python -m compileall -q src
find scripts -type f -name '*.sh' -print0 | xargs -0 -n1 bash -n
git diff --check
npm ci --prefix frontend
npm run build --prefix frontend
node tests/frontend_report_smoke.mjs
```

这不启动训练，也不运行14B生成。真实模型回归必须显式执行，并写新报告。

## 十五、测试失败如何处理

先判断是代码回归、过时测试还是环境缺失，不能为了全绿直接删断言。短技能 C 失败属于旧业务 contract 被破坏，正确做法是修通用 boundary 并补专项测试。

若 GPU/vLLM 不可用，应把真实 benchmark 标记 pending，而不是 mock 一个吞吐数字。若 Gold 已被查看，应改变评测语境，而不是只改报告名称。

## 十六、面试标准回答

> 我的测试分三层：纯函数和数据 builder 用517个 CPU 单测保护确定性语义；前端和脚本用生产构建、smoke 和语法检查；真实模型用冻结 Gold 做三层产品回归。单测不加载14B，Gold 回归不覆盖历史文件，两者分别解决代码稳定和模型行为问题。当前还缺浏览器 E2E、CI 和真实 vLLM A/B，这是已知而非隐藏的边界。
