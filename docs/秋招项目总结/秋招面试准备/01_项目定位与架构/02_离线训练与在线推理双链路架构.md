# 离线训练与在线推理双链路架构

## 一、为什么必须画成两条链

训练系统和在线服务共享 schema、Prompt、模型与评测规则，但它们不是同一个请求链。如果把“采集→SFT→DPO→API”画成一条线，面试官很容易追问：用户每发一次请求难道都重新训练吗？正确架构是离线产出可晋级 adapter，在线服务只加载冻结资产。

## 二、离线链路

```text
Source Registry / DB / 外部文件
          ↓
许可、用途、来源元数据检查
          ↓
文本清洗、隐私处理、规范化、去重
          ↓
JD / Resume / Match Candidate Pool
          ↓
SourceGroup 与 Entity-level Split
          ↓
单任务 SFT messages
          ↓
多任务配比与去重
          ↓
Readiness Gate
          ↓（仅通过时）
Qwen3-14B + QLoRA SFT
          ↓
可选 Preference 构建与 DPO Gate
          ↓（仅通过时）
DPO
          ↓
Raw / Normalized / Product Final 评测
          ↓
Gold、泄漏、绝对阈值与基线回归
          ↓
Adapter 晋级或拒绝
```

### 关键入口

- 数据源配置：`configs/public_*_sources.yaml`、`configs/dataset_registry.yaml`。
- 公开数据导入：`src/jobmatch_tune/crawler/` 与 `dataset/import_public_*_data.py`。
- 数据池重建：`scripts/data/build_current_data_pools.sh`。
- 多任务构建：`dataset/build_multitask_sft_dataset.py`。
- SFT：`train/train_lora.py`。
- DPO：`train/train_dpo.py`。
- Readiness：`eval/report_data_readiness.py`、`eval/assert_training_readiness.py`。
- 产品评测：`eval/run_match_eval.py` 与 `scripts/eval/run_product_adapter_suite.sh`。

## 三、在线链路

```text
浏览器文本或文件
        ↓
Pydantic / Upload Content Validation
        ↓
文件文本提取，必要时 OCR
        ↓
JD Parse ─────────┐
                  ├─ 等待两侧结构结果
Resume Parse ─────┘
        ↓
JSON 提取、字段修复、Schema Normalization
        ↓
Requirement Evidence + Skill Canonicalization
        ↓
Direction / Skill / Education / Experience / Project Rule
        ↓
Heuristic Score + Match Level
        ↓
规则事实注入 Explanation Prompt
        ↓
结构化解释
        ↓
FastAPI Response → Vue ResultPanel / Markdown
```

在线入口在 `src/jobmatch_tune/api/server.py`。模型实例由 `ModelService` 延迟加载并复用，不会每次请求重新加载。

## 四、共享契约

### Prompt 契约

`dataset/templates.py` 同时服务数据构建和推理，包含三个任务：`jd_parse_prompt`、`resume_parse_prompt` 和 `match_prompt`。共享 Prompt 可以降低训练/推理格式漂移，但也意味着修改模板必须触发数据 freshness 审计。

### Schema 契约

`schemas.py` 定义 JD、Resume、Match Rule 和 Match Analysis 的字段。vLLM 路径还通过 `inference/structured_output.py` 把对应 JSON Schema 作为 response format；Transformers 路径依靠 Prompt 和后处理。

### Label Schema

`configs/label_schema.yaml` 保存岗位方向和技能 alias，是离线规则弱标注、在线 canonicalization 和匹配规则的共享词表。共享带来一致性，也带来耦合：词表修改需要同时回归数据和产品。

### 评测契约

训练不直接决定 adapter 是否上线。`run_manifest.json` 记录 Git、配置、数据 hash 和 readiness；评测报告再比较 Raw、Normalized 和 Product Final。

## 五、数据如何跨层变化

以一条 JD 为例：

1. Raw：原网页或 API 返回的标题、描述和 meta。
2. Clean：HTML 去除、空白规范、模板行去除、隐私处理。
3. Normalized Pool：方向、学历、经验、技能弱标签和 source 元数据。
4. SFT：system/user/assistant messages；assistant 是结构化 JSON。
5. Model Raw Output：生成字符串，可能有围栏、杂质或字段错位。
6. Product Normalized：合法 JSON、canonical 技能和 requirement evidence。
7. Rule Result：命中/缺失、方向关系、硬条件和分项。
8. Analysis：只能解释 Rule Result。

任何一层出错都应该保留足够信息定位，而不是只留下最终分。

## 六、组件职责与不做的事情

| 组件 | 负责 | 不负责 |
|---|---|---|
| Crawler/Importer | 获取和映射来源数据 | 证明数据自动可训练 |
| Cleaner/Normalizer | 清洗、格式与弱规则字段 | 生成真实招聘 outcome |
| SFT Model | 从文本生成结构化候选 | 决定最终录用概率 |
| Canonicalization | 有界同义/OCR 收敛 | 全文无界 fuzzy search |
| Rule Engine | 可复查硬条件与启发式等级 | 学习真实招聘决策函数 |
| Explanation Model | 根据事实生成说明 | 覆盖或修改规则结果 |
| Evaluator | 测层级质量和一致性 | 证明建议真的有效 |
| Readiness Gate | 阻止证据不足的训练 | 自动创造缺失数据 |

## 七、为什么采用单体服务而不是微服务

当前运行单元是一个 FastAPI 进程、一个模型后端和一个静态前端。请求规模小，主要复杂度来自模型推理和数据语义，而不是组织边界。拆成“解析服务、规则服务、解释服务、文件服务”会增加部署、序列化、故障定位和版本一致性成本。

只有出现独立扩缩容、不同团队所有权、模型路由或异步长任务时，服务拆分才有明确收益。当前保持单体不是缺少架构能力，而是基于规模的选择。

## 八、模型后端边界

Transformers 后端直接在 API 进程加载 tokenizer、基座和 PEFT adapter。共享模型通过 Lock 串行生成，适合演示和低并发，逻辑简单。

vLLM 后端由独立 OpenAI-compatible server 提供推理。API 使用 BoundedSemaphore 限制并发；JD/Resume 在槽位至少为2时可并行，批量也能受控并发。当前环境没有安装 vLLM，因此只能说“实现了路径和 benchmark harness”，不能宣称吞吐提升多少。

## 九、故障边界

- 输入层失败：返回4xx，不调用 OCR 或模型。
- 单侧解析失败：匹配停止，不生成假完整结果。
- JSON 失败：保留 raw output 和 error，用于诊断。
- 规则异常：作为服务错误暴露，不让 LLM 猜一个替代分。
- vLLM 不可达：当前没有自动切 Transformers，避免后端悄悄变化导致性能和质量不可追溯。
- 批量部分失败：逐项返回状态，保留成功项。
