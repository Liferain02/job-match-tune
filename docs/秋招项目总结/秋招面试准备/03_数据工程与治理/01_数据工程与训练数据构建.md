# 数据工程与训练数据构建

## 一、为什么数据工程是项目主角

结构化招聘任务很容易获得“看起来很多”的数据：抓取几十万 JD、把一份简历改成六个模板、把 JD 与 Resume 自动配对。但这些操作增加的是行数，不一定增加独立事实、标签质量或真实行为证据。

JobMatchTune 后期的核心转变是：不再问“有多少行”，而是同时问来源是否合法、独立实体有多少、标签如何得到、条件分布是否完整、训练与 Gold 是否重叠。

## 二、来源登记和准入

### 数据源清单

公开 JD、Resume、Match 来源分别配置在 `configs/public_job_sources*.yaml`、`public_resume_sources.yaml` 和 `public_match_sources.yaml`。字段应描述来源名、URL/本地文件、格式、许可、处理器和是否启用。

`src/jobmatch_tune/dataset/download_verified_sources.py::verify_or_download_source` 不只下载，还能验证预期 SHA256。这样外部资源变化时不会悄悄污染实验。

### 可访问不等于可训练

网页能打开、文件能下载，只证明技术可达。训练准入还需要：

- 明确许可或允许用途；
- 来源可追溯；
- 不包含不必要 PII；
- 与任务字段兼容；
- 标签来源可信；
- 不与 Gold 或其他 split 泄漏。

未满足的内容只能进入 candidate/quarantine 或研究清单，不能因为样本稀缺就降低门槛。

## 三、JD 数据链路

### 获取

`crawler/` 包含多个官网/API 适配器；原始职位进入 SQLite 或 raw JSONL。数据库层保留来源、标题、正文、抓取时间和 meta。

### 清洗

`preprocess/clean_text.py` 负责：

- HTML 转正文；
- 空白规范；
- 常见模板/boilerplate 去除；
- 重复行去除；
- 必要的隐私掩码。

`src/jobmatch_tune/preprocess/normalize_jd.py::normalize_jd_row` 再根据 `label_schema.yaml` 生成方向、学历、经验、技能等弱结构字段，并写 normalization manifest。

### 去重

`preprocess/deduplicate.py` 同时提供：

- compact fingerprint：确定性重复；
- normalized similarity text；
- character shingles；
- Jaccard similarity：近重复候选。

不能只按岗位标题去重，因为同名岗位在不同公司可能有完全不同要求；也不能只按原始字符串，因为 HTML/空白差异会保留重复。

### 质量分层

JD 组合池由 manual、公开候选、supplemental、weak structured 等来源构成。`build_jd_quality_sft_dataset.py` 根据缺字段、职责/要求串位、方向风险等决定质量层级，部分确定性错误可修复，风险过高则拒绝。

最终 JD SFT 当前是 train 4,240、valid 530、test 530，数量和格式门禁通过；但这不自动让 Resume/Match readiness 通过。

## 四、Resume 数据链路

### 输入形式

简历可能是文本、DOCX、文本 PDF、扫描 PDF 或图片。离线流程用 `resume/ingest.py` 提取，`resume/ocr.py` 处理 OCR sidecar，`resume/normalize.py` 形成统一行结构。

### 隐私

`src/jobmatch_tune/resume/privacy.py::sanitize_resume_text_for_training` 对训练文本去标识；`report_resume_privacy_readiness.py` 检查手机号、邮箱等风险。私有文件放在 Git 忽略目录，去标识化也不能替代数据授权。

### Bootstrap 和模板扩展

为了早期打通 Resume 任务，项目从 JD/结构字段生成了 Resume bootstrap，再生成 original、profile_card、bullets、compact、ocr_like、mixed_cn_en 等形式变体。

这可以教模型适应格式，但不能把每个变体当成新的独立候选人。当前 profile 的关键事实：

| 指标 | 数值 |
|---|---:|
| Resume SFT 行数 | 15,470 |
| 独立 source group | 2,557 |
| 扩展比 | 6.0501 |
| bootstrap 样本 | 15,150 |
| bootstrap source group | 2,525 |
| bootstrap source group 占比 | 98.75% |

因此 `profile_ready=false`。面试重点不是解释为什么15k很大，而是解释为什么它并不代表15k个真实简历实体。

## 五、SourceGroup 的作用

`source_group` 表示同一原始语义实体。一个 Resume 的六个模板、一个 JD 的不同渲染、同一来源记录派生的训练样本必须共享 group。

`src/jobmatch_tune/dataset/build_multitask_sft_dataset.py::sample_task_rows` 先按 group 聚合，每轮从每个 group 取一个样本，再取第二个变体。这防止拥有很多模板的少数 source 挤掉其他来源。

`src/jobmatch_tune/dataset/grouped_split.py::split_linked_samples` 用连通分量思想把存在 source/entity 关联的样本放入同一 split。若 group 数不足3，函数会退化为很小的 train/valid/test，这只适合测试，不适合正式评测。

## 六、Match Pair 的构建

### 为什么需要 Pair

匹配任务的基本观测单位不是独立 JD 或 Resume，而是 `(JD, Resume, label)`。仅有两侧独立数据不能证明真实候选人会投递什么岗位，也不能证明规则等级符合招聘者判断。

### 早期合成策略

`build_match_train_pool_synthetic.py`：

1. 从 JD 构建方向、学历、经验和技能结构。
2. 选择同方向 Resume 作为正候选，不同方向作为负候选。
3. 调用当前规则生成 label。
4. 写入 generator、方向、entity hash 和 split。

合成 Pair 的用途是让模型学输出格式和覆盖主要字段，不应被解释为人类偏好或招聘行为。

### 先分实体再配对

旧风险是配对后随机 split：JD A 可以在 train 与 Resume X 配对，在 test 与 Resume Y 配对；模型见过 JD A 后，test 不再独立。Resume 也有同样问题。

修复后的 `partition_match_entities`：

1. 对 JD 正文生成 entity hash，并按来源家族分层。
2. 对 Resume 去标识文本生成 entity hash，并按方向分层。
3. 独立把两侧实体分为 train/valid/test。
4. 只在同一个 split 内构造正负 Pair。

这阻断了 JD/Resume 节点跨 split，但不能把合成标签变成真实标签。

### 当前 Match 事实

- Pair 总数4,798。
- synthetic 4,798。
- human training pair 0。
- real observed pair 0。
- 显式年限要求样本1,944条，全部为“不满足”。

所以 Match readiness=false 是必然结论。继续生成更多同类 Pair 只会扩大偏差。

## 七、SFT messages 如何构造

JD、Resume、Match builder 最终都写 `messages`：

```json
[
  {"role": "system", "content": "严格基于输入输出 JSON"},
  {"role": "user", "content": "任务 Prompt + 原文"},
  {"role": "assistant", "content": "结构化 JSON 标签"}
]
```

`build_resume_sft_dataset.py` 将一个 source 渲染为多种输入；`build_match_sft_dataset.py` 用 Pair label 生成规则事实和解释目标；`build_multitask_sft_dataset.py` 根据 registry 配置做任务采样和全局 content hash 去重。

训练时 `assistant_only_loss=True`，只对 assistant 响应计算主要损失，避免模型学习复述 system/user 文本。

## 八、Preference 数据

`build_preference_dataset.py` 要求同一 Prompt 下有 chosen 和 rejected。Match chosen 应与人工/规则事实一致；`build_preference_bootstrap_dataset.py` 可以通过删字段、改方向、串字段等方式制造 rejected。

合成 rejected 对格式偏好有用，但无法证明人类更喜欢 chosen。Preference audit 还要检查 prompt hash 不跨 train/valid/holdout。

当前 DPO 数据依赖已 stale，且 DPO 被质量目标显式暂停。即使 readiness summary 中某些旧的 DPO 数量/格式项为 true，`dpo_execution_ready=false` 才是最终执行状态。

## 九、Pipeline Freshness

`dataset/pipeline_freshness.py` 记录上游文件、转换代码和下游产物关系。当前 SFT 链 fresh，但两个 preference 依赖 stale，因此总 `pipeline_fresh=false`、`dpo_pipeline_fresh=false`。

Freshness 解决的是“产物是否由当前输入和代码生成”，不是“数据是否高质量”。一个新鲜的全合成 Match 池仍然不 ready。

## 十、数据问题的面试回答框架

遇到“为什么不多抓数据”时，按四层回答：

1. 法律与用途：是否允许训练。
2. 实体与来源：多少独立 source/entity，而非多少行。
3. 标签证据：人工、观察、弱规则还是合成。
4. 分布与评测：硬条件正负是否完整，是否与 Gold 泄漏。

这个框架比列出更多数据集名称更能体现数据工程能力。

## 十一、当前最合理的数据恢复条件

重新开放训练至少需要一种实质证据变化：

- 一批授权、去标识、来源独立的真实 Resume；
- 人工构造并复核的真实语义 Match Pair；
- 有明确选择依据的 human preference；
- 未参与开发调参的 Blind Gold V2；
- 用户投递反馈或招聘 outcome。

如果只有更多模板、更多规则配对或更多同来源 JD，不应重启训练。
