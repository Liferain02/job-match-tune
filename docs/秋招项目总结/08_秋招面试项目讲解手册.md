# 秋招面试项目讲解手册

## 1 分钟版本

我做了一个中文技术岗位的人岗匹配系统。它不是让大模型直接给一个不可解释的分数，而是先用 Qwen3-14B 分别把 JD 和简历解析成统一结构，再由确定性规则检查方向、技能、学历、年限和项目证据，最后让模型基于规则结果生成解释。工程上支持 PDF、DOCX、图片 OCR、FastAPI、Vue 页面，以及 Transformers 和 vLLM 两种推理后端。

我投入最多的其实是数据和评测可信度。Match Pair 是二部图，随机切 Pair 会泄漏同一个 JD 或简历，所以我改成先按实体分组切分、再配对；同时把格式/OCR 变体归到同一来源组。最终建立了 25 条人工复核且五类训练重叠为 0 的 Gold，Product Final 的技能 F1 约 0.99、等级和方向准确率 0.96。审计也发现现有 Match Pair 全是合成、Resume 来源高度集中，所以 readiness 会主动阻止新训练。

## 3 分钟版本

项目起点是 JD 结构化，后来扩展到简历和匹配。我把产品边界控制在三个核心任务：JD 解析、简历解析、可解释匹配。输入可以是文本或文档，扫描 PDF/图片先做 OCR；两侧文本通过同一 14B adapter 的不同模板生成结构化 JSON，随后做 schema 校验、JSON 修复和证据约束归一化。

匹配没有直接交给模型裁决。规则引擎按方向 20、技能 45、学历 10、年限 15、项目证据 10 计算，并保留命中、缺失和硬条件证据。模型最后只把这份结果解释成用户可读内容。这样既使用模型处理表述多样性，也让核心决策可复查。

训练使用 4-bit NF4 QLoRA，SFT 采用 assistant-only 的 DFT loss；DPO 处于 SFT 之后，但历史偏好指标虽然好，没有带来独立产品收益，所以目前暂停。推理方面，默认 Transformers 用锁串行以保护单卡显存，vLLM 才会并发解析 JD 和简历。

最大的坑是数据看起来多但不独立。简历格式变体曾虚增来源；Match 随机切 Pair 导致同一实体跨集合，负样本复用还形成巨型连通分量。我重建了 source group、实体分组切分、五类泄漏审计和八维 readiness。最后 Gold V1 有 25 条人工复核，最终技能 F1 约 0.99、等级/方向 0.96；但 Resume 98.75% 来源组来自 bootstrap，4,798 个 Match Pair 全合成，所以系统现在会拒绝继续训练。这个项目最核心的能力不是调了多少模型参数，而是能识别一个高分是否真的可信。

## 10 分钟版本结构

1. 需求：非结构化文本难比较，直接生成 Match 分不可解释。
2. 架构：模型抽取、规则裁决、模型解释；展示数据流和职责边界。
3. 模型：Qwen3-14B 4-bit QLoRA、SFT/DFT，DPO 为什么暂停。
4. 推理：Transformers 与 vLLM 的资源/吞吐取舍，文件和 OCR。
5. 数据：JD 分层、Resume 隐私与来源组、Match 合成 Pair。
6. 泄漏：二部图、先切实体再配对、Gold 五类重叠。
7. 评测：Raw/Normalized/Product Final 与冻结指标。
8. 复盘：旧 64 条失效、格式变体伪多样性、DPO 无业务收益。
9. 产品判断：为什么不追 100 分、不继续合成、不做平台化。
10. 下一条件：新合法、独立、去标识化 Resume/Match 数据通过 readiness。

## 30—40 分钟深挖路线

- 0—5 分钟：现场用一份 JD 和简历展示输入、结构化字段、匹配证据、解释和报告。
- 5—12 分钟：沿 API 请求讲模型加载、模板、Pydantic、后处理、规则引擎和解释生成。
- 12—20 分钟：画 JD—Resume 二部图，解释 pair split 泄漏和 source group 修复。
- 20—27 分钟：展示三层评测、Gold 冻结哈希和三个具体错例。
- 27—33 分钟：讲 QLoRA 参数、SFT 与 DPO，以及为什么训练指标不能代表产品。
- 33—38 分钟：讲 readiness、隐私/许可、主动停止训练的产品决策。
- 38—40 分钟：总结可迁移能力：结构化 LLM、pairwise 数据治理、可信评测和工程取舍。

## 项目问答（50 题）

### 产品与架构

1. **为什么做这个项目？** 传统关键词匹配不理解表述差异，直接让 LLM 评分又不可审计。我希望验证一个混合系统能否同时获得语义抽取能力和稳定业务边界。

2. **产品核心用户是谁？** 当前是求职者、招聘人员和技术评审者的单机分析工具，不是完整 ATS；核心价值是快速定位匹配证据和差距。

3. **为什么不直接让 LLM 输出匹配分？** 方向、学历、年限和技能命中是需要复查的硬条件。直接生成容易漂移、难定位错误，也不能保证解释与结论一致。

4. **混合架构如何分工？** LLM 负责从异构文本抽取结构；后处理负责格式与证据归一；规则负责裁决；LLM 最后只负责表达规则结论。

5. **规则引擎是不是太简单？** 当前目标是可解释原型，不是拟合真实录用概率。100 分启发式足以暴露证据，真实 Pair 到来后才有资格校准权重。

6. **为什么规则后还要生成解释？** 用户需要知道如何行动。结构化结果适合机器和审计，解释层把命中、缺失和硬条件组织成人能读懂的报告，但不得重新裁决。

7. **有哪些核心流程？** JD 解析、简历解析、人岗匹配三条；批量和文件只是输入形式，不单独扩业务概念。

8. **为什么没做账号、职位库和工作流？** 当前风险在数据真实性与评测，不在平台功能。提前做多租户和微服务不会提高匹配可信度，属于过度设计。

9. **产品现在能上线吗？** 能做受控演示和研究验证，不能作为公开生产招聘决策系统；缺鉴权、配额、安全上传、线上监控和更大规模真实评测。

10. **最重要的产品指标是什么？** 当前是独立 Gold 上的技能 F1、等级/方向 EM、硬条件准确性和解释一致性，同时看 readiness；不能只看一个总分。

### 模型、训练与推理

11. **为什么选择 Qwen3-14B？** 中文和结构化生成能力较强，14B 在单卡 QLoRA/4-bit 条件下仍可运行；项目早期小模型用于验证，之后把主路径收敛到 14B。

12. **QLoRA 如何配置？** 4-bit NF4、double quant、bf16 计算；LoRA r8、alpha16、dropout0.05，覆盖 attention 和 MLP projection，主 SFT 一轮、学习率 1e-4。

13. **为什么不用全参数微调？** 数据量和硬件都不支持全参成本，任务主要是学习模板和领域结构；QLoRA 足以验证增量能力，也便于保留底座。

14. **DFT 和 NLL 有什么区别？** 它们优化权重定义不同，loss 绝对值不可直接横比。历史实验耗时和业务结果接近，所以不能从 loss 大小得出谁更好。

15. **SFT 和 DPO 的顺序是什么？** 通常先 SFT 建立任务能力，再 DPO 学 chosen/rejected 偏好。没有稳定 SFT 或可靠偏好对时，直接 DPO 没有清晰基准。

16. **为什么暂停 DPO？** 历史 reward accuracy 0.9297，但独立业务评测没有提升，偏好数据真实性也不足。继续训练只会优化代理目标。

17. **DPO 什么时候恢复？** 新偏好数据有合法来源和人工/真实证据、SFT readiness 通过、预先定义独立 Gold 主指标，而且能与 SFT baseline 做受控 A/B。

18. **Transformers 还是 vLLM 更好？** 低并发单卡演示用 Transformers 更简单稳妥；服务和批量吞吐用 vLLM 更合适。两者的结构化业务逻辑相同，差别主要是调度和运行成本。

19. **JD 和简历为什么默认不并行？** 业务上可以并行，但 Transformers 共享模型/GPU，直接线程并发有显存和状态风险，所以加锁；vLLM 能调度批处理时才受控并发。

20. **如何约束 JSON 输出？** 提示模板要求严格 schema，vLLM 可传 JSON Schema，返回后再去 thinking、修复常见 JSON 错误、按 Pydantic 和业务字段归一化。

21. **后处理会不会篡改模型输出？** 只允许基于原文证据恢复结构和通用别名，不凭常识补技能。并且单独报告 Raw 与 Normalized，避免隐藏后处理影响。

22. **一次 Match 要几次生成？** JD 解析一次、Resume 解析一次、解释一次，通常三次；vLLM 可并发前两次，规则评分本身是确定性 CPU 逻辑。

23. **如何保证解释不乱说？** 给解释模型的是结构化规则结果，提示要求只基于输入；评测检查解释与命中、缺失、硬条件是否一致。但这不等价于建议的现实有效性。

### 数据工程与治理

24. **数据从哪里来？** JD 来自受控公开招聘源和导入；Resume 包含基础样本、bootstrap 和审计候选；Match 主要由现有实体规则配对。每类来源单独记录准入状态。

25. **为什么 15,470 条 Resume 仍不够？** 行数包含同源扩展。有效来源组只有 2,557，其中 2,525 来自 bootstrap，来源高度集中，不能代表真实简历多样性。

26. **source group 是什么？** 表示同一个语义根来源。格式变体、OCR 变体和派生改写继承同组，使去重、切分和来源集中度基于实体而非文件。

27. **如何做去重？** 对去标识化、归一化后的内容计算稳定标识，结合来源元数据识别同源和近重复；不能只按文件名或原始字节哈希。

28. **为什么先切分再配对？** Pair 随机切分会让同一个 JD/Resume 通过不同边进入训练和验证。先切实体再在 split 内配对，才能阻断节点级信息泄漏。

29. **巨型连通分量怎么来的？** 负样本大量复用两侧实体，把看似不同的 Pair 连成图上的同一分量。历史 4,788/4,796 条边在一个分量，说明边随机切分几乎必然污染。

30. **当前 Match 数据最大问题是什么？** 4,798 Pair 全为规则合成，人工训练和真实观察 Pair 都为 0；显式年限 1,944 条又全是不满足，真实性和条件分布都不足。

31. **合成数据有没有价值？** 有，适合启动格式、补结构模式和测试，但必须标来源，不能用于证明真实招聘效果，也不能替代独立 Pair。

32. **Readiness 检查什么？** 格式、隐私、许可、来源、来源多样性、条件分布、真实 Pair 证据、跨集合泄漏八类；freshness 只检查管线版本一致，不等于 ready。

33. **为什么门禁要阻止训练？** 训练成功会产生一个看似正式的新 checkpoint，容易让人忽略数据证据失败。把判断前移到 shell gate 可以减少人为误用。

34. **如何处理简历隐私？** 检测并删除电话、邮箱、社交账号、身份证、姓名语境及性别、婚育、户籍、健康等敏感字段；原文可达不代表允许训练。

35. **FairCV 为什么没用？** 1,000 条隐私清洗后内容去重只剩 1 条，且许可用途不满足训练准入，因此拒绝比强行扩量更合理。

36. **`resume-ner` 为什么只 audit-only？** BIO NER 任务与目标结构不一致，大量敏感内容被剔除，原始来源、标注和授权证据又不足；包的开源许可不能自动覆盖原始个人数据权利。

### 评测与可信度

37. **什么是人工 holdout？** 完全隔离于训练和调参、由人审核标签的留出集；还必须避免实体、模板或派生变体泄漏，并在评测前冻结。

38. **为什么旧 64 条评测失效？** 它们来自 16 个基础案例的格式变体，基础案例进入过训练。人工看过标签不能消除训练污染，所以只能保留为历史实验。

39. **Gold V1 为什么可信？** 25 条全部人工复核，覆盖 9 类难例，完整 Pair、两侧 Match 实体和两个单任务路径五类重叠均为 0，并冻结了数据、预测、报告和模型哈希。

40. **Gold V1 有什么局限？** 只有 25 条，每错一条指标变化 0.04，岗位覆盖有限。它适合防回归和暴露错例，不足以估计线上总体准确率。

41. **Raw 指标是什么意思？** 原始 JD/Resume 模型解析结果接同一固定规则 scorer，不是 LLM 直接预测 Match；它用于隔离后处理和规则整合前的结构化质量。

42. **最终指标是多少？** Product Final 命中/缺失技能 F1 0.990649/0.986667，等级/方向 EM 0.96，学历、年限、解释一致率 1.0；必须同时说明 n=25。

43. **为什么 Raw 到 Final 提升这么多？** 归一化恢复字段、限制证据、统一方向/技能别名，规则再稳定执行硬条件。它是整个系统的提升，不能全归因于微调。

44. **剩下三类错误是什么？** 职责 Agent 被算作要求技能、OCR 的 `Py test` 未归一、AI 后端与算法平台 taxonomy 边界；分别对应字段边界、OCR 别名和方向体系问题。

45. **为什么不把 0.96 修到 1.0？** Gold 太小且错误已知，针对它加专用规则会过拟合。先在新独立样本观察错误是否复现，再做通用修复。

46. **如何保证实验可复现？** run manifest 记录 Git 状态、配置哈希、数据行数与哈希、来源分布、readiness、环境和命令；正式 Gold 另冻结 adapter、预测、报告和审计哈希。

### 工程判断与延伸

47. **项目最难的技术问题是什么？** 不是调用 14B，而是识别 pairwise 数据的实体泄漏和伪来源多样性，并让训练/评测工具真正执行这些约束。

48. **如果获得 1 万条新简历，第一步做什么？** 不直接合并。先核验许可和用途，做隐私清洗、内容去重、来源分组和条件统计，再看独立实体增量是否让 readiness 改变。

49. **如果要做线上系统，优先改什么？** 先扩大独立 Gold 和真实 Pair，再补鉴权、上传安全、任务队列、监控和冻结压测；不是先拆微服务或加入更多模型。

50. **这个项目最大的个人收获是什么？** 模型效果必须放在数据谱系、切分方式、后处理和产品门槛中解释。能训练、loss 下降和页面可用都不是最终证据；知道何时停止训练同样是工程能力。

## 术语速查

- **SFT**：监督微调，用目标答案教模型完成任务。
- **DPO**：直接偏好优化，利用 chosen/rejected 调整相对偏好，通常位于 SFT 之后。
- **QLoRA**：量化底座并只训练低秩 adapter，降低显存成本。
- **DFT**：本项目 SFT 使用的动态加权 loss 方案；不能与 NLL loss 数值直接比较。
- **Holdout**：训练和调参期间完全隔离的最终留出评测集。
- **Gold**：经人工确认、口径稳定的高可信标签集合。
- **EM**：Exact Match，预测与标签完全一致的比例。
- **F1**：precision 与 recall 的调和平均，适合技能集合匹配。
- **Source group**：同一语义根来源及其所有派生变体的分组。
- **Entity split**：按 JD/Resume 实体分组切分，而非随机切 Pair。
- **Data leakage**：训练信息通过重复实体、模板或派生内容进入评测。
- **Readiness**：数据是否具备训练资格的多维门禁。
- **Freshness**：派生数据是否与上游当前版本一致，不代表质量合格。
- **Bootstrap**：从少量根样本或规则启动的派生数据，不能等同真实独立来源。
- **Product Final**：归一化、规则评分和最终解释组成的产品输出层。
