# 核心推理流程优化

更新时间：2026-08-09

## 本轮目标

只优化当前产品最核心的“JD + 简历 → 可解释匹配”链路，不引入消息队列、微服务拆分、分布式调度或新的模型层。

## 审查发现

### 1. 可并行分支被主动串行

JD 解析和简历解析没有数据依赖，但 `ModelService.match()` 原来连续调用两次同步 `parse()`。vLLM 客户端也使用同步调用，因此推理引擎没有机会把两条请求放进同一调度窗口。

### 2. 默认 Transformers 不能靠线程直接提速

Transformers 后端只有一个 4-bit 14B 模型实例，`generate()` 外还有全局锁。简单增加线程最终仍然串行；移除锁则会增加 KV Cache 显存峰值，并引入同一模型实例并发访问风险。因此本轮保留其串行行为。

### 3. 批量 API 只是循环单条 API

`batch_parse` 和 `batch_match` 原来逐条处理。它们有批量接口外观，但没有批量吞吐收益。

### 4. 文件接口会阻塞异步事件循环

三个上传路由声明为 `async def`，读取文件后却直接执行 OCR/解析和模型推理。FastAPI 不会自动把异步路由中的同步重任务移入线程池，这会阻塞同一事件循环上的其他请求。

### 5. vLLM 不属于统一服务生命周期

此前 `start_project.sh` 只管理 API 和前端，vLLM 要手工分两次启动，`stop_project.sh` 也不会停止它。容易留下进程、端口和错误 adapter 版本。

### 6. 只有总延迟，没有阶段证据

一次匹配包含两个解析、规则计算和一次解释生成。只有总耗时无法判断优化是否真正作用于瓶颈。

## 开源项目实践对照

- Haystack `AsyncPipeline` 只在依赖允许时并发执行独立组件，并提供并发上限。当前 JD/简历分支正适合 fan-out/fan-in，而规则和最终解释仍需等待两路结果。
- vLLM 和 Hugging Face TGI 把请求调度与模型服务分开，利用连续批处理提高 GPU 利用率。并行应该提交给推理服务器调度，而不是让同一个原生 Transformers 模型被多个线程无界访问。
- BentoML 的 adaptive batching 强调服务端聚合、最大 batch 和等待窗口。当前项目不需要引入 BentoML，但应采用“服务端受控并发、客户端保持简单”的原则。
- Transformers 已提供 continuous batching 能力，但当前项目的版本下限和 4-bit LoRA 组合尚未完成兼容性验证，因此不在本轮启用。

## 已实现

### vLLM fan-out/fan-in

vLLM 模式下，JD 和简历解析通过两个受控工作线程同时提交；两路结束后才执行规则匹配与解释生成。

```text
JD ─────→ vLLM ────┐
                    ├→ 规则匹配 → 匹配解释
简历 ───→ vLLM ────┘
```

默认最大 vLLM 请求并发数为 4，由同一个 `BoundedSemaphore` 约束。批量解析和批量匹配也复用这一上限，返回顺序仍与输入一致。

### 保守的 Transformers 路径

Transformers 继续使用串行生成锁。没有为了形式上的“并行”牺牲显存稳定性。后续只有在真实 GPU 基准证明静态 batch 的质量、显存和延迟均可接受时，才考虑一次生成两个解析 prompt。

### 分阶段耗时

单次匹配响应新增：

```json
{
  "execution": {"backend": "vllm", "parse_mode": "parallel"},
  "timings": {
    "jd_parse_seconds": 0,
    "resume_parse_seconds": 0,
    "parse_wall_seconds": 0,
    "rule_seconds": 0,
    "analysis_seconds": 0,
    "total_seconds": 0
  }
}
```

前端结果页展示后端、并行模式、解析耗时、解释耗时和总耗时；高级设置中显示当前后端和匹配解析模式。

### 文件路由隔离

文件读取仍保持异步，读取后的同步解析与推理通过 Starlette threadpool 执行，避免阻塞 FastAPI 事件循环。

### 统一启停

设置 `JOBMATCH_INFERENCE_BACKEND=vllm` 后，统一脚本会管理 vLLM → API → 前端的启动顺序、健康检查、日志和 PID；停止脚本覆盖三个进程。

## 当前边界

- 当前 `tune-demo` 环境没有安装 `vllm` 和 `openai`，所以本轮完成了代码、并发单测和启动前依赖门禁，尚不能在本机做真实 vLLM GPU 对照。
- Transformers 模式仍然是默认选择，并保持原有推理行为。
- 并发提高吞吐但会增加 KV Cache 占用。首次压测从 `JOBMATCH_VLLM_MAX_CONCURRENCY=2` 开始，不应直接调到批量接口允许的最大样本数。
- 没有实现持久化解析缓存。简历属于敏感数据，在没有缓存隔离、TTL 和删除机制前，不应为省一次推理而落盘。

## 下一阶段优先级

1. 安装与当前 CUDA/PyTorch 兼容的 vLLM，在 2/4 并发下跑固定 holdout 基准。
2. 比较 Transformers 与 vLLM 的 JSON 成功率和字段指标，不能只看 p95。
3. 若单用户延迟仍高，尝试 Transformers 静态 batch 或合并双解析 prompt，但必须以字段准确率决定是否保留。
4. 最后再考虑流式状态更新；结构化 JSON 只有完整生成后才能可靠解析，流式主要改善感知延迟，不减少计算时间。

## 其余审查项

这些问题真实存在，但没有必要和本轮并行改完：

| 优先级 | 问题 | 建议 | 本轮不做的原因 |
| --- | --- | --- | --- |
| P0 | API 没有请求取消和服务端生成超时 | vLLM 稳定后增加超时、取消传播和明确的 504 | 需先确认所用 vLLM/OpenAI 客户端版本 |
| P0 | 已单独解析的 JD/简历在匹配时仍会重复解析 | 增加带 schema 版本的“使用已有解析结果”接口 | 必须防止客户端伪造结构化字段影响规则分数 |
| P1 | `server.py` 约 650 行，模型、上传、路由混在一起 | 按 model service / document ingest / routes 三层拆分 | 先稳定行为，再做机械拆分，避免同时改结构和语义 |
| P1 | API 响应没有统一 Pydantic contract | 为 parse/match/error 增加 response model | 需要先冻结新增的 timings/execution 字段 |
| P1 | 前端请求没有 AbortController 与超时提示 | 支持用户取消、区分加载/排队/生成阶段 | 取消必须先能传播到后端，否则只是隐藏结果 |
| P1 | 前端 Vue 来自 CDN | 引入本地构建和锁文件 | 当前单页演示可用，不是核心推理瓶颈 |
| P1 | 没有 CI 和依赖锁 | 加最小 lint/test CI，再固定训练与服务环境 | GPU/vLLM CI 需要单独资源，不宜伪装成普通单测 |
| P2 | 没有 Prometheus 指标 | 有持续流量后再增加请求、队列、token、显存指标 | 当前文件型基准报告足以支持单机选型 |

其中下一项最值得做的是“安全复用已有解析结果”。它能直接减少重复推理，但必须由服务端签名/缓存键或重新校验保护规则输入，不能直接信任浏览器提交的任意 JSON。
