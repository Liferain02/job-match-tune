# 产品交互与优化目标

更新时间：2026-08-09

## 本轮目标

围绕 JobMatchTune 的核心流程完成一轮不过度设计的交互优化：让用户清楚地完成 JD/简历输入、人岗匹配、依据核对和建议获取。保留 JD、简历单项解析与批量模式，但不让这些辅助能力干扰默认任务。

本轮不增加账号、数据库、岗位管理、候选人看板、在线简历编辑器或新的前端框架。

## 开源项目参考

| 项目 | 可借鉴做法 | 本项目取舍 |
| --- | --- | --- |
| [Resume Matcher](https://github.com/srbhr/resume-matcher) | 主流程是上传简历、粘贴 JD、查看改进内容；匹配分数、关键词和建议服务于同一求职任务 | 借鉴单一任务链，不扩展求职信、面试准备、模板编辑和多模型配置 |
| [OpenResume](https://github.com/xitanggg/open-resume) | 导入、解析和反馈边界清楚，并明确强调简历数据的隐私处理 | 借鉴清晰输入反馈与隐私提示，不建设简历制作器和实时 PDF 编辑器 |
| [Reqcore](https://github.com/reqcore-inc/reqcore) | 匹配排序展示评分明细，强调结论不是不可解释的黑盒 | 借鉴“结论必须附依据”，不复制完整 ATS、招聘管道、多租户和文档存储 |

这些参考指向同一个产品原则：用户首先需要完成一件事并理解结果，而不是先理解模型、Adapter、API 和任务枚举。

## 当前产品交互

默认路径只有四步：

1. 在“目标岗位 JD”中粘贴文本或上传文件。
2. 在“候选人简历”中粘贴文本或上传文件。
3. 点击“开始匹配”。
4. 按顺序查看综合结论、硬性条件与技能依据、简历优化建议；需要排查时再展开完整解析或原始 JSON。

交互约定：

- 文本与文件可以二选一；同时提供时，界面明确提示以文件为准。
- OCR 补充文本只在选择文件后按需展开，不占用默认页面。
- API 地址、模型路径、Adapter 和批量模式放入“高级设置”。
- 匹配分数明确标注为规则结果，模型负责文字解释和建议，避免把二者混成一个黑盒结论。
- 页面提示上传原件不主动持久化，同时提醒不要处理未经授权的真实简历。
- JD 解析和简历解析仍可切换，但默认任务是人岗匹配。

## 后续优化顺序

### P0：让核心结果更快、更可信

- 匹配接口先返回规则分数和命中依据，详细模型建议改为按需生成，减少用户等待三次顺序推理的时间。
- 为方向、学历、经验和技能结论补充对应的 JD/简历原文片段；用户应能直接判断抽取是否正确。
- 把文件格式不支持、正文为空、扫描件缺 OCR、服务未启动分别显示为可行动的中文错误，不只展示请求失败。
- 建立小型人工任务集，记录“能否完成输入—匹配—理解依据—采取行动”，而不是只看页面是否能打开。

### P1：补齐基本可用性

- 提供一个公开、脱敏的端到端样例，并在 README 中给出预期结果。
- 增加浏览器级主流程测试，覆盖示例填充、文本匹配、文件优先提示、结果层级和报告下载。
- 在 API 返回中增加评分规则版本，保证报告可比较。
- 明确临时文件生命周期和服务端日志边界；准备公网部署前再补认证、限流和删除机制。

### P2：由评测结果决定

- 只有精确技能别名在人工排序评测中成为主要瓶颈时，才引入语义召回或 reranker。
- 只有真实用户需要同时比较多个候选人时，才设计轻量对比视图；不提前建设候选人管理系统。
- 只有静态 Vue 方案阻碍浏览器测试或发布时，才引入构建工具和依赖锁定。

## 本轮完成标准

- 首次打开默认进入人岗匹配。
- 不展开高级设置即可完成一次文本或文件匹配。
- 用户能在结果首屏区分规则分数、事实依据和模型建议。
- JD/简历详细解析默认折叠，仍可查看和下载。
- 前端 smoke 对默认任务、文件优先提示、结果阅读顺序和解释边界进行断言。

## 浏览器实测记录

2026-08-09 使用 Chromium 分别按桌面端和 390px 移动端完成真实点击测试，覆盖空输入、示例填充、文件选择、高级设置、首次模型加载、人岗匹配、完整解析展开、原始 JSON、复制和报告下载。

真实 14B 流程结果：

- 首次模型加载约 103 秒；
- 两次示例匹配分别约 53 秒和 49 秒；
- 示例得到 95 分、高匹配，方向、学历、经验和五项技能依据均正常；
- 页面无横向溢出、控制台错误或请求失败；
- JSON 复制和 Markdown 报告下载正常。

实测后已直接修正：

- 移除单独的“预热模型”步骤，首次提交自动加载模型并提示约需 2–3 分钟；
- 将主按钮移动到输入区底部，移动端无需滚回页首提交；
- 在主按钮旁显示空输入错误、处理阶段、完成状态和真实耗时；
- 汉化文件选择控件并明确文件优先；
- 禁用空结果时的复制和下载操作；
- 修复移动端结果标题与工具按钮挤压；
- 避免任务完成状态被“模型已加载”覆盖。

仍然最值得优先优化的是响应时间：当前一次匹配需要 JD 解析、简历解析和建议生成三次顺序推理。下一轮应先返回可复算的规则结果，再让用户按需生成详细建议；在此之前不增加账户、ATS 工作流或新的模型层。
