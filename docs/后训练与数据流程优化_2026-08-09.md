# 后训练与数据流程优化

更新时间：2026-08-09

## 1. 本轮目标与结论

本轮目标是参考成熟开源后训练框架和招聘信息抽取项目，审查 JD 解析、简历解析、人岗匹配的 SFT/DPO 数据链路，并在不增加新框架的前提下修复最影响正确性和可复现性的流程问题。

结论：当前继续使用 TRL + PEFT + QLoRA 是合理的，主要问题不在训练器，而在派生数据可能陈旧、抽样把模板数量当成数据多样性、各训练阶段门禁互相耦合，以及合成偏好数据的性质没有被显式记录。本轮已经修复这四项。

## 2. 其他开源项目怎么做

### 2.1 通用后训练框架

- [TRL 数据格式](https://github.com/huggingface/trl/blob/main/docs/source/dataset_formats.md)把 SFT 与 preference 数据契约分开；DPO 使用同一 prompt 下的 `chosen`/`rejected`，并建议显式保存 prompt。本项目现有消息格式与此兼容，不需要迁移。
- [LlamaFactory 数据说明](https://github.com/hiyouga/LlamaFactory/blob/main/data/README.md)通过单一 `dataset_info.json` 注册文件、字段映射和是否为 preference 数据。可借鉴的是“配置真实生效且语义明确”，而不是复制它的全部配置层。本项目保留 `configs/dataset_registry.yaml`，删除了从未被构建器使用且总和不等于 1 的 `weight` 字段，只保留实际生效的样本数。
- [Axolotl](https://github.com/axolotl-ai-cloud/axolotl)用一份 YAML 串联预处理、训练、评测和推理，并支持本地/Hugging Face 数据与多种偏好训练。它说明统一入口和训练清单很重要，但本项目规模不需要引入第二套训练框架。

### 2.2 招聘领域项目

[SkillSpan](https://github.com/kris927b/SkillSpan)发布了 14.5K 句、12.5K+ 技能 span 的领域专家标注数据，保留来源字段，并分别评测领域适配与多任务训练。最值得借鉴的不是模型结构，而是：真实来源、专家标注、固定切分和独立评测比大量模板改写更能证明效果。其结果还表明多任务并不天然优于单任务，因此本项目必须分别保留 JD、简历、匹配评测，不能只看总 loss。

## 4. 已完成的核心优化

### 4.1 统一构建入口不再读取旧产物

`scripts/data/build_current_data_pools.sh` 现在按真实依赖顺序执行：

```text
JD pool
  → 简历评测种子与 pool
  → 匹配评测种子与 pool
  → JD/简历/匹配 SFT
  → 多任务 SFT
  → JD preference / 产品 preference
  → 全部 readiness 报告
```

修复了三个问题：原脚本在简历 pool 之前构造匹配数据；没有生成三项 SFT 和多任务 SFT；没有生成产品 preference，却直接读取可能陈旧的报告。JD 风险报告也改为每次 readiness 时重算。两个 SFT wrapper 只负责 SFT 转换，避免统一入口重复构建上游 pool。

### 4.2 多任务抽样优先原始来源

旧逻辑对所有行随机抽样。简历训练池中一个来源最多有 20 个格式变体，旧的 2800 条简历多任务训练样本只覆盖 1522 个来源。

新逻辑先从每个 `source_group` 取一条，再取第二轮变体。实际重建结果是 2800 条覆盖 2800 个来源；valid 为 338 条覆盖 338 个来源。readiness 还会检查：

- JD 来源比例至少 0.95；
- 简历、匹配来源比例至少 0.80；
- 同一个 source group 不得跨 train/valid。

这没有删除模板增强，只是不再让模板数量虚增多任务样本的语义多样性。

### 4.3 训练门禁按阶段解耦

旧逻辑要求每个正式训练入口同时满足 SFT、JD-DPO 和产品-DPO。现在改为：

- 多任务/简历 SFT：检查 `all_ready_for_sft` 和简历隐私；
- JD-DPO：只检查 `ready_for_dpo`；
- 产品 DPO：只检查 `ready_for_product_dpo`；
- 手工审查完整链路时仍可使用 `all`。

这使门禁更严格地对应当前训练输入，同时避免无关数据缺失阻塞当前阶段。

### 4.4 训练清单与偏好报告诚实记录来源

`run_manifest.json` 除路径、hash 和行数外，现在记录任务数量、唯一 source group 数量/比例、quality tier 和 preference provenance。偏好 readiness 会输出 `synthetic_preference_rate` 和 `preference_origin`。

当前两套 preference 的 `synthetic_preference_rate` 都是 1.0。它们可以通过格式和泄漏门禁并进入实验训练，但任何正式 adapter 仍必须通过人工留出集与产品回归，不能把合成 DPO 数据量本身当成产品提升证据。

### 4.5 外部 JD 来源与弱标注占比受控

公开 JD 清单固定了 revision 和 SHA-256，并把包装许可证、岗位正文权利和训练用途分开记录。两个无许可证 GitHub 爬虫源和正文仅有合理使用声明的 `open-apply-jobs` 不进入训练。学历弱标注家族最多占 JD 质量集 40%；最新真实构建为 `2070 / 5300 = 39.06%`，职责字段空率为 0.19%，经验字段空率为 50.62%，技能空率为 17.98%，学历空率为 26.49%，全部门禁通过。

### 4.6 修复格式变体跨切分泄漏

原检查只比较完整输入与答案，漏过了原始文本和 OCR 文本只差空格、标点、全半角的情况。新增 Unicode 规范化输入指纹后，首次发现 resume 9 个、match 5 个、multitask 1 个跨切分碰撞。现在切分前会把相同 `source_group` 或规范化输入相同的样本合并成连通组，重建后 JD、resume、match、multitask 四项碰撞均为 0。

### 4.7 全量 JD 规范化改为固定批次

旧实现同时保留数据库原始行、规范化行和 upsert 预处理列表。293582 条真实数据实测峰值约 6.3GB。新实现按 1000 条读取、规范化、写 SQLite 和 JSONL；全量验证耗时 18分24秒，峰值 RSS 103936KB。流式改造基准中新旧产物均为 293582 行且 SHA-256 相同；后续标签规则修复会正常改变产物哈希。

### 4.8 派生产物不能静默陈旧

规范化输出现在先写临时文件，成功后原子替换，避免中断留下半个正式 JSONL。`jd_clean.manifest.json` 记录原始数据库状态、正式输出哈希和语义规则哈希；readiness 还检查十个下游数据集相对其直接输入是否过期。当前 `pipeline_fresh=true`。只有真正影响清洗标签的规则进入语义哈希，批次大小和写盘实现变化不会触发没有意义的全量重建。

### 4.9 岗位方向冲突改为可重复审计

方向规则先后修复了“部门/领域前缀压过明确算法岗位”“网络安全被归到网络基础设施”和弱来源修复逻辑再次覆盖安全方向的问题。正式审计只统计标题恰好命中一个保守强信号的样本：最新重建的 5300 条 JD 中有 2479 条符合条件，34 条标签不同，冲突率 1.37%。剩余样本包含机器学习平台、嵌入式测试等复合岗位，只作为人工复核候选，不自动覆盖标签。报告固定写入 `outputs/eval_reports/jd_direction_conflicts.json`，每次训练 readiness 都会重算并附带该结果。

### 4.10 修复经验要求的确定性漏标和日期误抽

旧规则不接受数字与“年”之间的空格，也漏掉“至少两年”“3年+”“工作年限3～5年”等常见写法；另一方面，裸范围规则会把“1-2024年10月1日毕业”误当经验。修复后全量重建 293582 条规范化数据和全部下游集，质量集经验空值从 2899 降到 2727（54.70% → 51.45%），strict 从 3191 增到 3204，弱外部来源降至 39.55%。正式审计确认剩余空标签中可由当前规则明确恢复的数量为 0；没有明确信号的空值保持为空，不臆造“经验不限”。

### 4.11 JD 质量集不再全量载入 strict 输入

真实重建时，质量集构建器峰值 RSS 约 3329024KB。根因是为了最终选择约 3200 条 strict 样本，先把 269351 条、约 1.3GB 的去重 JSONL 全部解析成 Python 对象。入口现改为单遍读取并立即筛选，候选池、排序、随机种子和标签逻辑不变。独立临时目录全量基准耗时 3分35秒，峰值 RSS 为 347136KB（约下降 89.6%）；train、valid、test 和质量 profile 的 SHA-256 均与优化前正式产物完全一致。

### 4.12 JD 去重边判重边写盘

去重输入虽然已经是生成器，旧实现仍先把 269351 个完整结果字典放进列表，再一次性写盘，真实重建峰值约 1246356KB。新入口逐行判重并立即写出，只在桶中保留后续近重复比较需要的文本；缓存文本预先执行原比较函数本来就会执行的幂等规范化。独立全量基准输出 269351 行，SHA-256 与正式产物同为 `c228560de0a54d19b3f38b48ab18ba5d18ec396a594a19a226f910f854b4364b`，峰值 RSS 为 714916KB（约下降 42.6%），耗时 2分44秒。阈值、桶键、输出顺序和公共列表 API 均未改变。

### 4.13 技能 schema 变化不再绕过新鲜度门禁

旧规范化清单只哈希 Python 规则，遗漏了真正决定技能标签的 `configs/label_schema.yaml`，修改别名后旧数据仍可能显示 `pipeline_fresh=true`。清单现在记录 schema 路径并把内容纳入 transform SHA-256，配置变化测试会立即阻断训练。本轮先审计 1106 条空技能样本，只补含义明确的 23 项常见技术实体，schema 从 51 项增至 74 项。全量规范化耗时约 24 分钟；最终技能空值从 1106 降至 943（20.87% → 17.79%），恰好减少预审计命中的 163 条，弱外部来源降至 39.43%。新增技能抽样集中在预期岗位，没有用模型生成标签，也没有加入“开发能力”等泛词。

### 4.14 学历偏好不能被改成硬门槛

对 1403 条空学历样本做保守扫描后，只找到 11 条明确漏标：研究生、学士和专科表述。新增规则返回完整原文片段，特别保留两条“研究生及以上学历优先”的“优先”，避免改变招聘条件。全量重建后 11 条全部进入 strict 层，学历空值从 1403 降到 1392（26.47% → 26.26%），strict 增至 3211，弱外部来源降至 39.42%。其余空值没有明确信号，保持为空。

### 4.15 职责分段不能依赖“一行一个标题”

旧分段器一行只识别一个标题；当“岗位描述：……岗位要求：……”位于同一行时，职责会被后一个标题覆盖。它还缺少“岗位描述、核心职责、主要职责”等常见别名，并把普通句子中的“优先”误当加分段开头。新规则按标题位置切分同一行，支持 HTML、方括号和高置信无冒号标题，删除泛化“优先”别名。规则移入 `jd_sections.py` 并纳入规范化 transform SHA，今后修改会正确阻断旧产物。

小米历史源另有少量“工作职责/工作要求”正文倒置。这里只在要求/职责信号同时充分且倒置分数明显更高时交换，实际纠正 11 条；模糊或缺失正文不猜。全量重建后核心职责空值从 75 降至 10（1.42% → 0.19%）。剩余 10 条中，多数确实没有职责正文，另有个别源把职责写在错误标题下，不用更宽泛启发式强行搬移。

### 4.16 基础 SFT 只保留可能入选的候选

`build_sft_dataset.py` 原来无论最终选多少，都会把 269351 条去重 JD 全部读成 Python 对象。改造后单遍收集 strong 与 weak candidate，再沿用原有顺序、去重优先级、随机种子和切分逻辑。真实 strict 构建峰值 RSS 为 67072KB，expanded 20000 条构建峰值从约 3341824KB 降至 297472KB（约 -91.1%）；六个 train/valid/test SHA-256 与改造前逐一相同。

### 4.17 弱结构池筛选与去重合并为一遍

弱结构池原来先加载全部输入，再筛选、字段收缩、最后去重。现在输入使用生成器，合格行转换后立即计算同一个标题/公司/地点/正文前 500 字哈希；重复行不进入结果列表。真实输入 269351 条、输出 36090 条，SHA-256 仍为 `3373a68f1c030bdb77cf0db41c90c5ff22f8912dc90aa92ba0ff9944b6163100`，峰值 RSS 从约 1461760KB 降至 260096KB（约 -82.2%）。

### 4.18 组合池保持来源优先级但不保留全量输入

组合池旧入口分别加载 manual、public、supplemental 和 weak structured，再转换 manual、合并、统一去重。新入口仍严格保持 `manual → supplemental → weak structured → public` 的先到优先级，但每读到一条就完成转换和同键去重。真实输入规模分别为 269351、325、13261、36090，输出 39765 条；SHA-256 与改造前同为 `0c63e62a01555d886a669db4c9cb07b06d0c36c4965e1a283303756ed852e522`，峰值 RSS 为 301568KB。

## 5. 后续优化顺序

### P0：补小而可信的人工数据

1. 从人工留出集和真实产品测试中按错误类型抽样，不追求大规模。
2. JD 优先复核 `quality_weak` 中正文明确写出但标签漏掉的经验/技能，以及方向冲突审计生成的少量候选；正常缺省字段不算错误。
3. 匹配优先积累 100～300 组人工排序对：同一 JD/简历输入下，明确哪份解释更准确、可追溯、无编造。
4. 人工 preference 与规则合成 hard negative 分开报告和消融；前者不足时，DPO 只作为实验步骤，不默认晋级。

人工留出集（holdout）是预先隔离、不会参与训练和调参的“最终考试卷”。从中发现错误后可以总结错误类型并另采训练样本，但不能把同一题答案直接回灌后再用原 holdout 宣称提升。

### P1：让数据来源成为稳定契约

所有新 builder 都应保留 `source_group`、原始来源、标注方式和质量层级。每次训练先看唯一来源数和跨 split 泄漏，再看总行数。现阶段不需要引入数据版本平台；`dataset_registry.yaml`、文件 hash、run manifest 和 readiness 足够。

### P1：分别评测三项任务

多任务训练后必须分别比较 JD、简历、匹配的人工指标和产品失败类型。某一任务回退时先调整样本配比或质量，不因为总 loss 下降就晋级。匹配解释还要单独检查是否能引用 JD/简历中的真实证据。

### P2：训练有效后再优化推理延迟

产品匹配当前需要 JD 解析、简历解析、匹配解释三次生成。先建立稳定质量基线，再考虑缓存解析结果、并行解析或按需生成解释；暂不增加 embedding、reranker、队列或微服务。

## 6. 使用与验收

完整重建：

```bash
conda activate tune-demo
bash scripts/data/build_current_data_pools.sh
```

查看门禁：

```bash
bash scripts/data/assert_training_readiness.sh --stage sft
bash scripts/data/assert_training_readiness.sh --stage jd_dpo
bash scripts/data/assert_training_readiness.sh --stage product_dpo
```

本轮验收结果：统一入口完整重建后 `all_ready_for_training=true`、`all_ready_for_sft=true`、`pipeline_fresh=true`；多任务 source group 跨 split 重叠为 0；方向冲突候选率为 1.37%；经验规则可恢复空标签为 0；核心职责空值率降至 0.19%；三种分阶段门禁均通过。质量集构建峰值内存约 363MB，去重峰值约 692MB；随后基础 expanded SFT、弱结构池和组合池峰值分别降至或控制在约 290MB、254MB、295MB，输出哈希不变。长期目标继续运行，当前审查下游 builder 代码变化能否正确触发产物过期。
