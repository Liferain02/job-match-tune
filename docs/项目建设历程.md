# 项目建设历程

更新时间：2026-06-01

这份文档按项目从 0 到当前版本的实际推进过程整理：最开始为什么做这个项目，每一步做了什么，怎么做，留下了哪些代码和数据产物，以及后续为什么调整方向。

项目当前定位已经不是单一的 JD 解析 demo，而是一套面向招聘场景的多任务微调与应用系统，覆盖：

1. JD 结构化解析
2. 简历结构化解析
3. JD 与简历匹配度分析
4. 数据抓取、导入、清洗、审计和训练集构造
5. Qwen3-14B QLoRA 微调
6. FastAPI 服务和前端演示
7. 训练前数据 readiness 门控

---

## 1. 项目起点：先做 JD 结构化解析

项目最早的目标是：把公开招聘 JD 解析成固定 JSON，方便后续搜索、筛选、推荐和匹配。

最初定义的 JD 输出字段包括：

- `岗位方向`
- `核心职责`
- `必备技能`
- `加分项`
- `经验要求`
- `学历要求`

这个任务适合做 SFT，而不是只靠 prompt，原因是：

1. 输出结构稳定，字段边界明确。
2. 错误类型稳定，主要集中在职责/要求混淆、技能漏抽、学历和经验误判、岗位方向分类偏差。
3. 可以通过人工 gold、规则后处理和训练数据持续迭代。

所以项目一开始就把重点放在数据闭环，而不是只写一个一次性的推理脚本。

## 2. 模型路线：从可跑通到 Qwen3-14B

早期评估过 Qwen2.5 系列，但项目推进过程中结合模型发布时间、简历表达价值和中文能力，最后把默认路线调整为 Qwen3。

当前默认方案：

- 基座模型：`models/Qwen3-14B`
- 微调方式：`4-bit QLoRA`
- 训练框架：`Transformers + PEFT + TRL + Accelerate`
- 推理方式：
  - 本地 `Transformers + PEFT`
  - 服务化 `vLLM + OpenAI-compatible API`
- 后处理：`JSON 修复 + 字段归一化 + 规则校验`

为什么最终坚持 14B：

- 当前节点有 `3 x NVIDIA L20`，单卡约 46GB 显存。
- 1.7B 可以做验证，但容量偏小，不适合作为最终展示模型。
- 14B 配合 QLoRA 可以在有限 GPU 上完成微调。
- LoRA adapter 方便多轮增量训练和回滚。

训练链路中逐步接入或预留了这些能力：

- assistant-only loss
- DFT loss
- packing
- gradient checkpointing
- Liger Kernel
- DPO preference tuning

这些能力不是独立噱头，而是为两个目标服务：

1. 降低 14B 微调显存和吞吐压力。
2. 让项目能从 SFT 延展到偏好优化。

## 4. 第一条数据链路：腾讯招聘

最开始没有直接大规模抓所有网站，而是先选一个稳定公开源，把完整链路跑通。

第一条源是腾讯招聘。

选择原因：

- 技术岗位多。
- JD 结构相对完整。
- 公开接口比较稳定。
- 职责、要求、学历、经验等字段容易从正文抽取。

相关文件：

- `src/jobmatch_tune/crawler/tencent_careers.py`
- `configs/tencent_keywords.txt`
- `scripts/data/refresh_tencent_data.sh`

处理方式：

1. 按关键词请求腾讯招聘公开职位接口。
2. 分页拉取职位列表。
3. 请求职位详情补全文本。
4. 写入 `data/raw/tencent_jd_raw.jsonl`。
5. 同步写入 `data/jobmatch_tune.sqlite3` 的 `jd_raw` 表。
6. 进入后续 `raw -> clean -> dedup -> sft` 链路。

这个阶段的核心价值不是数据量，而是验证了项目的数据骨架：

```text
公开职位源 -> raw JSONL / SQLite -> 清洗 -> 去重 -> 规则标注 -> SFT JSONL
```

## 5. 扩展中文官网招聘源

腾讯链路跑通后，项目开始扩展更多中文官网源。选择标准是：

1. 匿名可访问。
2. 接口或页面结构稳定。
3. JD 正文完整。
4. 技术岗占比较高。
5. 能复现，不依赖登录态和高风险绕过。

### 5.1 百度招聘

百度招聘不是单纯 JSON API，而是从 SSR 页面数据中解析职位。

相关文件：

- `src/jobmatch_tune/crawler/baidu_talent.py`
- `configs/baidu_keywords.txt`
- `scripts/data/refresh_baidu_data.sh`

做法：

1. 按关键词访问搜索页。
2. 解析页面中的 `window.__INITIAL_DATA__`。
3. 提取职位列表和详情。
4. 映射到项目统一 raw schema。

### 5.2 京东招聘

京东招聘后来成为重要来源，因为匿名职位接口比较稳定。

相关文件：

- `src/jobmatch_tune/crawler/jd_careers.py`
- `scripts/data/refresh_jd_data.sh`

做法：

1. 请求京东招聘匿名列表接口。
2. 分页拉职位列表。
3. 请求详情接口。
4. 写入 raw JSONL 和 SQLite。

### 5.3 Moka 托管招聘官网

Moka 是后续中文官网数据扩充中最有价值的一条线。

选择原因：

- 很多技术公司招聘官网托管在 Moka。
- API 形态相对一致。
- 通过配置公司源即可复用同一个抓取器。
- JD 质量通常比泛化招聘平台导出数据更稳定。

相关文件：

- `src/jobmatch_tune/crawler/moka_careers.py`
- `configs/moka_sources.yaml`
- `scripts/data/refresh_moka_data.sh`

做法：

1. 在 `configs/moka_sources.yaml` 维护公司源。
2. 对每个源调用统一抓取逻辑。
3. 拉职位列表和详情。
4. 写入 `data/raw/moka_jd_raw.jsonl` 和 SQLite。

- 高性能计算

### 5.4 其他官网源

后续也接入或探测过：

- 携程
- 小米
- 美团
- 滴滴
- 拼多多
- 得物
- 小红书
- 蚂蚁
- B 站

项目没有把所有招聘平台都硬接进主线，原因是：

- Boss 直聘、智联等平台常需要登录或强风控。
- 部分接口签名和网关校验不稳定。
- 抓取成本高，但训练数据结构质量未必更高。
- 项目目标是可复现的工程链路，不是一次性抓取。

## 6. 接入公开数据集：扩大原始池而不是直接训练

官网数据质量高，但增长慢。为了扩大原始语料池，项目接入了公开数据集和职位导出文件。

相关文件：

- `src/jobmatch_tune/crawler/import_public_job_data.py`
- `configs/public_job_sources.yaml`
- `configs/public_job_sources_zh_large.yaml`
- `scripts/data/import_public_job_exports.sh`
- `scripts/data/import_chinese_job_exports.sh`

接入过的数据包括：

- GitHub `jhcoco/bosszp`
- GitHub `WorkAggregation`
- Hugging Face `open-apply-jobs`
- Hugging Face 中文招聘学历数据

这一步的重要结论是：

```text
公开数据集进入 raw pool 或 candidate pool，不等于直接进入高质量训练集。
```

原因：

- 有大量英文 JD，不适合当前中文企业场景。
- 有不少教师、培训、销售、运营、实习、校招、非技术岗。
- 有些字段来自弱标注，不适合作为默认监督信号。
- 文本结构不统一，需要先审计和分层。

这也是项目后面反复强调的原则：数据量不是唯一目标，高质量 SFT 数据必须经过准入门控。

## 7. 数据落盘：raw JSONL + SQLite

所有抓取和导入的 JD 最终落到两类存储：

1. `data/raw/*.jsonl`
2. `data/jobmatch_tune.sqlite3`

这样设计的原因：

- JSONL 方便人工审查和离线重放。
- SQLite 方便统一重建、统计、去重和增量写入。
- raw 层尽量保留原貌，只做最小字段映射。

raw 层不是训练集，它只是原始事实层。

## 8. 清洗、标准化和去重

原始数据来自多个站点，不统一就不能训练。项目把所有 JD 转成统一 clean schema。

相关文件：

- `src/jobmatch_tune/preprocess/clean_text.py`
- `src/jobmatch_tune/preprocess/normalize_jd.py`
- `src/jobmatch_tune/preprocess/jd_field_rules.py`
- `src/jobmatch_tune/preprocess/deduplicate.py`
- `scripts/data/rebuild_data_pipeline.sh`

处理步骤：

1. 清理 HTML、特殊空白、重复符号和页面噪声。
2. 统一标题、公司、地点、正文、来源等字段。
3. 拆分 `岗位职责 / 任职要求 / 加分项`。
4. 通过规则抽取学历、经验、技能和岗位方向。
5. 标记 `sft_ready`。
6. 基于标题和正文做去重。
7. 输出 `data/interim/jd_clean.jsonl` 和 `data/interim/jd_clean_dedup.jsonl`。

这一步解决的问题是：把来自不同网站、不同格式、不同字段名的招聘文本放到同一处理平面。

## 10. 为什么几十万原始数据不能直接变成几十万高质量训练集

项目过程中原始 JD 数量已经做到几十万，但严格高质量训练集没有同步到几十万。

原因不是数据没有价值，而是原始数据和 SFT 数据之间隔着质量门控。

不能直接训练的典型原因包括：

- 非中文。
- 非技术岗。
- 教师、培训师、编导、新闻编辑、销售、运营等岗位混入。
- 职责和要求正文太短。
- 缺少学历、经验、技能等关键监督信号。
- 岗位方向无法稳定判断。
- 弱标注字段可能互相污染。
- 相同职位跨平台重复。

项目中间曾经把默认训练集扩到更大规模，但复查后发现混入太多弱标注样本和非目标职位。后续调整为：

1. 默认训练集收紧口径。
2. 大规模样本进入候选池和扩展集。
3. 通过质量分层逐步回收可训练样本。

这个调整不是“数据减少”，而是把不同质量层分开，避免弱数据污染默认模型。

## 11. JD 训练数据分层

当前 JD 数据不是一条线，而是多层。

### 11.1 `data/sft/`

默认严格集。

特点：

- 高信任中文官网源。
- 技术岗标题明确。
- 方向能稳定识别。
- 职责/要求结构较完整。
- 适合做最保守的 JD 解析训练和对照。

### 11.2 `data/sft_jd_strict_plus/`

strict_plus 是 strict 和弱标注之间的过渡层。

特点：

- 从合并候选池回收结构较完整的样本。
- 过滤低信号标题和明显非技术标题。
- 用于扩充严格集不足的问题。

### 11.3 `data/sft_jd_quality/`

这是当前 JD 解析最重要的质量集。

构建逻辑：

1. 先放入 strict 样本。
2. 再补 strict_plus 样本。
3. 再补 quality_weak 样本。
4. 不够时才考虑 bootstrap，但当前没有使用 bootstrap 兜底。

当前目标规模：

- `train = 4400`
- `valid = 550`
- `test = 550`
- 总计 `5500`

最近一次重建后的分层统计：

- `strict = 3200`
- `strict_plus = 260`
- `quality_weak = 2040`
- `bootstrap = 0`

### 11.4 高风险 JD 过滤

最近新增了训练前风险门控。

相关文件：

- `src/jobmatch_tune/dataset/jd_quality_risk.py`
- `src/jobmatch_tune/eval/report_jd_quality_risks.py`
- `src/jobmatch_tune/dataset/build_jd_quality_sft_dataset.py`
- `scripts/data/report_jd_quality_risks.sh`

风险规则会检查：

- 教师、编导、新闻编辑等可疑非技术标题。
- `quality_weak` 层样本。
- 弱公开来源。
- 学历、经验、技能、职责字段为空。
- 单条职责过长。

构建 `data/sft_jd_quality/` 时，高风险样本会被过滤，不再进入 JD quality 训练集。

当前风险审计结果：

- `total = 5500`
- `high_risk_samples = 0`
- `high_risk_rate = 0.0`

这一步的意义是：训练前先把明显风险样本挡掉，而不是等模型学坏后再调 prompt。

### 11.5 样本级质量分数

在高风险过滤之后，又把质量信息写入了每条 JD quality 样本的 `meta`。

新增字段：

- `quality_tier`
- `quality_reason`
- `quality_risk_score`
- `quality_risk_reasons`
- `quality_score`

质量分数的思路是：

1. `strict / strict_plus / quality_weak / bootstrap` 先给不同基础分。
2. 再根据风险原因扣分。
3. 高风险样本直接被过滤，不进入训练集。
4. 留在训练集里的样本仍保留低风险原因，方便人工复核和采样加权。

当前质量画像：

- `quality_score_avg = 78.42`
- `risk_score_counts = 0:944, 1:2949, 2:1261, 3:346`

这一步参考的是 Data-Juicer / DataFlow 一类数据处理框架的可追溯思路：训练样本不只是文本，还要带上来源、准入原因和质量信号。

随后又根据低分样本复核发现的职责/要求粘连问题，把 section 边界修复前移到 JD quality 构建阶段：

1. `核心职责` 中出现 `任职要求 / 技能要求 / 任职资格` 等 marker 时，自动切出并合并到要求文本。
2. 要求文本中出现 `岗位职责 / 工作职责` 等 marker 时，自动切回职责文本。
3. 风险审计增加字段边界泄漏原因，用于继续追踪漏修样本。

重建后：

- `oversized_single_responsibility` 从 `220` 降到 `112`
- `responsibility_contains_requirement_marker = 0`
- `requirement_contains_responsibility_marker = 0`
- `high_risk_samples = 0`

### 11.6 低分样本复核集

有了 `quality_score` 之后，项目新增了低分优先复核集：

- `data/eval/jd_quality_low_score_review_seed.jsonl`

生成命令：

```bash
bash scripts/data/build_jd_quality_review_set.sh \
  --strategy lowest-score \
  --per-tier 50 \
  --out data/eval/jd_quality_low_score_review_seed.jsonl
```

这份文件每个 tier 抽 `50` 条低分样本，共 `150` 条。它主要用来人工检查：

- 职责和要求是否粘在一起。
- 弱公开源是否有字段缺失。
- `quality_weak` 是否真的可以进入训练。
- 岗位方向是否被标题或技能误导。

这一步把数据处理从“生成训练集”继续推进到“生成可操作的人工复核任务”。

## 12. 简历解析链路

项目后面从 JD 解析扩展到简历解析，因为最终产品目标是：

```text
JD 解析 -> 简历解析 -> JD 和简历匹配度分析
```

简历解析目标字段：

- `目标岗位`
- `教育背景`
- `核心技能`
- `实习经历`
- `项目经历`
- `优势标签`

相关文件：

- `src/jobmatch_tune/resume/ingest.py`
- `src/jobmatch_tune/resume/normalize.py`
- `src/jobmatch_tune/resume/ocr.py`
- `src/jobmatch_tune/dataset/build_resume_sft_dataset.py`
- `scripts/data/resume_ingest.sh`
- `scripts/data/resume_normalize.sh`
- `scripts/data/resume_ocr_sidecar.sh`

简历格式比 JD 更复杂，项目按下面方式处理：

1. `txt` 简历直接读取文本。
2. `docx` 简历用文档解析抽取文本。
3. 文本型 `pdf` 用 PDF 文本抽取。
4. 图片型 PDF 或图片简历标记为 `needs_ocr`。
5. OCR 结果通过 sidecar 文件进入统一 normalize 层。
6. 所有格式最终统一成 clean resume text。

为了让模型适应真实简历格式，数据构造时生成了多种变体：

- 原始文本
- bullet list
- compact
- OCR-like
- education-first
- project-first
- table-like
- dense resume
- mixed CN/EN

当前简历 SFT 数据规模：

- `data/sft_resume/train.jsonl = 39132`
- `data/sft_resume/valid.jsonl = 5083`
- `data/sft_resume/test.jsonl = 4952`

## 13. JD 与简历匹配链路

匹配任务是项目的第三条主线。

输入：

- JD 文本
- 简历文本
- JD 结构化结果
- 简历结构化结果
- 规则匹配结果

输出：

- `匹配结论`
- `匹配优势`
- `主要短板`
- `简历优化建议`
- `推荐投递岗位方向`

相关文件：

- `src/jobmatch_tune/match/rule_engine.py`
- `src/jobmatch_tune/dataset/build_match_sft_dataset.py`
- `src/jobmatch_tune/dataset/build_match_train_pool_synthetic.py`
- `src/jobmatch_tune/dataset/build_match_train_pool_combined.py`
- `scripts/data/build_match_sft_dataset.sh`

处理方式：

1. 用规则引擎计算方向、技能、学历、经验匹配。
2. 生成不同匹配等级样本。
3. 构造 `prompt / assistant JSON`。
4. 对高匹配、一般匹配、低匹配都给出解释。
5. 训练模型输出更自然、结构化的匹配分析。

当前 match SFT 数据规模：

- `data/sft_match/train.jsonl = 3917`
- `data/sft_match/valid.jsonl = 486`
- `data/sft_match/test.jsonl = 493`

最近一次扩量把 synthetic match 生成从 `720` 个 JD 提升到 `1200` 个 JD，并把每个 JD 的负样本从 `1` 个提升到 `2` 个。重建后：

- `data/eval/match_train_pool_combined.jsonl = 4896`
- 覆盖 `高匹配 / 较匹配 / 基本匹配 / 低匹配`

## 15. 评估体系

项目不是只看训练 loss，而是逐步补了多层评估。

### 15.1 人工 gold 评估

早期先做小规模人工 gold，然后扩展到 50 条。

重点评估字段：

- 岗位方向
- 职责
- 要求
- 技能
- 学历
- 经验

这个阶段明确过一个原则：

```text
职责 / 要求 / 技能 / 学历 / 经验 的字段边界没修好前，不盲目加训练轮数。
```

### 15.2 数据 readiness 审计

相关文件：

- `src/jobmatch_tune/eval/report_data_readiness.py`
- `scripts/data/report_data_readiness.sh`

readiness 会检查：

- JD quality 总量
- JD 高风险率
- resume 数据量
- match 数据量
- 多任务数据是否存在
- 训练/验证拆分是否有交叉污染
- 关键字段覆盖率

这一步的作用是：训练前先判断数据是否值得训练。

### 15.3 JD 风险审计

相关文件：

- `src/jobmatch_tune/eval/report_jd_quality_risks.py`
- `scripts/data/report_jd_quality_risks.sh`

它不是直接训练脚本，而是训练前质量报告。最近已经把风险规则抽成 `src/jobmatch_tune/dataset/jd_quality_risk.py`，让审计和构建共用同一套口径。

## 20. 下一步建议

下一步不建议马上盲训，而是按下面顺序推进：

1. 继续抽检 `data/sft_jd_quality/`，尤其是 `quality_weak` 层。
2. 补更多中文官网技术岗位，优先 AI、芯片、云、自动驾驶、HPC、infra。
3. 扩大 JD quality，同时保持高风险样本不进训练集。
4. 扩充真实或半真实简历样本，减少纯模板化 resume 数据占比。
5. 扩 match 数据，增加低匹配和边界匹配样本。
6. 跑一次 Qwen3-14B 多任务 smoke SFT。
7. 用人工 gold 集评估 JD、resume、match 三类输出。
8. 再决定是否做完整 SFT 和 DPO。

这个项目目前最核心的原则仍然是：

```text
数据质量先于训练轮数，训练 readiness 先于大规模 SFT。
```
